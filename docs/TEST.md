## 1. [STOREFRONT] 식당OS 쇼핑몰

### 주문 생성

- [ ] 상품 선택 → 장바구니 → 결제 화면 → 주문 생성까지 **끊김 없이** 완료되는가 (로그인·RLS·네트워크 오류 시 사용자 메시지가 운영 대응 가능한가).
- [ ] 결제(주문 완료) 버튼 **연타** 시 `commerce_orders`가 **1건만** 생기는가 (관리자 목록·DB row count로 교차 확인).
- [ ] 주문 완료 직후 **새로고침·뒤로 가기 후 재전송** 시 중복 주문이 생기지 않는가 (`checkout_submission_id`·멱등 경로 적용 후 검증).
- [ ] **네트워크 throttling**(느린 3G 등)에서 타임아웃 후 재시도해도 주문이 1건으로 수렴하는가 (이중 청구·이중 배송 CS 리스크).
- [ ] 동일 시나리오 후 **관리자OS 주문 목록**에도 **1건**만 보이는가 (운영·공급자 전달 단일 진실원).

### 장바구니

- [ ] 품목 **추가** 후 수량·금액이 식당 입장에서 이해 가능한가.
- [ ] **수정**(수량 변경)이 저장·표시에 반영되는가.
- [ ] **삭제** 후 합계·체크아웃 진입이 일관되는가.
- [ ] 주문 성공 후 **장바구니가 비워지는가** (재주문 시 이전 주문과 섞이지 않는지·운영 혼선 방지).

### 상품 목록 / 상세

- [ ] `/buy` 목록이 **노출 정책**(공개·visible)과 어긋난 상품을 보여주지 않는가.
- [ ] **hidden / 비공개** listing이 목록·직링크 상세에서 **차단**되는가 (직URL 유출 시 플랫폼·식당 분쟁 리스크).
- [ ] 상세에서 **썸네일·상세 이미지**가 깨지지 않고 로딩 실패 시 사용자 안내가 있는가.
- [ ] **모바일** 실기기에서 가독성·터치 타깃·스크롤 후에도 주요 행동(담기·주문)이 닿는가.
- [ ] 상세·체크아웃에서 **하단 CTA(담기/주문)** 고정 또는 동등한 도달성이 있는가 (한 손 조작·운전 중 금지이더라도 업무 현장 사용성).
- [ ] 관리자OS **storefront preview iframe**과 식당OS 실제 `/buy`·상세가 **동일 정책·동일 상품 상태**로 보이는가 (미리보기만 통과하는 사고 방지).

### 반복주문 UX

- [ ] **재주문**(최근 구매·동일 품목 다시 담기 등)으로 이어지는 UI 경로가 있는가.
- [ ] 식당 입장에서 **“다음에도 여기서 산다”**고 느낄 만큼 반복 구매가 **짧은 동선**인가 (탭 수·입력 반복).
- [ ] RFQ(견적·입찰) 흐름 이후 **storefront로 다시 들어와 구매**할 수 있는 진입점·안내가 있는가 (없으면 RFQ만 쓰고 storefront는 유령화될 운영 리스크).

## 2. [ADMIN] 관리자OS

### 상품 등록

- [ ] `createListingFull` 경로로 **저장 → 목록 반영**까지 한 사이클이 되는가 (중간 실패 시 롤백·메시지가 운영자가 조치 가능한가).
- [ ] **썸네일** 업로드 후 Storage·DB URL이 연결되는가 (깨짐·403 시 담당자가 원인 추적 가능한가).
- [ ] **상세 이미지** 다장 업로드·순서가 저장·재편집 시에도 유지되는가.
- [ ] **공개 / 비공개(초안·숨김 등)** 전환이 식당 노출과 일치하는가.
- [ ] **validation 실패** 시 저장되지 않고, 실패 이유가 한 화면에서 파악되는가 (재시도 비용).
- [ ] 저장 성공·실패 **toast**가 구분되는가 (성공인데 실패로 오해하는 CS 방지).
- [ ] 동일 폼에서 **중복 저장**(중복 클릭) 시 주문·listing이 이중 생성되지 않는가 (가능한 한 서버·DB 제약과 함께 확인).

### 주문 처리

- [ ] `/admin/commerce/orders` **목록**이 필터·미확인 큐와 실제 업무 순서에 맞는가.
- [ ] **주문 상세**에서 품목·배송·연락처·결제 방식을 한 번에 판단할 수 있는가.
- [ ] **상태 전이**가 정책 문서와 같고, 잘못된 전이가 막히는가 (전화로만 되돌리는 운영 지옥 방지).
- [ ] **CSV export**로 공급자에게 그대로 넘길 수 있는가 (열기·인쇄·공유).
- [ ] **XLSX export**가 실제 xlsx로 열리는가 (확장자만 바꾼 파일이 아닌지).
- [ ] export 파일 **한글**이 Excel·메모장에서 깨지지 않는가 (공급자 대외 품질).
- [ ] export가 **한 줄 = 한 상품(라인)** 인지, 주문 1건 다품목이 **여러 행**으로 나오는지 (발주 실수·수량 누락 리스크).
- [ ] storefront 주문을 **입금 확인 완료(`paid`)** 처리했을 때 **`payments`** 원장에 **`commerce_order_id`** 로 inbound `confirmed` 행이 자동 생성되는가 (`PLATFORM-ERP-P0-001`, 손 실행 순서는 **`docs/TEST-DEV/TEST-RUN-001.md` STEP 8**). 이후 **숫자·중복·취소·RLS**는 **`docs/TEST-DEV/TEST-RUN-ERP-001.md`** 로 검증한다.

### 상품 운영 UX

- [ ] 등록된 상품의 **명·스펙·이미지 일괄 수정**이 코드 없이 가능한가 (불가면 “50개 SKU 유지보수” 현실성 평가).
- [ ] 상품 **삭제(또는 완전 비노출)** 요구가 있을 때 정책·UI가 일치하는가 (discontinued만 가능 등).
- [ ] 상품 **50개 이상**을 하루 관리할 때 **스크롤·검색·필터**로 버틸 수 있는가.
- [x] 상품 목록에서 **`window.prompt` 기반 가격 수정이 제거**되었고, 가격·핵심 메타는 **`/admin/commerce/products/[id]/edit`** 에서 다루는가 (`COMMERCE-009` 코드 반영).

### COMMERCE-008 구현 검증 (코드·스펙 기준, 수동 재확인 권장)

- [x] 상품 **quick edit** 구현 (`getListingForEdit` / `updateListingFull`, 편집 라우트·`ListingEditClient`)
- [x] **dirty check** 구현 (저장하지 않은 변경 시 이탈 확인)
- [x] **`admin_logs`** 저장 시 **`listing_updated`** (before / after / changed_fields) 기록
- [x] 상품 목록 **수정** 버튼 → **edit 페이지** 이동

### COMMERCE-009 / 운영 UI·문서 정합 (수동 검증)

- [ ] 상품 수정 후 **storefront**에 가격·이미지·노출이 기대대로 반영되는가
- [ ] **dirty** 상태에서 브라우저 **뒤로가기** 시 confirm이 표시되는가
- [ ] 저장 후 **`admin_logs`** 에 기대 필드로 기록되는가
- [ ] 상품 목록에 **`window.prompt` 가격 수정**이 남아 있지 않은가
- [ ] 상품 **신규 등록** 화면에 **DEBUG TEST BLOCK** 이 없는가
- [ ] **운영 빌드**(`NODE_ENV=production`)에서 forensic·DEBUG 패널이 **노출되지 않는**가

## 3. [RFQ]

- [ ] RFQ **생성**부터 제출까지 식당이 실수 없이 완료할 수 있는가.
- [ ] 공급자 **입찰/응답** 흐름이 끊기지 않는가 (알림·목록·상태).
- [ ] **계약 전** 단계에서 식당명·식별 정보가 공급자에게 **노출되지 않는지** (스크린·export·이메일까지 포함해 확인).
- [ ] 공급자가 플랫폼 밖으로 식당을 붙잡을 **우회 경로**(연락처 노출·카톡 유도)가 없는가.
- [ ] RFQ 완료 후 **storefront로 이어지는** 안내·링크·데이터 추적이 있는가 (없으면 “RFQ만 쓰고 매출은 밖으로” 운영 리스크).

## 4. [비가역 원칙]

> 이 섹션은 “기능 테스트”가 아니라 **플랫폼 생존 원칙 검증**이다.

- [ ] RFQ **계약 전** 공급자에게 **식당명·직접 식별**이 노출되지 않는가 (우발적 유출 포함).
- [ ] storefront 주문·주문 export·카카오 요약에 **공급자 직접 연락처·내부 식별**이 붙지 않는가.
- [ ] UI 문구·버튼이 **플랫폼 외 개인 연락·다른 채널 결제**를 유도하지 않는가.
- [ ] 공급자가 주문 데이터만으로 **식당을 특정**할 수 있는지 여부를 운영 관점에서 판단했는가 (가능하면 [!] 및 완화 계획).
- [ ] RFQ → storefront 전환 구간에서 **수수료·중개 우회**가 가능한 구조인가 (가능하면 플랫폼 매출·분쟁 리스크).

## 5. [운영 테스트]

- [ ] 주문 **30건**을 export했을 때 파일 크기·열 너비·정렬로 **공급자에게 그대로 전달** 가능한가 (수동 편집 없이).
- [ ] **100건** 규모에서 관리자 주문 화면이 **스크롤·필터·버튼 반복**으로 하루를 버틸 수 있는가 (정무님 1인 처리 시나리오).
- [ ] **동일 배송지·다른 주문**을 export/목록에서 구분할 수 있는가 (주문번호·식당명·일시).
- [ ] 모바일에서 **실제 주문 3분 내**(탐색·담기·배송 입력·제출) 목표가 현실적인가 (불가 시 현장 대체 프로세스 문서화).
