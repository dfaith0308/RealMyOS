# AI 작업 이력 — worklog 운영 규칙

> **목적**: Cursor·AI가 장기 작업해도 **무엇을·왜·어떻게** 바꿨는지 한눈에 추적한다.  
> **범위**: 본 디렉터리는 **문서 기반 로그**만 다룬다. 코드·migration 실행은 각 worklog 본문에 따라 별도 수행.

---

## 1. 기본 원칙

| 원칙 | 설명 |
|------|------|
| **작업 1회 = 로그 1개** | 의미 있는 작업 단위(한 PR·한 이슈·한 세션 목표)마다 **worklog 파일 1개**를 만든다. 같은 날 여러 주제면 **파일을 분리**한다. |
| **사후 보강 최소** | 작업 직후 또는 PR 직전에 초안을 채운다. 며칠 뒤 “기억 의존” 작성은 지양. |
| **추측 금지** | migration·스키마·테스트는 **실제로 한 것만** 기록. 실행 안 했으면 “미실행”으로 명시. |

---

## 2. 파일명 규칙

```
YYYY-MM-DD_phase-topic.md
```

| 부분 | 규칙 |
|------|------|
| `YYYY-MM-DD` | 작업 **완료일** 또는 **로그 확정일** (타임존 팀 합의, 기본 UTC 권장). |
| `phase` | 로드맵 단계 또는 배치 이름: `phase0`, `phase1`, `docs`, `chore`, `hotfix` 등 **소문자·하이픈**. |
| `topic` | 짧은 식별자: `tasks.md` ID·기능명·위험 ID 등 **소문자·하이픈** (`db-danger-004`, `rfq-atomic`). |

**예시**

- `2026-05-06_phase1_db-danger-004.md`
- `2026-05-06_phase1_rfq-atomic.md`
- `2026-05-08_docs_worklog-readme.md`

**금지**: `log.md`, `temp.md`, `notes.md`, 날짜 없는 단일 파일 누적.

---

## 3. 기록 필수 항목

아래는 **모든 worklog에 반드시** 포함한다 (해당 없음이면 “해당 없음” 한 줄).

1. **작업 목적** — 왜 이 작업을 했는지 1~3문장.  
2. **관련 `tasks.md` ID** — `DB-DANGER-004`, `SUP-PARTIAL-003` 등; 없으면 “없음” + 대체 맥락.  
3. **수정 파일 목록** — 경로 나열; 문서만이면 그대로, 코드 없으면 “코드 변경 없음”.  
4. **변경 내용 요약** — 불릿으로 요약; 동작·의도·트레이드오프.  
5. **migration 여부** — `없음` / `계획만` / `파일 추가(미적용)` / `dev 적용` / `prod 적용` 중 택일 + 파일명 있으면 기재.  
6. **테스트 결과** — 실행한 명령·스코프·pass/fail/skip; 미실행 시 이유.  
7. **남은 위험** — 알려진 리스크·가정·기술 부채.  
8. **다음 권장 작업** — 후속자·AI에게 한 줄 이상.

---

## 4. 완료 / 미완료 상태 기록

파일 **상단** YAML 프론트매터 또는 첫 번째 표로 상태를 고정한다.

**권장 (표)**

| 필드 | 값 |
|------|-----|
| **상태** | `완료` / `부분완료` / `중단` / `초안` |
| **완료일** | `YYYY-MM-DD` (상태가 완료·부분완료일 때) |
| **차단 사유** | 상태가 중단·초안일 때만 필수 |

- **완료**: 목적 달성, 리뷰 가능한 산출물 있음.  
- **부분완료**: 일부 범위만 끝남; “남은 위험”·“다음 작업”에 반드시 명시.  
- **중단**: RULE 위반·권한·환경 문제 등으로 중단; **차단 사유** 필수.  
- **초안**: 로그만 먼저 열어둔 상태; 실제 작업 전이면 후속에서 갱신.

---

## 5. migration 여부 기록 규칙

| 상황 | 기록 예 |
|------|---------|
| 코드만 변경, DB 무관 | `migration: 없음` |
| `supabase/migrations/`에 파일 추가, DB 미적용 | `migration: 파일 추가 — 20260510120000_foo.sql (미적용)` |
| dev/staging만 적용 | `migration: dev 적용 — 동일 파일명, 일시·실행자` |
| production 적용 | `migration: production 적용 — 일시·승인자·백업 확인 여부` |
| 거버넌스·문서만 (DDL 없음) | `migration: 없음 (문서/정책만)` |

**금지**: 실제로 만들지 않은 migration 파일을 “있는 것처럼” 쓰기. **환각 migration 이력**은 `docs`·`tasks.md` SSOT 정책과 동일하게 금지.

---

## 6. rollback 관련 기록 원칙

- **계획 단계**: 롤백이 가능한지(되돌리는 migration, feature flag, 배포 revert)를 “남은 위험” 또는 별도 소절에 적는다.  
- **실제 롤백 수행 시**: **같은 날짜에 별 worklog**를 두거나, 기존 worklog에 **“Rollback 부록”** 절을 추가하고 롤백 커밋·범위·DB 여부를 명시.  
- **DB 롤백**: 데이터 손실 가능성이 있으면 반드시 **누가·언제·어떤 환경**에서 했는지 적는다. 추측으로 “롤백 완료” 쓰지 않음.

---

## 7. 테스트 결과 기록 원칙

| 항목 | 설명 |
|------|------|
| **범위** | 단위 / 통합 / 수동 / CI job 이름 |
| **명령** | 실제 실행한 명령어 (또는 “CI: workflow 이름”) |
| **결과** | pass / fail / skip — fail이면 로그·이슈 링크·요약 |
| **미실행** | “미실행 — 이유: …” (시간·환경·범위 밖 등) |

전부 skip이면 **완료**로 표기하지 말고 **부분완료** 또는 **차단**을 검토한다.

## 8. worklog 템플릿

새 파일 작성 시 아래를 복사해 파일명 규칙에 맞게 저장한다.

```markdown
# [한 줄 제목]

| 필드 | 값 |
|------|-----|
| **상태** | 초안 / 완료 / 부분완료 / 중단 |
| **완료일** | YYYY-MM-DD (해당 시) |
| **차단 사유** | (중단·초안 시) |

## 작업 목적

## 관련 tasks.md ID

- 

## 수정 파일 목록

- 

## 변경 내용 요약

- 

## migration 여부

- 

## 테스트 결과

- 

## 남은 위험

- 

## 다음 권장 작업

- 
```

*(섹션 제목은 “다음 권장 작업” 또는 “다음 작업 권장사항” 중 하나로 통일해도 됨.)*

## 9. `tasks.md`와의 관계 (**필수**)

- **코드·문서·스키마 관련 작업을 끝낼 때**: 관련 **`tasks.md` 감사 ID** 블록에 **작업 이력**(날짜·요약·본 worklog 경로)을 남기고, **`docs/worklogs/YYYY-MM-DD_phase-topic.md`** 1건을 생성한다.  
- **작업 완료 정의**: 변경 + `tasks.md` 반영 + worklog (상세: **`.cursor/rules/worklog-completion.mdc`**).  
- worklog는 **`tasks.md` ID를 참조**해 교차 검색 가능하게 한다. ID가 없으면 `## 문서 사용법`·`[OPS]` 등 맥락이 있는 위치에 한 줄 남긴다.

### 선택 (PR·체크리스트)

1. PR 템플릿에 `Worklog: docs/worklogs/YYYY-MM-DD_....md` 링크 항목.  
2. Phase 시작 체크리스트에 “관련 worklog 경로” 필드.
