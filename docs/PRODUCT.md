## 식식이OS 최상위 선언

> **식식이OS는 발주 시스템이 아니라,**
> **거래를 만들고 운영을 자동화하는 시스템이다.**

```
식당OS   → 사장님 대신 판단하고 실행하는 운영 엔진
공급자OS → 덜 틀리게 영업하고 운영하게 만드는 시스템
관리자OS → 플랫폼이 스스로 판단하고 진화하게 만드는 시스템
```

## 1. 서비스 정의

### [철학]

**식식이OS는 발주 시스템이 아니다.**
식당과 공급자의 거래를 자동으로 생성하고, 돈의 흐름까지 관리하는 **외식 공급망 운영 시스템**이다.

식식이OS는 단순 기능 제공 시스템이 아니라,
거래 → 돈 → 행동까지 자동으로 이어지는 운영 시스템이다.

#### 핵심 가치

| 기존 관점 | 식식이OS 관점 |
|----------|-------------|
| 발주를 쉽게 | 덜 틀리게 운영하게 |
| 데이터 제공 | 행동 제시 |
| 기능 제공 | 루틴 형성 |

데이터를 보여주는 것이 아니라
"지금 무엇을 해야 하는지"를 결정하게 만드는 것이 목적이다.

#### 설계 철학

```
입력 줄인다  →  데이터 쌓인다
데이터 쌓인다  →  판단 자동화
판단 자동화  →  돈 번다
```

#### 숨겨진 비밀 (핵심 가설)

시장의 착각: "식당 문제 = 매출 문제"
진짜 진실: "많은 식당 문제 = 운영 불확실성 문제"

- 사장님은 데이터가 아니라 **결론(행동지시)**을 원한다
- 발주보다 **돈의 흐름(원장/수금/외상/예치금)** 이 더 강한 락인을 만든다
- "얼마 더 팔게"보다 **"얼마 덜 새게"** 가 더 큰 가치다

운영이 안정되면 매출은 자연스럽게 따라온다.
반대로 운영이 불안정하면 매출이 있어도 돈은 남지 않는다.

---

### [실행 규칙]

식식이OS는 아래 3개 흐름을 연결하는 시스템이다.

```
1. 거래 생성 (RFQ → 주문)
2. 돈 흐름   (수금 / 지급 / 원장)
3. 행동 생성 (대시보드 / 자동화영업)
```

모든 기능은 반드시 위 3가지 중 하나에 속해야 한다.
속하지 않으면 구현하지 않는다.

## 2. 사용자

### [철학]

#### 식당 (구매자)
- 식자재를 발주하고 구매하는 주체
- 식당OS를 통해 발주요청 생성, 공급자 선택, 결제 관리
- 입력 최소화 / 추천 중심 UX

#### 공급자 (판매자)
- 식자재를 공급하는 주체
- 공급자는 단순 판매자가 아니라, ERP + 영업 + 거래 확장 기회를 동시에 사용하는 사용자다
- 공급자OS를 통해 발주요청 수신, 입찰, 주문 처리, 수금 관리
- **플랫폼 Storefront 고객의 소유권은 공급자에게 없다.** Storefront에서 식당이 결제·주문한 거래의 **고객·주문·결제 주체(ownership)는 플랫폼 운영사(디닷페이스)** 이다. 공급자(예: 해내음코리아 등 fulfillment 파트너)는 **납품·출고·배송 등 fulfillment** 및 **공급자 자체 CRM·원장** 축에서 역할을 가진다.

#### 플랫폼 관리자
- 전체 시스템을 운영·조정·실험하는 컨트롤 타워
- 플랫폼 관리자는 단순 관리자가 아니라, 시장 구조를 설계하고 통제하는 역할이다
- 관리자OS를 통해 거래 관제, 수치/문구 제어, 정산 관리

---

### [실행 규칙]

```
식당      → 거래 생성
공급자    → 거래 처리 및 매출 생성
플랫폼    → 돈 흐름 통제 및 정책 제어
```

모든 기능은 사용자 역할 기준으로 권한이 분리된다.

## 3. 핵심 흐름

### [철학]

#### 거래 흐름 (식당 → 공급자)

```
[1] 식당: 발주요청(RFQ) 생성
      ↓
[2] 기존 거래처 우선 공개
    → 일정 시간 후 확장 공개
      ↓
[3] 공급자: 입찰 / 조건 제안
      ↓
[4] 식당: 선택 / 협상 수락
      ↓
[5] 주문 확정
      ↓
[6] 납품 완료
      ↓
[7] 매출 / 매입 / 원장 자동 생성
      ↓
[8] 수금 / 지급 발생
      ↓
[9] 자금 반영 / 원장 반영
```

#### 돈 흐름 원칙

```
모든 데이터는 거래에서 생성된다
```

- 매출 — 납품 기준으로 자동 계산
- 매입 — 주문 기준으로 자동 생성
- 원장 — 거래 기준으로 자동 생성
- 정산 — 플랫폼이 관리 (직거래 차단 핵심 구조)

### [실행 규칙]

**거래 흐름 (실행 기준)**
```
RFQ 생성
→ 공급자 노출
→ 입찰
→ 선택
→ 주문 생성
→ 납품 완료
→ 매출/매입 생성
→ 수금/지급 발생
→ 원장 반영
→ 자금 반영
```

모든 데이터는 위 흐름에서만 생성된다. 외부 입력 금지.

**돈 흐름 강제 규칙**
```

직접 거래 금지.
플랫폼이 돈 흐름을 통제하지 못하면 시스템은 실패한다.
```

식당과 공급자 간 직접 결제는 허용하지 않는다.
모든 돈의 흐름은 플랫폼을 통해서만 이루어진다.

## 4. 핵심 데이터 원칙 (전 기능 공통)

### [철학]

모든 데이터는 "행동"을 만들기 위해 존재한다.

- **tenant_id 필수** — 모든 테이블, 모든 쿼리
- **계산값 DB 저장 금지** — 잔액, 마진율 등은 실시간 계산 또는 캐싱
- **과거 데이터 불변** — 주문·수금은 스냅샷 저장, 수정 금지
- **Soft Delete** — 물리 삭제 금지, deleted_at / deleted_by로 처리
- **Server Action 전용** — 클라이언트에서 직접 Supabase 쿼리 금지
- **N+1 쿼리 금지**
- **TODO 코드 금지**

#### 상태 기준 통일

상태 판단은 반드시 기준값(settings) 기반으로 계산된다.

- **연체금 기준** — 상태 판단은 미수금이 아닌 연체금(due_date 초과)으로 통일
- 미수금 = 정상 거래 포함 / 연체금 = 결제기한 초과 금액
- 공식: `연체금 = SUM(미수금 WHERE due_date < 오늘)`

#### 금액 계산 규칙

- DB 저장: INT (원 단위)
- 화면 표기: 1,000원
- 과세: 공급가 = 판매가 / (1 + vat_rate), 부가세 = 판매가 - 공급가
- 면세: 공급가 = 판매가, 부가세 = 0
- 부가세 계산 후 원 단위 반올림
- 마진율(%) = (판매가 - 매입가) / 판매가 × 100

모든 계산 기준은 settings 값에 의해 변경 가능해야 한다.

#### 가격 우선순위 (주문 시 고정)

1. 견적가
2. 거래처 기준 마지막 거래 가격
3. 상품 기본 판매가

---

### [실행 규칙]

모든 데이터는 아래 3가지로 구분된다.
```
1. 입력값  → DB 저장
2. 계산값  → DB 저장 금지 / 실시간 계산
3. 로그    → 변경 시 자동 기록
```

```
계산값 DB 저장 금지

```

**settings 연결**
```
모든 기준값은 settings에서 관리된다.
settings 변경은 즉시 시스템에 반영된다.
```

```
지급관리    — 돈 나감 (outbound)

설정        — 시스템 판단 기준 (코드 수정 없이 운영 통제)
```

#### 식당OS

```
오늘운영    — 행동 중심 대시보드 (파트너형)
발주관리    — 발주요청 생성 / 입찰 / 선택
돈관리      — 지급 / 미지급 / 예치금 / 자금 흐름 통합
거래처관리  — 매입처 선택 및 유지 판단
알림        — 행동 트리거 시스템 (단순 알림 아님)

```

#### 관리자OS

```
통합 대시보드   — 전체 현황
거래 관제       — 전체 거래 모니터링
거래처 관리     — 식당 + 공급자 + 일반
데이터 조회     — 식자재 / 메뉴 / 가격
```

**확장 정의 (디닷페이스 ERP)**: 관리자OS는 단순 “관제 패널”을 넘어, **디닷페이스(식식이OS 플랫폼 운영사)** 의 **플랫폼 ERP·정산 허브** 방향을 가진다. 여기에는 **플랫폼 주문(storefront / `commerce_orders`)**, **플랫폼 매출·미수(receivable)**, **공급 allocation·공급자 정산**, **플랫폼 수수료·PG/결제 운영** 등이 포함된다(구현 범위는 `tasks.md`의 **`[PLATFORM-ERP-001]`** 등으로 단계 관리).

## 6. 공급자OS 기능 상세

### 6-1. 대시보드

**한 줄 정의**
대시보드는 상태를 보여주는 것이 아니라 **"지금 무엇을 해야 하는지"를 정확히 알려주는 시스템이다.**

```
원장      = 돈 흐름
매출분석  = 성과 분석
대시보드  = 행동
```

**목적**: 오늘 돈을 벌고, 돈을 받고, 돈을 지키게 만든다

---

#### 우선순위 (레이아웃 순서 기준)

1. 지금 해야 할 행동
2. 돈 회수
3. 돈 벌 기회
4. 위험 관리
5. 성과 확인
6. 자금 의사결정

---

#### 전체 레이아웃

```
[오늘 행동 / 알림]              full width   ← 1순위
[수금 우선순위 TOP5]            full width   ← 2순위
[돈 요약 KPI]                  4 column     ← 3순위
[오늘 할 일 상세]               half width   ← 4순위
[거래처 매출 TOP5]  [상품 매출 TOP5]        ← 5순위
[오늘 자금 배치 제안]           full width   ← 6순위
```

---

#### 블록 1 — 오늘 행동 / 알림 (최상단 full width)

**목적**: 지금 당장 뭘 해야 하는지 명확히 제시

**구성**
- 미수금 총액 알림
- 긴급 액션 메시지 (조건 기반 자동 생성)

**예시**
```
"미수금 155만원 있습니다. 오늘 수금하세요."
"수금 지연 거래처 3곳 있습니다."
```

**클릭**: → /ledger

**Empty State**: "미수금이 없습니다 👍"

---

#### 블록 2 — 수금 우선순위 TOP5 (full width)

**목적**: 어디서 먼저 돈 받아야 하는지 + 오늘 수금 대상 강조

**컬럼**
```
거래처명 | 미수금 | 지연일 | 우선순위 점수
```

**표시 방식**
- TOP 1~3 → "오늘 수금 대상" 강조 표시
- TOP 4~5 → 일반 표시

**정렬**: 우선순위 점수 높은 순

**행동 버튼**
- [수금하기] → 수금등록
- [원장] → /customers/[id]/ledger

**연체 판단 기준**
```
약속 없음: due_date + 3일 초과 시 연체
약속 있음: promised_date + 1일 초과 시 연체
```

**약속 기반 로직** (연체보다 약속이 우선)
```

약속일 -1일         → "내일 수금 예정" 표시
약속일 당일         → "오늘 수금 예정" 표시
약속일 +1일 초과    → 연체로 전환
```

**Empty State**: "수금 대상 거래처가 없습니다 👍"

### 6-2. 발주요청 (RFQ)

**한 줄 정의**
발주요청은 단순 입찰 기능이 아니라
"노출 → 판단 → 입찰 → 협상 → 계약 → 결제 → 납품 → 정산 → ERP"까지 이어지는
공급자OS의 핵심 수익 엔진이다.

---

#### 상태 흐름 (완전 정의)

```
open
→ bidding
→ counter_offered
→ selected
→ contract_pending
→ paid
→ address_revealed
→ delivery_in_progress
→ delivered_by_supplier
→ confirmed_by_restaurant
→ settlement_pending
→ settled
→ completed

예외:
expired / cancelled / disputed
```

---

#### 발주요청 노출 로직

**목적**: 무분별한 공개 방지 / 기존 거래 중심 / 단계적 확장

```
1단계 (우선 공개)  → 생성 즉시
  기존 거래처 공급자에게만 노출

2단계 (확장 공개)  → 생성 후 30분 경과
  동일 지역 공급자에게 확장 공개

3단계 (전체 공개)  → 생성 후 2시간 경과
  전체 공급자 공개
```

**노출 우선 조건**: 동일 지역 우선 / 거래 이력 우선 / 활동 공급자 우선

**MVP**: 30분 / 2시간 고정값 사용
**이후**: 관리자 settings로 변경 가능

---

#### 발주요청 목록 화면 UX

**화면 유형**: 카드 + 리스트 혼합형

**컬럼**
```
제품명 | 수량 | 희망 가격 | 지역(부분) | 마감 시간 | 입찰 수 | 상태
```

**정렬**: 마감 임박순 (기본) / 최신순

**필터**: 지역 / 제품 / 상태 / 참여 여부 (미참여 / 참여)

**강조 표시**
- 신규 요청 → NEW 표시
- 마감 임박 → 빨간색
- 인기 요청 → 입찰 많음 표시

---

#### RFQ 상세 UX

```
[요청 정보]
[입찰 리스트 (익명)]
[내 입찰 상태]
[입찰하기 버튼]
```

**입찰 리스트 제한 공개**
- 가격 범위만 표시 (예: 10,000~11,000원)
- 입찰 수 표시
- 공급자 식별 정보 ❌

---

#### 입찰 (공급자 액션)

**입력 항목**

| 구분 | 항목 |
|------|------|
| 필수 | 가격 / 납품 가능일 |
| 조건부 | 최소 수량 / 공급 가능 수량 |
| 선택 | 메모 / 대체 상품 |

**상태 변화**
```
입찰 전        → open
입찰 후        → bidding
조건 제안      → counter_offered
식당 수락      → selected
```

**협상 흐름**
```
공급자 제안 → 식당 수정 요청 → 재제안 → 확정
```

**입찰 이후**
- 수정 가능 (마감 전)
- 철회 가능 (마감 전)

---

#### 계약 생성 흐름 (MVP)

**계약 정의**: 입찰 확정 조건을 기록하는 "전자 합의 데이터"

**계약서 구성** (자동 생성)
```
제품 / 수량 / 단가 / 총 금액 / 납기 / 정산 조건 / 취소·분쟁 기준
```

**서명 방식**: 체크박스 + [동의 및 진행] 버튼 (전자서명 아님)
- 공급자: [동의 및 진행]
- 식당: [동의 및 진행]

**상태 흐름**
```
selected → contract_pending → (양측 동의) → paid
```

**향후 확장**: 전자서명 (카카오 / PASS) / PDF 계약서

---

#### 낙찰 / 미낙찰 처리

**낙찰 시**
- 알림 발생
- 계약 생성 → contract_pending 진입
- "선정/계약" 탭으로 이동

**미낙찰 시**
- 상태: 탈락
- 알림 발생
- 기록 유지 (분석용 데이터로 축적)

---

#### 알림 시스템 (상태 변화 기반)

모든 알림은 "상태 변화 기준"으로 발송한다.

| 알림 | 발송 기준 |
|------|----------|
| 신규 발주요청 | 내가 노출 대상이 된 시점 (1단계/2단계/3단계 각각) |
| 마감 임박 | 마감 1시간 전 / 마감 10분 전 추가 1회 |
| 식당이 내 제안 확인 | 식당이 내 입찰 카드를 클릭/확장한 시점 (supplier_bid_viewed 이벤트) |
| 식당이 조건 수락 | counter_offered → selected 상태 전환 시 |
| 낙찰 | selected 상태 진입 시 |
| 탈락 | 다른 공급자가 selected 됐을 때 |
| 계약 요청 | contract_pending 상태 진입 시 |
| 결제 완료 (주소 공개) | paid 상태 진입 시 |
| 납품 요청 | address_revealed 상태 진입 시 |
| 납품 완료 | delivered_by_supplier 상태 진입 시 (식당에게 발송) |
| 정산 완료 | settled 상태 진입 시 |

**"식당이 내 제안 확인" 이벤트 정의**
```
event: supplier_bid_viewed
조건:
  - rfq_id 일치
  - supplier_id 일치
  - 식당이 해당 bid_card expand/click

처리:
  - 페이지 단순 진입 → 이벤트 기록만 (알림 없음)
  - 제안 카드 클릭/확장 → 해당 supplier에게 알림 발송
```

---

#### 공급자 판단 지원 데이터

**예상 마진 색상 표시** (숫자 직접 노출 ❌)

| 색상 | 기준 |
|------|------|
| 초록 (양호) | 마진율 15% 이상 |
| 노랑 (보통) | 5% ~ 15% |
| 빨강 (주의) | 5% 이하 |

**계산 기준**: 마진율 = (판매가 - 예상 원가) / 판매가

**기타 판단 지원**
- 거리: 가까움 / 보통 / 멀음 (텍스트만)
- 거래 가능성: 색상으로만 표시
- 점수 직접 노출 ❌

---

#### 핵심 UX 원칙

1. 공급자는 "입력"이 아니라 "판단"한다
2. 식당은 요청 생성, 공급자는 참여
3. 전체 주소는 결제 후 공개 (paid 상태)
4. 직거래 방지 구조 유지
5. 협상 가능 구조 유지
6. 거래는 반드시 플랫폼 결제로 종료
7. 모든 거래는 ERP 자동 반영
8. 데이터는 삭제하지 않고 축적 (미낙찰 포함)

### 6-3. 거래처관리 (CRM)

**한 줄 정의**
거래처관리는 단순 정보 조회가 아니라,
**누구에게 언제 연락하고, 무엇을 제안하고, 어떻게 매출을 올릴지 결정하는 행동형 CRM 시스템**이다.

---

#### 메뉴 구조

```
거래처관리
ㄴ 거래처목록
ㄴ 거래처등록
ㄴ 대량등록
```

---

#### 거래처목록

**목적**: 거래처를 조회하는 화면이 아니라 "영업 타겟을 고르는 화면"

**상단 요약 KPI**
```
전체 거래처 수 | 미수 거래처 수 | 총 미수금 | 위험 거래처 수 | 신규 거래처 수
```

**빠른 필터 버튼**
```
전체 / 오늘 연락 필요 / 미수금 있음 / 주문주기 초과 / 위험 거래처
신규 거래처 / 주력관리 / OS 미구독 / 목표매출 미달
```

**고급 필터**

| 항목 | 옵션 |
|------|------|
| 고객유형 | 사업자 / 개인 / 예비 |
| 거래상태 | 거래중 / 휴면 / 중단 |
| 고객상태 | 신규 / 정상 / 주의 / 위험 |
| 관리등급 | 방치 / 정기관리 / 주력관리 |
| 유입경로 | (acquisition_channels 기반) |
| 식식이회원여부 | 비회원 / 일반 / 사업자 / 구독 / 협력업체 |
| 식식이OS 구독여부 | 구독 / 미구독 |
| 역할 | 매출처 / 매입처 / 둘 다 |
| 미수금 | 있음 / 없음 / 금액 범위 |
| 최근 주문 | 7일 / 30일 / 90일 이상 없음 |

**검색**: 거래처명 / 대표자명 / 연락처 / 사업자등록번호 / 주소 일부

**정렬 옵션**
- 미수금 높은 순
- 최근 주문 오래된 순
- 이번달 매출 높은 순
- 평균월매출 높은 순
- 목표매출 미달 큰 순
- 매출 상승률 높은 순 / 하락률 높은 순
- 전체 매출 순위 높은 순

**목록 컬럼**
```
거래처명 | 연락처 | 고객유형 | 거래상태 | 고객상태 | 관리등급
유입경로 | 식식이회원 | OS상태 | 미수금
이번달매출 | 평균월매출 | 목표월매출 | 목표대비차이
최근주문일 | 주문주기 | 다음예상주문일
전체매출순위 | 전월대비순위변동 | 매출상승률 | 다음행동
```

**URL**: 목록에서 거래처명 클릭 → `/customers/[id]`

---

#### 주문주기 계산 기준

**계산 조건**: 최근 90일 내 주문 3건 이상
**계산 방식**: 최근 주문 간격 평균 (settings: order_cycle_calculation_count = 3)
**조건 미달 시**: "주기 없음" 표시 / 주문주기 기반 알림 생성 안 함

---

#### 다음 예상 주문일

```
다음 예상 주문일 = 최근 주문일 + 주문주기
```

**계산 불가 조건**: 주문 2건 이하 / 최근 90일 데이터 부족
**불가 시 표시**: "-" 또는 "예측 불가"
- 다음 예상 주문일 기반 알림 생성 금지
- 고객상태 계산에서도 주문주기 로직 제외

**현재 날짜 기준 비교 표시**
```
"3일 후" (예상일 남음)
"5일 지남" (지연)
```

---

#### 매출 지표

**이번달 매출**: 해당 월 confirmed / delivered 주문 합계 (cancelled 제외)

**평균월매출**: 최근 3개월 매출 평균 / 데이터 부족 시 "데이터 부족" 표시

**목표월매출**: customers.target_monthly_revenue → 없으면 settings.default_target_monthly_revenue → 없으면 "목표 없음"

**표시 예시**
```
평균월매출 100,000원
목표월매출 200,000원
목표 대비 -100,000원
```

**매출 순위 / 상승률**
- 전체 매출 순위: 이번달 매출 기준 / 표시 예: `#3 / 59`
- 순위 변동: 전월 대비 / 표시 예: `▲2` `▼3` `-`
- 매출 상승률: `(이번달 매출 - 지난달 매출) / 지난달 매출`
  - 상승: 초록 / 하락: 빨강 / 데이터 부족: 표시 안 함

7. 엑셀 다운로드는 저장용이 아니라 타겟 추출용이다
8. 모든 전화/문자/방문은 contact_logs로 남긴다
9. 거래상태와 고객상태는 절대 분리한다
10. CRM의 목표는 고객 관리가 아니라 매출 행동을 만드는 것이다

### 6-4. 주문관리

**한 줄 정의**
주문은 거래를 기록하고, 수금은 돈을 움직이며, 시스템은 잔액을 계산한다.

---

#### 메뉴 구조

```
주문관리
ㄴ 주문목록  (메인)
ㄴ 주문등록
ㄴ 주문현황
```

---

#### 핵심 테이블 분리

```
orders       — 거래 문서 (헤더)
order_lines  — 상품 상세 (스냅샷 저장)
payments     — 수금 (독립 테이블)
order_logs   — 수정이력
notices      — 안내/메모
```

주문 = 문서 / 수금 = 돈 / 안내 = 메시지 → 절대 하나로 섞지 않는다

---

#### 주문번호 체계

```
ORD-YYYYMMDD-NNNN
```
- 4자리 시퀀스 / tenant 기준 증가
- 중복 불가 / 수정 불가

---

#### 상태 이중 구조 (분리 필수)

**주문상태** (운영 흐름 — 일 진행 상황)
```
접수 → 확인 → 출고준비 → 출고완료 → 납품완료 → 취소
```

**거래상태** (원장 기준 — 돈 계산 포함 여부)
```
draft → confirmed → cancelled
```

- draft → 잔액 계산 제외
- confirmed → 잔액 계산 포함
- cancelled → 잔액 계산 제외
- 반품(refund) = 거래 유형 / 취소(cancelled) = 상태 → 구분
- 두 상태는 절대 섞지 않는다

---

#### 결제상태 (자동 계산 / DB 저장 금지)

```
결제완료: 수금 합계 = 총주문금액
미수:     수금 합계 = 0
부분수금: 0 < 수금 합계 < 총주문금액
```

계산 기준: `orders.total_amount vs payments 합계 비교`

---

#### 주문목록

**목적**: 등록된 주문 전체를 조회하고 관리하는 화면

**컬럼**
```
주문번호 | 주문일시 | 거래처명 | 상품수 | 총주문금액 | 주문상태 | 결제상태 | 담당자
```

**기능**
- 검색: 주문번호 / 거래처명
- 필터: 주문상태 / 결제상태 / 거래처 / 기간
- 정렬: 최신순 / 주문금액순
- 주문 클릭 → 주문상세 이동
- 엑셀 다운로드: 전체 / 현재 필터 / 컬럼 선택
- 주문상태 변경
- 기본 조회: 해당 월 1일 ~ 오늘

**Empty State**: "이번 달 주문이 없습니다"

#### 주문등록

**한 줄 정의**: 속도가 먼저다. 5초 내 입력 가능해야 한다.

**입력 흐름 (표준)**
```
거래처 선택
→ 최근 주문 상품 자동 노출
→ Enter
→ 수량 입력
→ Enter
→ 최근 가격 자동 입력
→ 완료
```

**거래처 선택 시 자동 세팅**
```
최근 주문 상품 / 최근 거래 가격 / 납품 주소 / 결제조건
```

**상품 입력 자동화**
- 최근 주문 상품 TOP 우선 노출
- 자주 쓰는 상품 우선 노출
- Enter 시 다음 row 자동 생성

**총합 실시간 고정 표시** (화면 하단 고정)
```
총 공급가 | 총 부가세 | 총 주문금액
```

**입력 구조**
```
[기본정보]  주문일자 / 거래처 / 담당자 / 연락처 / 납품희망일 / 주문메모
[주문상품]  상품선택 / 주문수량 / 판매단가 / 공급가액(자동) / 세액(자동) / 합계(자동)
[결제정보]  결제조건 / 결제상태 / 수금예정일
[납품정보]  납품주소 / 납품방법 / 배송메모
[기타]      내부메모
```

**필수값**: 거래처 / 주문일자 / 주문상품 1개 이상 / 주문수량 / 판매단가
나머지는 자동 처리

**세금 계산**
```
과세: 공급가 = 판매가 / 1.1  /  부가세 = 판매가 - 공급가
면세: 공급가 = 판매가        /  부가세 = 0
```

**판매가 자동 입력 우선순위**
```
1. 견적가
2. 해당 거래처 최근 거래 가격 (order_lines 기준 / product 테이블 참조 ❌)
3. 상품 기본가
```
자동 입력은 편의 기능 / 저장 전 사용자 최종 확인 필수

**개발 유의**
- 여러 상품을 한 번에 담을 수 있어야 한다
- 상품별 단가가 다를 수 있으므로 주문상품 단위로 가격 저장
- 재고 차감 시점은 settings.inventory_deduction_timing으로 관리
  - 옵션: order_confirmed / shipment_completed
  - MVP 기본값: order_confirmed

#### 주문 스냅샷 (order_lines 필수 저장)

```
product_id / product_code / product_name / unit_price / cost_price / fulfillment_type
```

- 이후 상품 정보가 변경되어도 과거 주문은 절대 변하지 않는다
- 주문은 상품 테이블을 참조하지 않는다 → "그 시점 데이터 복사"

**주문목록 vs 주문현황**
```
주문목록  = 전체 관리용 (조회/수정 중심)
주문현황  = 운영 처리용 (상태 변경 중심)
```

6. 주문은 스냅샷으로 저장한다
7. 모든 수정은 로그로 남긴다
8. 입력 속도가 시스템 사용률을 결정한다

### 6-5. 견적관리

**한 줄 정의**
견적은 보내고 끝이 아니라, 기억되고 전환되어야 한다.

**목적**: 매출이 될 가능성을 관리하는 시스템

---

#### 메뉴 구조

```
견적관리 (독립 메뉴)
ㄴ 견적목록  (메인)
ㄴ 견적등록
ㄴ 견적현황
```

이유: 견적 → 주문 전환이 핵심 / 영업·매출 전 단계 / 주문관리와 역할이 다름

---

#### 견적 상태

```
draft → sent → partially_converted → converted → expired
```

---

#### 견적목록

**목적**: 견적을 조회하는 화면이 아니라 "전환할 견적을 찾는 화면"

**컬럼**
```
견적번호 | 견적일자 | 거래처명 | 상품수 | 총금액 | 견적상태 | 전환율 | 유효기간 | 담당자
```

**전환율 정의**
```
전환율 = converted_quantity / total_quantity
```

**빠른 필터**
```
전환 필요 / 유효기간 임박 / 부분 전환 / 미전환 견적
```

**고급 필터**
- 견적상태: draft / sent / partially_converted / converted / expired
- 유효기간: 만료 / 임박 / 정상
- 거래처 / 기간 / 담당자

**기능**
- 검색: 견적번호 / 거래처명
- 정렬: 최신순 / 금액순 / 만료임박순
- 엑셀 다운로드
- 견적 클릭 → 상세 이동

**Empty State**
```
"등록된 견적이 없습니다"
"견적을 생성하고 매출 기회를 만들어보세요"
```

---

#### 견적등록

**목적**: 빠르게 견적 생성 → 바로 전송 → 주문으로 전환

**입력 구조**
```
[기본정보]  견적일자 / 거래처 / 유효기간(자동) / 견적 메모
[상품입력]  상품선택 / 수량 / 단가 / 합계(자동)
```

**거래처 선택 UX**
- 기존 거래처 검색
- 없으면 → 즉시 prospect 생성 → 견적 연결

**가격 자동 입력 우선순위**
```
1. 확정된 견적 가격 (is_final_price = true)
2. 최근 거래 가격
3. 상품 기본가
```

**필수값**: 거래처 / 상품 1개 이상 / 수량 / 단가

**유효기간**: settings.quote_expiry_days 기준 자동 입력

---

#### 견적 상세 (`/quotes/[id]`)

**구성**
```
[기본 정보]     견적번호 / 거래처 / 견적일자 / 유효기간 / 상태
[상품 리스트]   상품명 / 수량 / 단가 / 합계 / 전환수량 / 잔여수량 / 상태
[전환 현황]     총수량 / 전환수량 / 남은수량 / 전환율(%)
[전송 이력]     전송일시 / 방식(카카오/링크/다운로드) / 담당자
[액션 버튼]     견적 전송 / PDF 다운로드 / 주문으로 전환 / 수정 / 만료 처리
```

---

#### 견적 전달 기능

**목적**: 견적은 전달되어야 의미가 있다

**전달 방식 (MVP)**
```
PDF 다운로드
JPG 다운로드
카카오톡 공유 (링크)
문자 공유 (링크)
이메일 (UI 제공 / 추후 구현)
```

**견적서 구성 (필수)**
```
로고 / 상호 / 연락처
거래처명
견적일 / 유효기간
상품 리스트 (상품명 / 수량 / 단가 / 합계)
총 금액
메모
도장 이미지 (settings)
```

**견적서 디자인 원칙**
- 가독성 중심
- 핵심 정보 강조
- 모바일에서도 잘 보임

**전송 UX**: [견적 전송] 버튼 클릭 → PDF 생성 → 공유 방식 선택

**전송 이력 기록**: 전송일시 / 방식 / 담당자

---

#### 견적 → 주문 전환 UX

**흐름**
```
[주문으로 전환] 클릭
→ 상품 선택 (체크박스)
→ 수량 입력
→ 확인
→ 주문등록 화면 이동 (선택 상품 자동 입력)
```

**전환 후 처리**
```
converted_quantity 증가
quote_items 상태 변경
견적 상태 자동 변경
  일부 전환 → partially_converted
  전체 전환 → converted
```

**quote_items 구조**
```
quantity / converted_quantity / status (pending / partially_converted / converted)
```

#### 견적 가격 기억 시스템

**원칙**: 확정된 견적 가격 = 이후 주문 기본 가격

**견적 → 가격 확정 조건**
- 주문 전환 발생 시
- 수동 확정 처리 (관리자 선택)

**저장 구조**
```
quote_items
- product_id / unit_price / is_final_price (boolean)

customer_product_prices
- customer_id / product_id / last_price / source (quote / order) / updated_at
```

**주문등록 시 자동 적용**
```
거래처 선택 → 상품 선택 → 해당 거래처 최근 가격 자동 입력
```

---

#### 견적 수정 정책

- 기존 견적 수정 가능 / 수정 시 이력 저장
- quote_logs: 수정 전 / 수정 후 / 수정자 / 시간
- 가격 변경 시: 기존 가격 유지 / 새 가격은 "새 견적 기준" 적용

---

#### 유효기간 관리

**기준**: settings.quote_expiry_days

**상태 자동 변경**: 기간 초과 → expired

**UX 표시**
```
"3일 남음"
"오늘 만료"
"만료됨"
```

---

#### 견적현황

**목적**: 견적을 상태 기준으로 빠르게 관리하는 영업 행동 트리거 화면

**탭 구조 및 기준**

| 탭 | 기준 |
|----|------|
| 전체 | 전체 견적 |
| 전환 필요 | sent 상태 + converted_quantity = 0 |
| 유효기간 임박 | 만료까지 3일 이하 |
| 부분 전환 | partially_converted 상태 |
| 만료 | expired 상태 |

**컬럼**
```
견적번호 | 거래처명 | 견적일 | 유효기간 | 총금액 | 전환율 | 상태 | 담당자
```

**기능**
- 상태별 빠른 조회
- 견적 클릭 → 상세 이동
- 바로 연락 (전화 / 문자)
- 바로 전환

**탭별 행동 연결**
```
전환 필요     → 즉시 연락
유효기간 임박 → 리마인드
부분 전환     → 추가 제안
만료          → 재견적
```

---

#### 예비거래처 연결

- 거래 전 업체 → customer_type = prospect로 즉시 생성 → 견적 연결
- 거래 발생 시 customer_type 변경 가능 / 변경 이력 저장

---

#### 핵심 철학

1. 견적은 거래가 아니라 "기회"다
2. 견적은 가격이 아니라 "고객 의사 데이터"다
3. 견적의 목적은 주문 전환이다
4. 전환되지 않은 견적은 분석 대상이다
5. 부분 전환은 정상 흐름이다
6. 견적은 반드시 전달되어야 한다
7. 견적은 가격 데이터로 축적된다
8. 견적현황은 영업 행동 트리거다

### 6-6. 상품관리 (Product Management + Product Intelligence 통합)

**한 줄 정의**
상품은 파는 것이 아니라, 남기는 것이다.

**목적**: 마진이 무너지는 상품을 즉시 발견하고 수익을 통제하는 시스템

---

#### 메뉴 구조

```
상품관리
ㄴ 상품목록  (메인)
ㄴ 상품등록
```

---

#### 상품목록

**목적**: 상품을 한눈에 보고 마진 문제를 즉시 발견하는 화면

**컬럼**
```
카테고리 | 제품코드 | 제품명 | 단위 | 현재 매입단가 | 판매가 | 현재 마진율 | 평균 마진율 | 사용처 수 | 평균단가 | 거래상태
```

- 현재 매입단가: 최근 적용 기준 (단일값 표시 / 시간 기반 변동값임을 명시)
- 제품코드: 수정 불가 (자동생성 / 한번 사용한 코드 재생성 금지)
- 수정이력: product_logs (최근 5개 UI 노출 / user_id + user_type + timestamp)

**마진율 이중 표시**
```
현재 마진율: 현재 판매가 기준
평균 마진율: 거래 평균 기준 (거래처별 판매가 기반)
```
- 경고 기준: 평균 마진율 기준 (보조: 현재 마진율 참고 표시)
- 마진율 < 기준값 → 빨간색 경고 표시

**사용처 수**
- 표시: `5개 (최근 거래 3)`
- 이유: 단순 숫자만 보면 "죽은 거래처" 포함됨
- 숫자 클릭 → 모달 팝업: `정무식당 (5,000원)`

**평균단가**
- 거래처별 판매가 기반 계산
- 실시간 계산 ❌ / 집계 테이블 또는 캐싱 ⭕

**검색**: 제품명 / 제품코드 / 바코드

**필터**: 카테고리 / 매입처 / 과세·면세 / 가격 범위 / 사용처 수 / 거래상태

**정렬**: 등록순 / 가격순 / 마진율순

**거래상태**: 활성 / 중단 / 단종
- 중단: 일시적 거래 중단
- 단종: 영구 판매 종료 (물리 삭제 금지 / 상태 변경으로 처리)

**기능**: 상품 클릭 → 상세 이동 / 거래상태 변경 / 엑셀 다운로드

---

#### 상품 상세 (`/products/[id]`)

**구성**
```
[기본 정보]
  제품명 / 카테고리 / 코드 / 단위

[가격 정보]
  현재 매입가 / 매입가 이력 / 기본 판매가 / 거래처별 가격

[마진 분석]
  현재 마진율 / 평균 마진율 / 경고 여부

[거래 통계]
  사용처 수 / 총 판매량 / 평균 판매가 / 최근 거래일

[이력]
  가격 변경 로그 / 수정 로그
```

---

#### 상품등록

**목적**: 신규 상품을 등록하는 화면

**입력 구조**
```
[기본정보]      제품명 / 카테고리 / 제품코드(자동) / 바코드
[규격/단위]     규격 / 단위 / 박스입수
[가격]          과세기준 / 매입단가 / 판매가 / 거래처별 단가
[거래/공급정보] 매입처 / 최소주문수량
[재고]          초기재고 / 안전재고
[운영설정]      보관조건 / 유통기한 관리 여부 / 거래상태
[기타]          메모
```

**필수값**: 제품명 / 매입단가 / 과세기준

**선택 입력 (입력 시 상품 인텔리전스 기능 활성화)**
```
원재료명 및 함량
  - 상품 구성 요소 분석용
  - 상품 간 연결 및 추천에 사용됨
  - 예) 참기름 → 참깨 100% / 양념장 → 고추장 40% / 설탕 10% / 마늘 5%

품목보고번호
  - 상품 식별용 고유 값
  - 추후 상품 매칭 및 데이터 정합성에 사용
```

---

#### 마진율 자동 계산 (핵심)

**원칙**: 마진율은 사용자가 입력하는 값이 아니다. 판매가 또는 마진 입력 시 자동 계산되는 값이다.

**계산 공식**
```
마진율(%) = (판매가 - 매입가) / 판매가 × 100
마진금액  = 판매가 - 매입가
```

**입력 모드 2가지 (토글)**
```
① 판매가 입력 모드
   사용자: 판매가 입력
   시스템: 마진율 + 마진금액 자동 계산

② 마진 입력 모드
   사용자: 마진율 입력
   시스템: 판매가 + 마진금액 자동 계산
```

**실시간 반영**: 입력 즉시 반영
```
매입가: 800원
판매가: 1,000원
마진율: 20%
마진금액: 200원
```

**마진 색상 표시**
```
초록: 정상 (기준 이상)
노랑: 주의
빨강: 위험 (기준 이하)
```
기준: 상품별 min_margin_rate 우선 / 없으면 settings.margin_warning_threshold 사용

**입력 제한**
- 판매가 < 매입가 입력 시 → 경고 표시
- 저장은 가능 (관리자 판단 영역)

**가격 추천**: 상품 선택 시 최근 거래 가격 자동 추천 → 선택 가능

---

#### 마진 경고 시스템

**기준 구조 (2단계)**
```
전역 기준: settings.margin_warning_threshold (%)  → 전체 상품 기본 적용
상품별 기준: products.min_margin_rate (nullable)  → 개별 예외 적용
```

**적용 로직**
```
상품별 기준 있음 → 상품별 기준 사용
상품별 기준 없음 → 전역 기준 사용
```

```
product_costs
```

8. 제품코드는 자동생성 / 수정 불가 / 재사용 금지

#### 상품 인텔리전스 (Product Intelligence 확장)

**정의**: 상품관리 위에 추가되는 확장 기능. 기존 구조를 대체하지 않는다.

**상품 상세 탭 구조 (확장)**
```
[기본정보] [가격/마진] [연관상품] [사용패턴] [로그]
```
별도 메뉴 ❌ / 상품 상세 내부에서 확인 ⭕

---

**[연관상품] 탭**

구성:
```
자동 추천 영역 (조건 충족 시 활성화)
수동 등록 영역 (항상 사용 가능)
```

수동 등록 (MVP 핵심):
```
상품 A → 연관 상품 직접 추가
예) 참기름 → 김 / 들기름 / 고추장
```

자동 추천 활성화 조건 (3개 중 2개 이상 충족 시):
```
1. 해당 상품 거래 횟수 ≥ 20건
2. 함께 구매된 상품 데이터 ≥ 30건
3. 서로 다른 거래처 수 ≥ 5곳
```

분석 방식: order_lines 기반 Market Basket Analysis
```
같이 주문된 상품 조합 분석
→ "이 상품을 사용하는 거래처는 이 상품도 함께 구매함"
```

**[사용패턴] 탭**

표시 항목:
```
주요 사용 업종
자주 함께 사용되는 상품
주요 거래처
```

데이터 기준: order_lines 스냅샷 / product 테이블 참조 금지

**데이터 전략 (수동 + 자동 공존)**

```
초기       → 수동 연관상품 기반 운영
데이터 축적 → 조건 충족 시 자동 추천 자동 활성화
운영 중    → 수동 + 자동 동시 표시
```

사용자 개입 없이 자동 전환된다.

**자동화영업 연결**

```
거래처 메뉴 + 상품 사용 데이터
→ 필요 상품 추론
→ 영업 스크립트 자동 생성
```

예시:
```
제육볶음 업종 → 돼지고기 / 고추장 / 참기름 필요

자동 스크립트:
"사장님 제육볶음 하시면 참기름 많이 쓰시는데
지금 쓰시는 제품보다 단가 좋은 제품 있습니다"
```

**금지 사항**
```
자동 발주 ❌
자동 추천까지만 ⭕
```

상품관리의 목적은 마진을 통제하는 것이고,
상품 인텔리전스의 목적은 무엇을 팔아야 하는지를 알려주는 것이다.
두 기능은 분리된 것이 아니라 하나의 시스템으로 동작한다.

**추가 원칙**
1. 상품은 단독이 아니라 관계다
2. 같이 팔리는 상품이 매출을 만든다
3. 초기에는 사람이 연결하고, 이후 데이터가 학습한다
4. 자동화는 추천까지만 한다
5. 상품 데이터는 영업과 반드시 연결된다

### 6-7. 매입관리

**한 줄 정의**
매입은 입력하는 게 아니라, 돈이 어디로 빠져나가는지 보여주는 시스템이다.

---

#### 메뉴 구조

```
매입관리
ㄴ 매입내역  (메인)
ㄴ 매입등록
```

매입처 관리: 거래처관리에서 `is_supplier = true` 필터로 처리
이유: 같은 업체가 매출처 + 매입처 동시 가능 → 테이블 분리 시 반드시 꼬임

---

#### 핵심 구조 (위탁 + 재고 혼합)

```
fulfillment_type
- consignment (위탁): 주문 발생 → 매입 자동 생성 / 재고 없음
- stock (재고):       재고 있음 → 재고 차감 / 재고 없음 → 자동 매입 생성
```

**자동 매입 로직**
```
if stock_quantity > 0:
  재고 차감
else:
  매입 자동 생성 (supplier_id = product.default_supplier_id)
```

**재고 구조 (간소화)**
```
products.stock_quantity
```
- 복잡한 재고 시스템 ❌ / 단순 수량 기반 ⭕
- ERP 확장 대비 구조만 확보

---

#### 상품 ↔ 매입처 매핑 (자동화 핵심)

```
products.default_supplier_id (필수)
```

- 상품등록 시 거래처 DB(customers)에서 검색 선택
- 텍스트 직접 입력 금지
- 이게 없으면 자동 매입 생성 불가능

---

#### 전체 흐름

```
주문 발생
→ 재고 확인
→ 재고 있으면 차감
→ 없으면 자동 매입 생성 (product.default_supplier_id 기준)
→ 매입 → 원장 자동 반영
```

---

#### 매입내역

**목적**: 발생한 매입을 조회하고 관리하는 화면

**컬럼**
```
매입일자 | 매입처명 | 상품수 | 총매입금액 | 총수량 | 평균단가 | 입고상태 | 매입유형 | 담당자
```

매입유형: 자동(consignment) / 수동(stock)
입고상태: 입고완료 / 부분입고 / 입고대기

**기간별 집계**
```
월별 / 기간별 매입 합계
예) 2026-05 매입 총 12,500,000원
```

**기능**
- 검색: 매입처명 / 상품명
- 필터: 기간 / 매입처 / 입고상태 / 매입유형
- 정렬: 최신순 / 금액순
- 매입 클릭 → 상세 이동
- 출력: 엑셀 / PDF / JPG

**매입처 기준 조회**
```
특정 매입처 선택 → 기간 설정 → 매입 합계 조회
출력: 엑셀 / PDF / JPG
```

---

#### 매입등록

**목적**: 수동 매입 내역을 등록하는 화면

**입력 구조**
```
[기본정보]  매입일자 / 매입처(검색선택) / 담당자 / 매입메모
[매입상품]  상품선택 / 매입수량 / 매입단가(최근 매입가 자동 추천) / 공급가액(자동) / 세액(자동) / 합계(자동)
[입고정보]  입고일자 / 입고상태
[결제정보]  결제조건 / 결제상태 / 지급예정일
[기타]      내부메모
```

**필수값**: 매입일자 / 매입처 / 상품 1개 이상 / 매입수량 / 매입단가

**최근 매입단가 자동 추천**
```
상품 선택 → 최근 매입가 자동 표시 → 선택 가능
```

---

#### 매입 원장

**정의**: 매입 흐름 + 지급 흐름을 추적하는 시스템

**구성**
```
날짜 | 매입번호 | 매입금액 | 지급금액 | 잔액 | 메모
```

**기능**
- 매입처별 조회
- 기간별 조회
- 잔액 계산 (DB 저장 금지 → 계산)
- 출력: 엑셀 / PDF / JPG

이유: 매입 = 외상거래 발생 → 지급 전 잔액 추적 필수

---

#### 매입처별 분석

```
매입처별 매입 금액
매입처별 비중 (%)
```

정렬: 매입금액 높은 순 / 비중 높은 순
목적: 어디에 돈 쓰는지 구조 파악 → 원가 협상 판단 기준

---

#### 핵심 원칙

1. 매입은 "원가 기록"이 아니라 "지출 흐름"이다
2. 매입처는 거래처와 분리하지 않는다 (customers 통합)
3. 상품은 반드시 매입처와 연결되어야 한다 (default_supplier_id)
4. 재고는 단순하게 시작하고 확장한다
5. 재고 없으면 자동 매입 생성
6. 매입은 원장에 반드시 반영된다
7. 모든 매입 데이터는 출력 가능해야 한다

---

### 6-8. 수금관리

**한 줄 정의**
수금은 입력이 아니라, 돈의 이동을 추적하는 것이다.

---

#### 메뉴 구조

```
수금관리
ㄴ 수금목록  (메인)
ㄴ 수금등록
```

---

#### payments 테이블

공통 데이터 모델(9번 시스템 구조)을 따른다.

```
수금 조회 기준: direction = 'inbound' / type = 'order'
status: confirmed (정상) / pending (대기) / reversed (취소)
payment_method: 무통장 / 현금 / 카드 / 플랫폼 / 기타
reference_id: order_id (nullable — 예치금/선입금은 null 허용)
```

**핵심 원칙**: 수금은 반드시 주문에 묶이지 않는다

---

#### payment_allocations 테이블 (수금 분배)

```
payment_id / order_id / allocated_amount
```

목적: 하나의 수금을 여러 주문에 나눠 적용
```
예) 100만원 입금 → 주문A 40만원 + 주문B 60만원 분배
```

---

#### 수금목록

**목적**: 언제, 누구에게, 얼마를 받았는지 추적하는 화면

**컬럼**
```
수금일자 | 거래처명 | 수금금액 | 수금방식 | 연결주문 | 미수잔액 | 메모 | 상태
```

**빠른 필터**
```
오늘 수금 / 미수 거래처 / 대량 수금
```

**기능**
- 검색: 거래처명
- 필터: 거래처 / 날짜 범위 / 수금방식 / 상태
- 정렬: payment_date DESC + created_at DESC
- 수금 클릭 → 상세 이동
- 거래처별 수금 합계 표시
- 기간별 수금 합계 표시
- 출력: 엑셀 / PDF / JPG

**Empty State**: "수금 내역이 없습니다"

---

#### 수금등록

**목적**: 수금관리에서 직접 수금을 등록하는 화면

**입력 항목**
```
거래처 선택 (검색)
수금일자 (기본값: 오늘)
수금방식: 무통장 / 현금 / 카드 / 플랫폼 / 기타
수금금액
연결주문 (선택 / 미연결 가능)
메모
```

**필수값**: 거래처 / 수금일자 / 수금방식 / 수금금액

**예치금 표시**
- 예치금 보유 거래처 → 수금등록 화면에 예치금 잔액 표시
- "예치금 사용" 체크 시 customer_deposits에서 차감

**수금 초과 처리**
```
수금액 > 현재 잔액 → 경고 표시
"현재 잔액보다 많이 입력되었습니다. 초과 금액은 예치금으로 처리됩니다."
초과 금액 → customer_deposits 저장
잔액 → 0 처리
```

---

#### 수금 → 주문 분배

**흐름**
```
수금 등록 완료
→ [주문에 분배] 버튼
→ 해당 거래처 미수 주문 목록 표시
→ 주문 선택 + 금액 입력
→ payment_allocations 저장
```

---

#### 수금 상세 (`/payments/[id]`)

**구성**
```
[기본 정보]   수금일자 / 거래처 / 수금방식 / 상태
[수금 금액]   수금액 / 미수잔액 (거래처 기준)
[연결 주문]   연결된 주문 목록
[분배 내역]   payment_allocations 기준
[메모]
[이력]        수정 / 취소 이력
```

**액션**
- 취소 (→ reversed)
- 수정 (관리자)
- 주문 재연결

---

#### 수금 취소 흐름

```
[취소] 버튼 클릭
→ 확인 모달: "이 수금을 취소하시겠습니까?"
→ 확인 시 status = reversed
→ 잔액 자동 재계산
→ 기존 데이터 유지 (물리 삭제 금지)
```

---

#### 수금 입력 경로 (2가지, 결과 동일)

```
1. 주문등록 시 [수금 버튼] → payments 테이블 생성
2. 수금관리에서 직접 입력 → payments 테이블 생성
```

절대 분리 금지 / 동일 테이블 동일 처리

---

#### 예치금 구조

```
customer_deposits 테이블
- customer_id / balance / updated_at

deposit_logs 테이블
- customer_id / amount / type (적립/사용) / created_at
```

예치금 = 부채 개념 (수익 아님)

---

#### 출력 기능

- 전체 수금: 엑셀 / PDF / JPG
- 거래처별 수금: 엑셀 / PDF / JPG
- 기간별 수금: 엑셀 / PDF / JPG

---

#### 핵심 원칙

1. 수금은 거래가 아니라 현금 흐름이다
2. 수금은 여러 주문에 나눠질 수 있다
3. 주문과 수금은 연결되지만 종속되지 않는다
4. 수금은 절대 삭제하지 않는다
5. 예치금은 반드시 추적 가능해야 한다
6. 초과 수금은 예치금으로 처리한다
7. 돈 데이터는 반드시 복구 가능해야 한다

---

### 6-9. 지급관리

**한 줄 정의**
지급은 매입의 결과가 아니라, 현금 흐름의 결정이다.

**목적**: 나가야 할 돈을 정확히 통제하고 현금 흐름을 지키는 시스템

---

#### 메뉴 구조

```
지급관리
ㄴ 지급목록  (메인)
ㄴ 지급등록
```

```
수금 = 돈 들어옴 (inbound / AR)
지급 = 돈 나감  (outbound / AP)
```
→ 절대 하나로 묶지 않는다

---

#### 데이터 구조

**payments 테이블 (direction 필드로 통합)**

공통 데이터 모델(9번 시스템 구조)을 따른다.

```
지급 조회 기준: direction = 'outbound' / type = 'order'
status: confirmed (지급완료) / pending (대기) / reversed (취소)
reference_id: purchase_id (nullable — 선지급은 null 허용)
```

**지급 분배 테이블**
```
payment_allocations
- payment_id / purchase_id(nullable) / allocated_amount
```

- purchase_id nullable: 선지급(매입 발생 전 지급) 허용

---

#### 지급 예정일 관리

**기준**: `purchase.due_date`

**생성 방식**
```
① 매입 등록 시 결제조건 기반 자동 생성
   예) net 30 → 매입일 + 30일

② 수동 수정 가능
```

**지급 상태 4단계**
```
미지급       → 지급 전
부분지급     → 일부만 지급
지급완료     → 전액 지급
지급지연     → due_date 초과
```

---

#### 지급목록

**목적**: 언제, 누구에게, 얼마를 지급했는지 추적하는 화면

**컬럼**
```
지급일자 | 매입처명 | 지급금액 | 지급방식 | 연결매입 | 미지급잔액 | 상태
```

**빠른 필터**
```
지급 예정 / 지급 지연 / 선지급
```

**기능**
- 검색: 매입처명
- 필터: 매입처 / 기간 / 지급방식 / 상태
- 정렬: 최신순 / 금액순
- 지급 클릭 → 상세 이동
- 기간별 지급 합계 표시
- 매입처별 지급 합계 표시
- 출력: 엑셀 / PDF / JPG

**Empty State**: "지급 내역이 없습니다"

---

#### 지급등록

**입력 항목**
```
매입처 선택 (검색)
지급일자 (기본값: 오늘)
지급방식: 무통장 / 현금 / 카드 / 플랫폼 / 기타
지급금액
연결 매입 (선택 / 미연결 가능)
메모
```

**필수값**: 매입처 / 지급일자 / 지급방식 / 지급금액

---

#### 선지급 처리

```
선지급 등록 → purchase_id = NULL (미연결)
→ 이후 매입 발생
→ 수동 또는 자동 매칭
```

원칙: 지급은 먼저 발생할 수 있다 / 매입은 나중에 연결된다

---

#### 지급 분배

**상황**: 한 번에 500만원 지급 → 여러 매입에 나눠야 함

**흐름**
```
지급 등록
→ [매입에 분배] 버튼
→ 미지급 매입 목록 표시
→ 매입 선택 + 금액 입력
→ payment_allocations 저장
```

---

#### 미지급금 계산

```
미지급금 = 총 매입 - 총 지급
```
DB 저장 금지 → 계산값

---

#### 지급 상세 (`/disbursements/[id]`)

**구성**
```
기본 정보    지급일자 / 매입처 / 지급방식 / 상태
지급 금액    지급액 / 미연결 금액 / 남은 잔액
연결 매입    연결된 매입 목록
분배 내역    payment_allocations 기준
메모
이력         수정 / 취소 이력
```

---

#### 지급 취소 흐름

```
[취소] 클릭
→ 확인 모달
→ status = reversed
→ 미지급금 재계산
→ 기존 데이터 유지 (물리 삭제 금지)
```

---

#### 지급 원장

**정의**: 매입 흐름 + 지급 흐름 추적

**구성**
```
날짜 | 매입금액 | 지급금액 | 잔액 | 메모
```

```
매입 발생 → 매입채무 발생
지급      → 채무 감소
```

**기능**: 매입처별 조회 / 기간별 조회 / 잔액 계산
**출력**: 엑셀 / PDF / JPG

---

#### 대시보드 연결

블록 7 (오늘 자금 배치 제안) 연결 데이터:
```
오늘 지급 예정: 3,200,000원
지연 지급:      1,100,000원
```

---

#### 출력 기능

- 지급목록: 엑셀 / PDF / JPG
- 매입처별 지급 리포트: 엑셀 / PDF / JPG

---

#### 핵심 원칙

1. 지급은 반드시 추적 가능해야 한다
2. 지급은 삭제하지 않는다 (reversed 처리)
3. 지급은 여러 매입에 나눌 수 있다
4. 지급은 매입채무를 감소시킨다
5. 지급은 수금과 절대 섞지 않는다
6. 선지급은 허용되며 이후 매입과 연결된다
7. 모든 돈의 흐름은 복구 가능해야 한다

---

### 6-10. 원장관리

**한 줄 정의**
원장은 숫자가 아니라, 돈의 흐름을 보여주는 지도다.

**목적**: 판매/수금/매입/지급의 누적 흐름을 조회하는 시스템
- 수동 수정 없음 / 모든 값은 계산값
- 원장은 "결과"가 아니라 "흐름"
- 입력 없음 (100% 조회 전용)

---

#### 메뉴 구조

```
원장관리
ㄴ 매출원장  (거래처 기준)
ㄴ 매입원장  (매입처 기준)
```

```
매출원장 = 판매 + 수금 + 반품 흐름
매입원장 = 매입 + 지급 흐름
```

---

#### 필터 (공통)

```
거래처 / 매입처 선택 (필수)
기간 선택 (필수): 이번달 / 지난달 / 기간 직접 선택
```

추가 필터:
- 세금계산서 발행 필요 (체크 시 해당 거래처만 노출)
- 결제수단: 현금 / 무통장 / 카드

---

#### 화면 상단 — 기초잔액 표시 (필수)

```
기초잔액: 1,200,000원
```

이유:
- 잔액이 왜 이 금액에서 시작하는지 확인 가능
- 엑셀/PDF 출력 시 회계 기본값
- 없으면 잔액 출발점 이해 불가

---

#### 거래 흐름 테이블

**컬럼**
```
날짜 | 유형 | 상품명 | 공급가액 | 부가세 | 합계 | 결제수단 | 잔액(누적)
```

**거래 유형 색상 구분** (한눈에 흐름 파악)
```
판매 → 파랑
수금 → 초록
반품 → 빨강
매입 → 주황
지급 → 보라
```

원장 = "읽는 것"이 아니라 "보는 것"

---

#### 잔액 계산 공식

**매출원장**
```
잔액 = 기초잔액 + Σ판매 - Σ수금 + Σ반품
```

**매입원장**
```
잔액 = 기초잔액 + Σ매입 - Σ지급
```

**데이터 기준**
```
confirmed만 포함
draft 제외
cancelled 제외
```

DB 저장 금지 → 계산값

---

#### 요약 영역

**매출원장**
```
총 매출 | 총 수금 | 현재 미수금
```

**매입원장**
```
총 매입 | 총 지급 | 현재 미지급금
```

---

#### 세금계산서 로직 (핵심)

**기준**
```
현금 / 무통장 → 계산서 대상 ⭕
카드           → 계산서 제외 ❌
```

**혼합 결제 처리**
```
예) 총 거래 100만원
   카드: 40만원
   현금: 60만원
   → 계산서 대상: 60만원
```

카드 금액 제외 → 나머지만 계산서 대상

**세금 요약 영역**
```
과세 합계
면세 합계
계산서 발행 금액
```

---

#### 출력 기능

- 거래처별 원장: 엑셀 / PDF / JPG
- 기간별 원장: 엑셀 / PDF / JPG
- 세금 기준 원장: 엑셀 / PDF / JPG

---

#### Empty State

```
"해당 기간 거래 내역이 없습니다"
```

---

#### 핵심 원칙

1. 원장은 계산된 결과다
2. 모든 값은 변경 불가 (계산값)
3. 매출과 매입 원장은 분리한다
4. 기초잔액은 반드시 화면에 표시한다
5. 카드 결제는 세금계산서 대상이 아니다
6. 현금/무통장만 계산서 대상이다
7. 혼합 결제는 반드시 분리 계산한다
8. 원장은 반드시 출력 가능해야 한다

---

### 6-11. 매출분석

**한 줄 정의**
매출분석은 얼마나 팔았냐가 아니라, 어디서 돈을 잃고 있는지 찾는 시스템이다.

**목적**: 의사결정에 쓰는 지휘통제실 — 수익 구조를 파악하고 위험을 탐지한다
- 입력 없음 (100% 조회)
- 분석 기준: order_lines 스냅샷 데이터만 (product 테이블 참조 금지)

---

#### 메뉴 구조 (탭 구조)

```
매출분석
ㄴ 매출현황     (전체 흐름)
ㄴ 마진분석     (상품 중심)
ㄴ 거래처분석   (고객 중심)
ㄴ 위험신호     (이상 탐지)
```

---

#### 데이터 기준

```
order.status = confirmed만 포함
cancelled 제외 / draft 제외
반품(refund) 포함 → 음수 처리
```

---

#### 기간 필터 (공통)

```
이번달 / 지난달 / 최근 3개월 / 1년 / 사용자 지정
```

---

#### 탭 1 — 매출현황 (전체 흐름)

**매출 요약**
```
총 매출 | 총 원가 | 총 마진 | 마진율(%)
전월 대비 변화율 (%)
```
이유: 절대값보다 "변화"가 중요

**차트**
- 타입: 라인 차트
- 구성: 매출 / 마진 / 원가
- 비교: 전월 대비 / 전년 동기 대비 (옵션)

---

#### 탭 2 — 마진분석 (상품 중심)

**상품별 분석 컬럼**
```
상품명 | 판매수량 | 매출 | 원가 | 마진 | 마진율 | 마진 기여도(%)
```

**마진 기여도 정의**
```
마진 기여도 = 해당 상품 마진 / 전체 마진 합계
```
이유: "돈 버는 상품"을 찾는 유일한 지표

**정렬**: 마진순 / 마진 기여도순 / 판매수량순

**상품 집중도**
```
상위 상품 매출 비중 → 상품 리스크 관리
```

---

#### 탭 3 — 거래처분석 (고객 중심)

**거래처별 분석 컬럼**
```
거래처명 | 매출 | 원가 | 마진 | 마진율 | 매출 비중(%) | 매출 순위 | 매출 성장률(%)
```

**정렬**: 매출순 / 마진순 / 성장률순

**고객 집중도**
```
상위 3개 거래처 매출 비중
```
이유: 특정 거래처 의존도가 높으면 1개가 빠졌을 때 회사가 흔들림

**추가 지표**
```
평균 결제 기간: 주문일 ~ 수금일까지 평균
미수금 비율: 미수금 / 총 매출
반복 구매율: 2회 이상 구매 고객 비율
```

---

#### 탭 4 — 위험신호 (이상 탐지)

목적: 위험은 항상 "잘 되는 곳"에서 발생한다

**1. 매출 감소 거래처**
```
기준: 전월 대비 -20% 이상
```

**2. 마진 낮은 거래처**
```
기준: 마진율 < settings.margin_warning_threshold
```

**3. 손해 상품**
```
기준: 마진 < 0
```

**4. 매출은 있는데 마진 없는 거래처 (핵심)**
```
매출 TOP인데 마진 하위
→ "열심히 팔았는데 돈 못 버는 구조" 탐지
```

**5. 반품 많은 상품**
```
기준: 반품율 높은 상품
이유: 숨은 손실 포인트
```

---

#### 원장관리와의 관계 정의

```
원장관리  = 거래 흐름 / 미수금 관리
매출분석  = 성과 분석 / 수익 구조
```
절대 섞지 않는다

---

#### 출력 기능

- 기간별 매출 분석: 엑셀 / PDF / JPG
- 거래처별 분석: 엑셀 / PDF / JPG
- 상품별 분석: 엑셀 / PDF / JPG

---

#### Empty State

```
"해당 기간 매출 데이터가 없습니다"
```

---

#### 핵심 원칙

1. 매출은 숫자가 아니라 흐름이다
2. 분석은 비교로 한다 (전월 대비 필수)
3. 매출보다 마진이 중요하다
4. 많이 파는 상품보다 많이 남기는 상품이 중요하다
5. 성장보다 구조가 중요하다
6. 위험은 항상 "잘 되는 곳"에서 발생한다

### 6-12. 자금관리

**한 줄 정의**
자금관리는 돈을 버는 시스템이 아니라, 망하지 않게 만드는 시스템이다.

**목적**: 회사가 망하지 않게 하고, 대표의 삶이 무너지지 않게 만드는 돈 분배 시스템

---

#### 메뉴 구조

```
자금관리
ㄴ 자금계획  (메인)
ㄴ 자금설정
```

---

#### 핵심 철학

1. 돈은 남으면 쓰는 게 아니라, 먼저 나눈다
2. 계획과 실행은 반드시 분리한다
3. 부족한 돈은 숨기지 않고 이월한다
4. 과거 데이터는 절대 수정하지 않는다
5. 자동 계산 + 수동 실행 구조로 간다

---

#### 자금설정

**계좌관리 (accounts)**

입력 항목:
```
은행명 / 계좌번호 / 별칭 / 용도(사용자 정의)
현재 잔액 / 마지막 업데이트 시각
```

잔액 상태 (대시보드 연동):
```
정상: 7일 이내 업데이트
주의: 7~14일
필요: 14일 초과
```

**자금 규칙 (fund_rules)**

구조:
```
name (예: 부가세 / 생활비 / 인건비)
calculation_type: fixed / percentage / manual
amount or rate
target_account_id
priority (우선순위)
```

계산 기준: 이번달 confirmed 매출

계산 방식:
```
fixed:      daily_amount = 월금액 ÷ 영업일수
percentage: daily_amount = (누적매출 × 비율) ÷ 영업일수
```

**영업일 설정**
```
calendar / business 선택
주말 포함 여부 / 공휴일 포함 여부
```

---

#### 자금계획 (핵심 화면)

**상단 요약**
```
오늘 계획 총액 | 오늘 실제 이행 금액 | 총 미납 금액 | 가용 자금(계좌 합계)
```

**리스트 구조 (각 row)**
```
계좌명 | 목적 | 오늘 계획 금액 | 이월 금액 | 오늘 총 필요 금액 | 상태 | [이체 실행] 버튼
```

**상태 정의**
```
pending:   아직 실행 안됨
partial:   일부만 실행
completed: 완료
overdue:   미납 발생
```

---

#### [이체 실행] 버튼 흐름

```
클릭
→ 실제 이체 금액 입력
→ 완료 / 부분이행 선택
→ 메모 입력 (선택)
→ 저장

저장 시:
fund_transfers 기록 생성
actual_amount 저장
상태 업데이트
```

---

#### 부족금 처리 (이월 시스템)

```
조건: actual_amount < planned_amount
처리: carry_over_amount = 차액 → 다음날 자동 포함
월 경계: 이월 미납 별도 표시 (숨기지 않음)
```

---

#### 우선순위 처리

```
fund_rules.priority 기준
가용 자금 부족 시 → 우선순위 높은 항목부터 배정
```

---

#### 대시보드 연결

```
대시보드 블록 7 (오늘 자금 배치 제안) 연결
표시: 오늘 이체 필요 금액 / 오늘 미납 금액
이동: 대시보드 → [자금관리로 이동] 버튼
```

---

#### 계좌 잔액 업데이트

```
방식: 사용자 수동 입력
위치: 자금관리 / 대시보드 양쪽에서 가능
표시: 현재 잔액 / 마지막 업데이트 시각 / 상태(정상/주의/필요)
```

---

#### 출력 기능

- 자금계획 리스트: 엑셀 / PDF / JPG
- 기간별 자금 흐름: 엑셀 / PDF / JPG
- 이월 내역: 엑셀 / PDF / JPG

---

#### 핵심 원칙

1. 돈은 계획 없이 쓰면 반드시 무너진다
2. 계획된 돈은 반드시 실행 여부를 기록한다
3. 부족한 돈은 숨기지 않고 드러낸다
4. 수익이 아니라 현금 흐름이 생존을 결정한다
5. 자금관리는 자동 계산 + 수동 실행이다

---

### 6-13. 자동화영업

**한 줄 정의**
자동화영업은 대신 해주는 시스템이 아니라, 가장 잘 팔 수 있게 만들어주는 시스템이다.

**핵심 정의**: 데이터가 행동을 지시하고, 행동이 매출로 이어지고, 그 결과가 다시 다음 행동을 만드는 시스템

---

#### 메뉴 구조

```
자동화영업
ㄴ 영업스케줄  (메인)
ㄴ 영업이력
ㄴ 스크립트관
ㄴ 실행센터   (빠른 실행 허브 / 매출 직결 핵심)
```

---

#### 영업스케줄 (핵심 화면)

**상단 요약**
```
오늘 해야 할 영업 수 | 오늘 완료 수 | 미처리 수
```

**뷰**: 달력 뷰 ↔ 리스트 뷰 전환

**리스트 컬럼**
```
거래처명 | 점수 | 행동유형(전화/문자/방문) | 추천 스크립트 | 상태 | [즉시 실행] | [내일로]
```

**핵심 UX**: 클릭 → 스크립트 자동 적용 → 실행

자동 생성 기준: 수금 우선순위 점수 (매일 03:00 배치)
Snooze: "내일로" → scheduled_date +1 (삭제 금지)

스케줄 필드:
```
customer_id / scheduled_date / action_type / script_id
status (pending / completed / missed)
중복 방지: (customer_id + date) unique
```

---

#### 점수 시스템 (고도화)

**최종 점수 = 연체 + 주문공백 + 미연락 + 매출기여 + 하락**

```
연체금 점수 (0~50):
  100만원 이상 → 50점 / 50만원 이상 → 30점
  10만원 이상 → 15점 / 1원 이상 → 5점

주문 공백 점수 (0~30):
  days_overdue = 마지막주문일 - 주문주기 초과분
  score += min(days_overdue × 2, 30)

미연락 점수 (0~20):
  score += min(days_since_last_contact, 20)

매출 기여도 점수:
  상위 거래처일수록 가중치 증가

하락 감지 점수:
  전월 대비 매출 감소 시 점수 추가
```

임계값: settings.sales_score_threshold = 15

---

#### 실행 시스템

**추천 행동 자동 제시 (데이터 기반)**

계산 기준:
```
전화 성공률  = 전화 후 7일 내 주문 발생 횟수 / 전체 전화 횟수
문자 성공률  = 문자 후 7일 내 주문 발생 횟수 / 전체 문자 횟수
카카오 성공률 = 카카오 후 7일 내 주문 발생 횟수 / 전체 카카오 횟수
```

추천 로직: 가장 성공률 높은 채널 추천
```
예) "이 고객은 전화 전환율 32% → 전화 추천"
```

추천은 감이 아니라 데이터로 결정한다

**실행 흐름**
```
[거래처] → [추천 행동 확인] → [스크립트 선택] → [즉시 실행]
```

**버튼 위치 (어디서든 실행 가능)**
```
영업스케줄 / 거래처목록 / 주문목록 / 거래처 상세 / 실행센터
```

**메시지 발송 (알리고 API)**
```
버튼 클릭 → message_logs 생성
API 호출 → 성공: sent / 실패: failed (재시도)
contact_logs 자동 기록
```

절대 금지: 자동 무한 발송 ❌ / 사용자 승인 없는 발송 ❌

---

#### 영업이력 (contact_logs 확장)

**컬럼**
```
날짜 | 거래처 | 행동유형 | 결과코드 | 다음행동일 | 담당자 | 주문 발생 여부
```

**필터**: 결과코드 / 기간 / 거래처

**결과 코드 (outcome_type)**
```
interested / potential / maintained / churn_risk
competitor / rejected / no_answer / callback_requested / order_placed
```

**다음 행동 날짜 (주문주기 기반)**
```
interested → 주문주기 × 0.3
potential  → × 0.5
maintained → × 0.8
churn_risk → × 0.2
rejected   → × 2.0
no_answer  → 2일 고정
```

**성과 연결**: 이 영업 → 실제 주문 발생 여부 연결
이거 없으면 영업이 의미 없음

**상태 이중 구조**
- system_status (자동 계산) / sales_status (영업자 입력)

**고객 동기화 (트랜잭션)**
```sql
BEGIN;
  INSERT contact_logs;
  UPDATE customers SET sales_status, last_contact_date, last_contact_outcome;
COMMIT;
```

연락 금지 고객: do_not_contact 필드 → 스케줄 자동 제외

---

#### 스크립트관 (고급화)

**기본 기능**: 목록 / 등록 / 수정 / 비활성화

**추가**
- 스크립트별 전환율 표시
- 전환율 높은 스크립트 우선 추천

허용 변수:
```
{{customer_name}} / {{last_order_date}} / {{last_order_amount}}
{{overdue_amount}} / {{main_product}} / {{my_name}} / {{company_name}}
```

최소 3~5개 기본 제공

---

#### 실행센터 (매출 직결 핵심)

**역할**: 지금 당장 해야 할 것을 즉시 실행

**구성**
```
지금 연락해야 할 고객 TOP 3
추천 행동 (채널 + 스크립트)
바로 실행 버튼
```

**대시보드 연결**: 대시보드 → 실행센터 바로 진입
이유: 찾는 시간 = 매출 손실

---

#### 네이버플레이스 분석

```
URL 입력 → 메뉴 / 가격 / 리뷰 자동 분석
→ 추천 식자재 + 영업 스크립트 자동 생성
```

예: "이 식당은 닭요리 중심 → 닭 관련 식자재 제안"

---

#### 연락 타이밍 최적화

**저장 구조**
```
contact_logs.contact_hour
contact_logs.outcome_type
```

**계산 기준**: order_placed 발생 시간 기준 집계

**예시**
```
A거래처
10시 → 주문 발생률 40%
15시 → 5%
→ 10시 추천 → 해당 시간대 자동 스케줄 생성
```

---

#### 초기 데이터 온보딩 (시스템 생존 조건)

**문제**: 초기 contact_logs 부족 → 추천 행동 정확도 낮음 → 신뢰 손실 → 사용 중단

**해결**: 기존 영업 이력 대량 입력 기능

**기능**
```
엑셀 업로드:
  거래처명 / 연락일자 / 행동유형 / 결과코드 / 주문 발생 여부

자동 매핑: 거래처명 → customer_id

저장: contact_logs 일괄 생성
```

최소 기준: 거래처당 3~5건 이상 확보 시 추천 정확도 상승

적용 시점: 초기 온보딩 시 필수

---

#### 자동화 수준

```
자동 발송 ❌
자동 추천 ⭕
수동 실행 ⭕
```

이유: B2B는 관계 비즈니스 / 자동화 과하면 관계가 깨진다

---

#### 핵심 원칙

1. 영업은 데이터로 한다
2. 행동 없는 CRM은 의미 없다
3. 전환율로 판단한다
4. 좋은 건 반복, 나쁜 건 제거한다
5. 자동화는 보조 역할이다
6. 데이터 없으면 자동화 의미 없다
7. 데이터가 쌓일수록 시스템이 강해진다

### 6-14. 설정

**한 줄 정의**
좋은 시스템은 개발자가 아니라 운영자가 통제한다.

**핵심 정의**: 설정은 개발자가 코드를 수정하는 영역이 아니라, 운영자가 수치·문구·정책을 직접 통제하는 시스템이다.

설정은 단순 값이 아니라 시스템의 판단 기준이다.
모든 설정 값은 변경될 수 있으며, 변경된 값은 시스템 전체에 즉시 영향을 미친다.

---

#### 핵심 철학

1. 모든 기준값은 설정에서 변경 가능해야 한다
2. 코드에 하드코딩된 값은 최소화한다
3. 운영 중에도 즉시 변경 가능해야 한다
4. 설정 변경은 반드시 로그로 기록된다
5. 설정은 시스템의 "뇌" 역할을 한다
6. 설정은 많을수록 좋은 것이 아니다 — 핵심만 노출한다

---

#### 메뉴 구조

```
설정
ㄴ 기본설정       (기준값)
ㄴ 계정/직원 관리
ㄴ 고객 분류 관리 (구매채널 / 회원등급 등)

```

```
설정 변경은 시스템 전체에 즉시 반영되고,
변경 이력은 추적 가능해야 한다.

설정 → 로그 → 기능 변화 → 결과
이 흐름이 하나로 연결될 때 시스템은 완성된다.
```

## 7. 공통 UX 원칙

**핵심 정의**: UX의 목적은 사용성을 높이는 것이 아니라, 행동을 발생시키고 돈을 만드는 것이다.

**한 줄 핵심**: UX는 경험이 아니라 "행동 제어 시스템"이다.

---

### 행동 선택 원칙

막지 않는다 → 선택하게 만든다 → 미루지 못하게 만든다
→ 가장 중요한 행동을 우선 제시한다

---

### 측정 UX (Measurement UX)

모든 UX는 측정 가능해야 한다. 감각이 아니라 데이터로 UX를 개선한다.

```
측정 항목:
- 평균 입력 시간
- 클릭 횟수
- 행동 완료율
- 이탈률

기준:
- 3초 초과 입력   → UX 실패
- 클릭 3회 초과   → UX 개선 대상
- 완료율 80% 미만 → 구조 문제
```

---

### 행동 강제 UX (Action Forcing UX)

사용자가 중요한 행동을 미루지 못하게 설계한다.

```
수금 미처리  → 대시보드 고정 노출
납기 임박   → 상단 강조 표시
연체 발생   → 행동 버튼 강제 노출
```

---

### 피드백 UX (Feedback UX)

모든 행동은 결과 피드백을 가져야 한다.
사용자가 무엇이 효과적인지 학습하게 만든다.

```
행동 → 결과 → 평가 → 다음 행동

예) 전화 → 7일 내 주문 발생
    → "전화 효과 있음" 표시
```

---

### 우선순위 UX (Priority UX)

사용자는 항상 "지금 가장 중요한 행동 1개"만 보게 한다.

```
금지: 해야 할 일 리스트 나열
허용: 지금 해야 할 1개 행동 우선 노출
```

적용: 실행센터 / 대시보드와 연결

---

### 협상 UX 원칙

협상 시 시스템은 거래 성사 확률 + 예상 수익을 함께 제시한다.
사용자의 행동을 제한하지 않고 선택을 돕는 구조.

---

### 실패 / 로딩 UX 원칙

- 핵심 액션은 실패 처리, 로딩 상태, 취소/되돌리기 포함
- 시스템은 항상 현재 상태를 명확히 표시
- 실패 시 단순 안내 금지 → 반드시 "다음 행동"을 제시한다

---

### 입력 원칙

```
3초 입력 목표 (3초 초과 시 UX 실패로 정의)
기본값 자동 적용
이전 값 기억
반복 입력 제거
단계형 입력 금지
불필요한 확인창 금지
```

---

### 디자인 기준

```
토스       → 직관적이고 깔끔한 정보 구조
당근마켓   → 빠른 행동 유도
Notion     → 단순하고 가독성 중심
```

```
UX (구조/흐름) → 절대 변경 금지
UI (디자인)    → 자유
```

---

### 실행 위치 정의 (핵심)

이 UX 원칙은 특히 아래 2곳에서 가장 강하게 적용된다.

```
1. 대시보드  — "오늘 무엇을 해야 하는가"를 결정하는 곳
2. 실행센터  — "지금 당장 무엇을 해야 하는가"를 실행하는 곳
```

```
대시보드 → 판단 (Decision)
실행센터 → 실행 (Action)
```

**필수 규칙**
```
대시보드는 여러 정보를 보여줄 수 있다.
실행센터는 반드시 "지금 당장 해야 할 1개 행동"만 보여야 한다.
```

**금지**
```
실행센터에 리스트 나열 금지
우선순위 없는 정보 노출 금지
```

---

### 절대 금지

```
감각 기반 UX 판단 금지
데이터 없는 UX 개선 금지
행동 없는 화면 금지
```

---

### 최종 선언

```
좋은 UX는 보기 좋은 UI가 아니라,
행동을 만들고 결과를 학습시키는 구조다.

UX 원칙은 대시보드에서 방향을 만들고,
실행센터에서 행동을 완성한다.

대시보드 (판단) → 실행센터 (실행) → 영업이력 (기록) → 대시보드 (반영)
이 루프가 닫힐 때 시스템은 완성된다.
```

## 8. 식당OS 기능 상세

### 8-1. 식당OS 정의

**한 줄 정의**: 식당OS는 "사장님 대신 생각해주는 운영 지시 엔진"이다.

식당OS의 본질은 **해답이 있는 제안을 통해 사장님의 행동을 이끌어내는 시스템**이다.

**[철학]**
- 추천은 선택이다 / 제안은 행동이다
- 모든 제안은 "언제 행동해야 하는지"를 포함
- 행동하지 않았을 때 발생할 결과까지 함께 제시
- 모든 입력은 즉시 제안으로 이어진다
- 최소한의 입력만으로도 제안 제공, 이후 점진적 확장

**[실행 규칙]**
```
핵심 흐름: 문제 감지 → 행동 유도 → 거래 발생 → 데이터 축적 → 반복 → 자동화

진입: 앱 실행 → 무조건 오늘운영 화면
메뉴 우선순위: 오늘운영 > 발주요청 > 나머지
```

---

### 8-2. 식당OS 메뉴 구조

```
식당OS
ㄴ 오늘운영     (메인 — 앱 진입 시 무조건 이 화면)
ㄴ 발주관리     (핵심 거래 기능)
  ㄴ 발주요청
  ㄴ 발주요청 목록
  ㄴ 입찰 결과
  ㄴ 발주 내역
ㄴ 돈관리       (생존 관리)
  ㄴ 지급 예정
  ㄴ 거래처 미지급금
  ㄴ 자금 흐름
ㄴ 거래처관리   (매입처 판단)
  ㄴ 거래처 목록
  ㄴ 거래처 정보
ㄴ 알림         (트리거 엔진)
  ㄴ 알림 목록
  ㄴ 중요 알림
ㄴ 설정         (기초 데이터 입력)
  ㄴ 매장 설정
    ㄴ 식자재 입력
    ㄴ 고정비 입력
    ㄴ 테이블 수 입력
    ㄴ 메뉴/가격 입력
  ㄴ 거래 조건 설정
```

**메뉴 역할 정의**
```
오늘운영  → 행동 시작 화면 (판단이 아닌 실행)
발주관리  → 검증 메뉴 (구매가 아닌 현재 거래 검증)
돈관리    → 지급 / 미지급 / 자금 흐름 통합 (생존 관리)
거래처관리 → 매입처 선택과 유지 판단 DB
알림      → 행동 트리거 시스템 (단순 알림 아님)
설정      → 제안 정확도 기반 데이터 입력 (강제 금지)
```

---

### 8-3. 오늘운영 (행동 중심 대시보드)

**최종 정의**: 오늘운영은 "정보를 보여주는 화면"이 아니라 "지금 해야 할 행동을 3개만 제시하고 완료 시 보상을 주는 실행 엔진"이다.

**목적**: 사장님이 매일 가장 먼저 보는 화면 — 판단 화면이 아니라 행동 시작 화면

---

#### UX 철학 (따뜻한 돈 게임화)

식당OS는 "관리 도구"가 아니라 "같이 장사하는 파트너"다.
- 돈은 정확하게 / 표현은 따뜻하게 / 행동은 쉽게
- 압박 ❌ → 함께 개선하는 느낌 ⭕

**즉각 보상**: "이번 선택으로 2,000원 아꼈어요 👍"
**누적 성과**: "이번 달 총 82,000원 절약했어요"
**부드러운 안내**: "이 부분은 조금 아쉬워요, 바꾸면 더 좋아질 수 있어요"

금지: 레벨/뱃지/랭킹 / 차가운 경고 / 판단 강요

---

#### 카드 우선순위 (최대 3개)

```
1순위: 지급 임박 → 돈 흐름 카드
2순위: 절약 5,000원 이상 → 절약 카드
3순위: 일반 할 일 카드
최대 3개 카드 노출 (초과 금지)
```

카드 = 정보가 아니라 "미완료 행동 리스트"다.

---

#### 카드 생성 조건 (자동 생성)

**돈 흐름 카드**
```
생성 조건:
- due_date - today ≤ 3일
- 또는 지급 예정 금액 ≥ 잔액 80%

카드 내용:
"이번 주 나갈 돈: 350,000원"
"내일 결제 35만원 부족해요 → 같이 맞춰볼까요?" (숫자 정확히)
버튼: [지금 정리하기]
```

**절약 기회 카드**
```
생성 조건:
- 최근 구매가 대비 추천가 -5% 이상
- 또는 직전 구매 대비 +10% 상승

카드 내용:
"지금 고춧가루 가격이 조금 높은 편이에요"
"다른 조건 보면 약 2,000원 아낄 수 있어요"
버튼: [같이 비교해보기]
```

**오늘 할 일 카드**
```
생성 조건:
- status = selected (선택 대기)
- 또는 status = bidding 중 24시간 경과
- 또는 미처리 발주요청 존재

카드 내용 (상태별):
- bidding 24~48시간:
  "입찰 결과를 기다리고 있어요. 내일까지 오면 알려드릴게요 👍"
- 결과 도착:
  "입찰 결과가 도착했어요. 지금 확인해보세요"
- 선택 대기:
  "오늘 확인하면 좋은 2가지 있어요"
버튼: [하나씩 해결하기]
```

### 8-4. 발주관리

**정의**: 구매 메뉴가 아니라 **검증 메뉴** (현재 거래가 맞는지 확인하는 기능)

#### 발주요청 핵심 심리

```
문제 없음 → 발주요청 안함
문제 발생 → 의심 → 비교 필요 → 발주요청
```

발주요청은 '주기적 기능'이 아니라 **'이벤트성 기능'**이다.
메뉴에서 찾아 쓰는 기능이 아니라 문제가 생겼을 때 자동으로 뜨는 기능이어야 한다.

예: "이 식자재 평균보다 18% 비쌉니다 → [발주요청하기]"

**발주요청 발생 트리거 (사장님이 의심할 때)**
```
가격이 비싸다고 느껴질 때
최근 가격이 올랐을 때
물건 품질이 떨어졌을 때
납품이 늦었을 때
메뉴 원가가 갑자기 올라갔을 때
```

#### 발주요청 단계적 전략

**① 초기 (능동형 MVP)**
- 사장님이 직접 발주요청 생성
- 입력 단순화 (기존 발주 데이터 활용)
- 목적: 사용자 행동 확보 / 가격·선택·거래 데이터 축적

**② 중간 (부분 트리거)**
- "지난주 대비 15% 상승했습니다" 등 단순 조건 기반 알림
- 과거 데이터와 비교한 이상 징후 감지

**③ 완성 (트리거형)**
- 시장 데이터 + 개별 데이터 기반 자동 판단
- 사장님이 요청하지 않아도 시스템이 먼저 제안
- "이 품목은 현재 평균보다 18% 비쌉니다 → 지금 발주요청을 하면 원가를 줄일 수 있습니다"

#### 핵심 원칙

```
1. 가격 강제가 아닌 조건 경쟁 (이 가격에 맞춰라 ❌ / 더 나은 조건을 제안해라 ⭕)
2. 최저가가 아닌 최적 선택 (가격 + 납기 + 신뢰도 + 거래 이력 종합 판단)
3. 기존 거래의 대체가 아닌 보완
```

#### 발주요청 상태 흐름

```
요청 생성 (draft)
→ 공개 (open)
→ 입찰 진행중
→ 조건 비교
→ 선택
→ 발주 확정 (ordered)
→ 거래 완료 (closed)

예외:
입찰 없음 → 자동 종료
기존 거래 유지 선택 → 이유 기록 (가격/납기/관계)
납기 지연/품질 문제 → 클레임 발생
cancelled → 취소 처리
```

#### 공급업체 들러리화 방지

```
동일 품목 반복 요청 제한 (월 3회)
일정 시간 내 선택 또는 종료 유도 (미선택 방치 금지)
결과 피드백 수집: 가격 경쟁력 부족 / 납기 조건 미흡 / 기존 거래 유지
식당 정보 일부 비공개: "인천 지역 / 중형 식당"
공급업체 참여 동기: 우수 결제 식당 표시 / 거래 안정성 정보 / 반복 거래 가능성
```

#### 4개 화면 역할 확정

```
1. 발주요청 (생성)
   → 새로운 RFQ 생성 / 최소 입력 UX
   → status: draft → open

2. 발주요청 목록 (진행 상태)
   → open / bidding / expired 상태 조회
   → "지금 처리해야 할 것" 강조 표시

3. 입찰 결과 (결정)
   → 결정 엔진 UI (추천 + 대안 구조)
   → selected → ordered 전환 핵심 화면

4. 발주 내역 (완료)
   → ordered / completed 조회
   → 반복 거래 진입 지점
```

공급자OS와 1:1 대응:
```
식당OS: RFQ 생성 → 선택 → 주문
공급자OS: RFQ 수신 → 견적 → 수주
```
같은 데이터를 서로 다른 관점으로 해석. 이 정합성 절대 깨지면 안 된다.

#### 발주요청 등록 입력

```
[필수]
- 제품 (SKU 기준 / 자동완성)
- 수량

[조건부 필수]
- 현재 구매가 (기존 사용 제품일 경우 → 절약 계산 가능)

[선택]
- 납기 희망일
- 요청 메모

[자동]
- buyer_tenant_id
- 위치
- 최근 구매 이력
- 평균 가격
- 과거 공급자
- 생성 시각
```

입력 즉시: "이 정도면 이 가격대가 일반적이에요"

핵심: 입력은 최소 / 판단은 시스템

---

#### 입찰 결과 화면 (결정 엔진 UI)

**이 화면은 비교 UI가 아니라 "결정 엔진 UI"다.**

구조: 추천 1개 + 대안 1~2개 (최대 3개)

**추천 카드 (반드시 존재)**
```
상단: "지금 이 조건이 가장 유리합니다"

표시:
- 가격 (강조)
- 납기
- 절약 금액 (금액 우선, % 보조)
  예) "약 3,200원 절약됩니다 (15%)"
- 신뢰도 (거래 횟수 / 안정성)

추천 기준: 가격 + 납기 + 거래이력 + 안정성 종합 점수 1위

CTA: [이 조건으로 진행하기]
```

**대안 카드**
```
CTA: [이 공급자 선택]
```

**절약 계산 우선순위**
```
1순위: 추천가 vs 최근 구매가
2순위: 추천가 vs 동일 RFQ 내 최고가
3순위: 추천가 vs 플랫폼 평균 (데이터 충분 시)
```

**선택 지연 방지**
```
"지금 선택하지 않으면 약 3,200원 더 지출될 수 있습니다"
```

금지:
```
4개 이상 리스트 ❌
단순 가격 나열 ❌
사용자 비교 유도 ❌
```

---

#### [이 조건으로 진행하기] 트랜잭션 (필수 규칙)

**이 버튼은 "선택 버튼"이 아니라 "거래를 생성하는 버튼"이다.**

클릭 시 아래 7단계를 하나의 트랜잭션으로 실행한다.

```
1. rfq_bids.status = 'accepted'
2. rfq_requests.status = 'ordered'
3. orders 레코드 생성
   - buyer_tenant_id
   - seller_tenant_id
   - order_type = 'purchase'
   - order_lines 자동 생성
4. payments 레코드 생성
   - direction = 'outbound'
   - payer_tenant_id = buyer
   - payee_tenant_id = seller
   - due_date = delivery_date 기준
5. 공급자OS에 수주 이벤트 전달
   → "주문이 확정되었습니다"
6. 오늘운영 카드 제거
   → 관련 액션 종료
7. 즉시 사용자 피드백
   "좋은 선택이에요 👍 거래가 시작됐어요"
```

추가 규칙:
```
atomic 트랜잭션 (중간 실패 시 전체 rollback)
중복 실행 방지 (idempotency 필수)
```

#### 반복 거래 루프

```
발주요청
→ 거래 완료
→ 만족도 기반 평가
→ "기본 거래처 등록" (자동 또는 선택)
→ 다음 주문 시 자동 추천
→ 반복 주문
→ 데이터 축적
→ 트리거 생성
```

발주요청은 시작이고, 반복 거래가 본질이다.

#### 데이터 테이블

```sql
rfq_requests (발주요청)
- id / restaurant_id / product_name / quantity
- current_price (nullable) / request_note
- deadline / region
- status (draft / open / closed / ordered / cancelled)

rfq_bids (입찰)
- id / rfq_id / supplier_id / price
- delivery_date / note
- status (submitted / accepted / rejected)
```

### 8-5. 돈관리

**최종 정의**: 돈관리는 "얼마가 있는지 보여주는 화면"이 아니라 "지금 나갈 돈을 통제하고 생존 상태를 안정시키는 실행 시스템"이다.

**핵심 철학**: 돈관리는 "정확한 재무 시스템"이 아니라 "망하지 않게 하는 시스템"이다.

---

#### 테이블 구조 (공통 payments 통합)

payments_outgoing 별도 테이블 생성 금지.
공통 데이터 모델(9번 시스템 구조)의 payments 테이블을 사용한다.

```
식당OS 조회 기준: direction = 'outbound'
공급자OS 조회 기준: direction = 'inbound'
같은 레코드를 서로 다른 관점에서 사용
```

#### 데이터 생성 경로

```
미지급금: 발주 확정 시 자동 생성 / 수기 입력 가능
지급 처리: 수동 체크 기반 (초기)
매출:     초기 수기 입력 기반
```

---

#### 3개 화면 상세

**1. 지급 예정 (핵심 실행 화면)**

목적: 지금 처리해야 할 돈을 바로 처리
```
컬럼: 거래처명 / 금액 / due_date / 상태(planned/paid)
정렬: due_date 오름차순 (임박 순)
필터: 3일 이내 / 이번 주 / 이번 달
행동: [지금 처리하기]
```

지급 전 문구: "내일 35만원 나가요 → 같이 정리해볼까요?"

**2. 거래처 미지급금 (관계 관리)**

목적: 어디에 얼마나 쌓였는지 파악
```
컬럼: 거래처명 / 총 미지급금 / 가장 오래된 미지급일
행동: 클릭 → 해당 거래처 상세 지급 내역
```

**3. 자금 흐름 (판단 보조)**

목적: 생존 상태 판단

```
MVP (초기):
- 이번 주 나갈 돈
- 이번 달 나갈 돈
- 표현: "이번 주 약 35만원 나갈 예정이에요"
- 잔액 없이 지급 예정 금액만 표시

중간:
- 지급 패턴 기반 예측
- "평소보다 이번 주 지출이 많아요"

고급 (선택 기능):
- accounts 테이블 추가 (잔액 수동 입력 허용)
- "잔액 vs 지급 예정" 비교 활성화
- 상태: 안정(지급 예정 < 잔액 50%) /
        주의(≥ 80%) / 위험(≥ 100%)
```

---

#### 잔액 정책 (단계적 진화)

```
MVP:  잔액 입력 없음 / 온보딩 장벽 제거
중기: 패턴 기반 예측 활성화
```

**핵심 철학**: 정보 제공이 아니라 "잘못된 선택을 부드럽게 교정하는 시스템"

#### 데이터 구조 (통합)

suppliers 테이블 별도 생성 금지.

```sql
relationships (식당-공급자 연결)

```
식당OS 사용 필드:


#### 2개 화면 상세

**1. 거래처 목록 (선택 유도 화면)**

목적: 목록이 아니라 "선택 유도"

```
컬럼:
- 거래처명
- 분류 (핵심 / 주의 / 비교 필요)
- 최근 거래일
- 가격 수준
- 총 거래 금액

행동:
[다시 주문하기]
[비교해보기]
```

**2. 거래처 상세 (판단 근거 화면)**

```
표시:
- 가격 이력 (그래프)
- 납기 이력 (지연 여부)
- 문제 발생 이력
- 결제 조건
- 과거 발주요청 결과

행동:
[이 거래처로 주문]
[조건 비교하기]
[이 거래처 기준으로 발주요청] → 제품/수량/최근구매가 자동 입력
```

---

#### 거래처 분류 기준 (수치 고정)

```
핵심 거래처:
- 최근 3개월 거래 3회 이상
- 납기 지연 없음

주의 거래처:
- 납기 지연 이력 존재
- 또는 가격 +15% 이상

비교 필요:
- 가격 +5% 이상
- 또는 마지막 거래 30일 초과
```

---

#### 가격 신호 체계

```
LEVEL 1 (약한 신호) — +5% ~ +10%
메시지: "이 거래처 가격이 조금 높은 편이에요"
행동: [비교해보기]

LEVEL 2 (중간 신호) — +10% ~ +20%
메시지: "다른 조건 보면 더 좋은 선택이 있을 수 있어요"
행동: [다른 조건 확인하기]

LEVEL 3 (강한 신호) — +20% 이상
메시지: "이 거래처 계속 쓰는 게 맞나요?"
행동: [조건 비교하기] / [그래도 유지하기]
```

---

#### 납기 신호 체계

납기 = 관계/신뢰 신호 (가격과 별도 체계)

**최근 기준**: 최근 거래 N건 기준
```
settings.delivery_signal_window = 5 (기본값)
관리자 전용 설정 / 식당 사용자에게 노출 ❌
이유: 사용자가 기준을 바꾸면 신호 신뢰 붕괴
```

**납기 신호 단계**
```
LEVEL 0 (정상): 지연 없음 → 메시지 없음

LEVEL 1 (약한 신호): 최근 N건 중 1건 지연 (1~2일)
메시지: "최근 납품이 조금 늦은 적이 있어요"
행동: [다른 조건도 확인하기]

LEVEL 2 (주의 신호): 최근 N건 중 2건 지연 / 또는 단일 3일 이상
메시지: "납품이 반복해서 지연되고 있어요"
행동: [다른 조건 비교하기]

LEVEL 3 (강한 신호): 최근 N건 중 3건 이상 지연
메시지: "이 거래처 계속 쓰는 게 맞나요?"
행동: [조건 비교하기] / [그래도 유지하기]
```

**데이터 부족 처리**
```
총 거래 < N건:
- 1건 지연 → LEVEL 1까지만 허용
- LEVEL 2 이상 금지
이유: 데이터 부족 상태에서 과도한 판단 방지
```

**극단 상황 예외 (N건 무관하게 즉시 적용)**
```
단일 납기 지연 ≥ 5일 → 즉시 LEVEL 3
이유: 심각한 문제는 즉시 개입
```

---

#### 가격 + 납기 신호 결합 규칙

```
가격 +15% AND 납기 지연 있음 → 무조건 LEVEL 3
충돌 시: 강한 쪽 우선 (최종 레벨 유지)
```

메시지 분리 (혼합 금지):
```
❌ "가격도 비싸고 납기도 늦어요" (정보 과부하)
⭕ 가격 카드 / 납기 카드 분리 표시
```

---

#### 신호 발동 조건 / 금지

```
발동 조건 (모두 충족 시):
- 가격 +5% 이상
- 최근 거래 2회 이상

발동 금지:
- 핵심 거래처 AND 가격 정상
- 첫 거래 (데이터 없음)
```

---

#### 반복 노출 제한 (늑대 소년 방지)

```
하루 1회 이상 노출 금지
"그래도 유지" 선택 시 → 7일간 동일 메시지 차단
→ relationships.signal_suppressed_until = today + 7
```

---

#### 선택 존중 UX → 데이터 전환

"그래도 유지하기" 선택 시 이유 기록:
```
- 가격
- 납기
- 관계
→ relationships 테이블에 저장
→ 이 데이터가 다음 추천 방식에 영향
```

핵심: 사용자 선택을 데이터로 만든다. 사용자 거부가 데이터 자산이 된다.

#### 핵심 원칙

```
가격은 계산으로 판단한다
납기는 반복으로 판단한다
공정성은 기간이 아니라 경험 횟수에서 나온다
판단 강요 ❌ → 선택 도움 ⭕
```

### 8-7. 알림

**최종 정의**: 알림은 OS의 신경계다 → 잘못 울리면 전체가 무너진다.

**핵심 정의**: 알림은 "보여주는 기능"이 아니라 "행동을 시작시키는 트리거 시스템"이다.

---

#### 역할 분리

```
알림     = 트리거 이벤트 (문제 감지 → 특정 메뉴로 이동 유도)
오늘운영 = 실행 집합 (알림 + 상태 종합한 행동 정리 화면)

알림 생성 → 오늘운영 카드 자동 생성 (중복 없이)
알림 action 실행 → 해당 카드 자동 제거
```

---

#### 우선순위

```
urgent    → 즉시 행동 (긴급)
important → 오늘 내 확인
normal    → 참고 정보
```

---

#### 알림 발생 조건 (전 시스템 연결)

알림은 각 모듈의 트리거 발생 시 자동 생성된다.

```
1. 돈관리
   조건: due_date - today ≤ 3일
   priority: urgent
   action_link: /money

2. 가격 신호 (LEVEL 1~3)
   priority: important
   action_link: /relationships

3. 납기 신호 (LEVEL 1~3)
   priority: important
   action_link: /relationships

4. 입찰 결과 도착 (rfq_result)
   priority: urgent
   action_link: /orders/results

5. bidding 24시간 경과 (rfq_waiting)
   priority: normal
   action_link: /orders
```

---

#### source_type 정의 (알림 타입 = 행동 시점 정의)

```
'price'       → 가격 신호
'delivery'    → 납기 신호
'payment'     → 지급 임박
'rfq_result'  → 입찰 결과 도착 (지금 결정해야 함)
'rfq_waiting' → bidding 대기 상태 (아직 기다리는 상태)
```

같은 RFQ라도 결과가 나오면 "행동", 기다리는 상태는 "대기". 이 둘은 완전히 다른 상태다.

**rfq_result (입찰 결과 도착)**
```
조건: 새로운 bid 도착 / 또는 bidding 종료 + bid 존재
priority: urgent
만료: 공급자 선택 완료(ordered) / 또는 사용자 결과 확인
```

**rfq_waiting (대기 상태)**
```
조건: bidding 24시간 경과 + 아직 선택 없음
priority: normal
만료: 새로운 bid 도착 → rfq_result로 전환 / 또는 expired
```

---

#### 중복 방지 정책

```
동일 type + source_id → 하루 1건만 생성
dedup_key = type + source_id + date

사용자 "무시/유지" 선택 시 → 7일간 동일 알림 차단
핵심: alert fatigue 방지
```

---

#### 만료 정책

조건 해소 시 자동 만료:
```
payments.status = 'paid'     → payment 알림 is_expired = true
가격 정상화                   → price 알림 is_expired = true
rfq 선택 완료(ordered)        → rfq_result 알림 is_expired = true
새 bid 도착                   → rfq_waiting 알림 is_expired = true
만료된 알림 → UI에서 자동 제거
```

---

#### notifications 테이블

```sql
notifications
- id
- restaurant_tenant_id
- type
- priority ('urgent' / 'important' / 'normal')
- message
- action_link
- is_read
- created_at
- expires_at
- is_expired
- source_type ('price' / 'delivery' / 'payment' / 'rfq_result' / 'rfq_waiting')
- source_id       (entity id — 어떤 거래처/발주의 알림인지)
- dedup_key       (중복 방지용)
```

```
상황(숫자 기반) → 영향(손해/절약) → 행동 버튼

예)

→ 약 2,000원 아낄 수 있어요
→ [견적 받아보기]"

→ [미리 준비하기]"
```

```
⭕ "지금 확인하면 좋아요"
```

### 8-8. 설정 (식당 기초 데이터)

**최종 정의**: 설정은 "입력하는 메뉴"가 아니라 "사용하면서 자동으로 쌓이는 데이터 시스템"이다.

**핵심**: 사용자가 몰라도 결과를 만들어주는 시스템

---

#### settings 레벨 구조

```
Level 1 (시스템 설정 — UI 노출 ❌)
- delivery_signal_window = 5
- price_signal_thresholds (LEVEL 1~3 기준)
- rfq_repeat_limit = 3
- signal_suppression_days = 7
→ 관리자 / 내부 로직 전용

Level 2 (사용자 설정 — UI 노출 ⭕)
- 결제 조건 기본값 (즉시결제 / 외상 / net30)
- 납기 희망 시간대 (오전 / 오후 / 특정 시간)
- 발주 기본 지역 (자동 설정 + 수정 가능)
- 선호 공급자 목록 (반복 거래 기반 자동 채움)
```

사용자는 "행동 설정"만 건드린다. 판단 기준은 시스템이 가진다.

---

#### 설정 입력 흐름 (행동에서 자연 발생)

설정은 "메뉴에서 입력"이 아니라 "행동 흐름에서 자연 발생"한다.

```
Step 1 (온보딩 — 30초)
- 지역
- 식자재 1개
- 현재 구매가

Step 2 (발주요청 이후)
- 거래 조건 입력 유도

Step 3 (돈관리 진입 시)
- 고정비 입력 유도

Step 4 (선택적)
- 메뉴 / 가격 입력
```

입력은 요청하지 않는다 → 필요할 때 자연 발생

---

#### 식자재 입력

**입력 방식**
```
수기 입력
사진 인식 기반 (촬영 → 자동 인식 → 확인 후 저장)
핵심: "자동 + 검증"
```

**사진 업로드 처리 범위**
```
MVP (즉시 구현 — OCR 기반):
추출 대상: 제품명 / 용량 (1kg, 500g) / 가격 (있을 경우)
→ 사용자 확인 후 저장

중기 (AI 확장):
- 브랜드 자동 인식
- 제조사 분류
- 카테고리 추정 (고기 / 채소 / 조미료 등)

MVP = "읽기" / AI 단계 = "이해"
```

---

#### 고정비 입력

```
1원 단위 정확성 요구하지 않음 / 현실성 중심
공과금 등 변동비용은 넉넉하게 입력하도록 안내
입력 부담이 생기면 입력 자체가 무너진다
```

---

#### 테이블 수 입력

```
2인 / 4인 등 단위별 입력
총 수용 인원 자동 계산
단순 개수가 아니라 "구조 데이터"로 활용
```

---

#### 메뉴 입력

```
수기 / 메뉴판 사진 인식
대표 메뉴 최대 3개 선택 (이후 제안/분석 기준)
원가 = "정확한 값"이 아니라 "의사결정을 위한 값" (±3% 오차 허용)
```

**원가 입력 전략 (3단계)**
```
LEVEL 1 (수동): 사용자가 직접 재료/수량 입력
LEVEL 2 (보조): "대략적인 양만 입력해도 충분합니다 ±10~20% 오차 OK"
LEVEL 3 (AI 추정): 사용자 입력 없을 경우 AI가 기본값 제공
  예) 제육볶음 → 돼지고기 150g / 양파 50g / 기타 재료 추정
  출력: "예상 원가 약 4,200원 (±15% 오차)"
```

UX 원칙:
```
❌ "정확히 입력하세요"
⭕ "대략 입력 OK"
⭕ "자동으로 계산해드릴게요"
```

AI 추정 시 반드시 표시: "이 값은 예상치입니다 (±15% 오차)" → 클릭 시 상세 공개

---

#### AI 원가 추정 구조

**데이터 소스 (MVP)**
```
GPT API 기반 레시피 추정
입력: 메뉴명
출력: 1인분 기준 재료 구성 + 재료별 예상 수량

예)
입력: "김치찌개"
출력: 돼지고기 150g / 김치 200g / 두부 100g / 기타
```

**단계적 진화**
```
LEVEL 1 (MVP): GPT 기반 추정
LEVEL 2:       식식이OS 내부 데이터 반영 시작
LEVEL 3:       자체 데이터 기반 AI 모델 (GPT 보조)
```

핵심: 외부 AI → 내부 데이터로 전환

**캐싱 구조 (비용 최적화)**
```
menu_cost_cache 테이블 (관리자OS 관리)
- menu_name
- estimated_ingredients (JSON)
- estimated_cost
- source ('gpt' / 'internal')
- confidence_level (%)
- updated_at

동작:
1. 메뉴명 입력
2. 캐시 조회 → 있으면 즉시 반환
3. 없으면 GPT API 호출 → 캐시 저장
4. 내부 데이터 충분 시 source = 'internal'로 전환
```

구현 상세: CONTEXT.md에서 확정

**내부 데이터 학습 대상**
```
메뉴 가격 / 메뉴 원가 / 식자재 구성
거래 가격 / 공급자 데이터
→ 전부 학습 대상
```

학습 목적:
```
메뉴별 평균 원가
업종별 원가 구조
지역별 가격 차이
표준 레시피 패턴
```

#### 관리자OS 연결

```
관리자OS에서 확인:
- 메뉴별 평균 원가
- 가격 대비 마진 구조
- 업종별 비교 데이터
- 식당별 효율 분석

예)
"김치찌개 평균 원가 4,200원
 평균 판매가 9,000원
 평균 마진율 53%"
```

#### 데이터 테이블

```sql
ingredients (식자재)
- id
- restaurant_tenant_id
- name
- category
- current_price (nullable)
※ supplier_name 저장 금지
※ 공급자 연결은 relationships / rfq / orders 통해 처리

menus (메뉴)
- id / restaurant_tenant_id / name / price / is_representative

menu_ingredients (메뉴-식자재 연결)

fixed_costs (고정비)

menu_cost_cache (AI 추정 캐시)
```

```
식식이OS는 사장님 데이터를 학습해서 더 정확한 답을 주는 시스템이다.
식식이OS는 사장님이 모르는 원가를 대신 계산해주는 시스템이다.
```

금지:
```
설정 먼저 강제 ❌
빈 화면 입력 유도 ❌
공급자 텍스트 저장 ❌
초기부터 완벽한 데이터 요구 ❌
```

## 9. 시스템 구조

**한 줄 정의**: 이 구조는 식당OS / 공급자OS / 관리자OS가 단일 DB 위에서 어떻게 격리되고, 연결되고, 통제되는지를 정의하는 플랫폼 전체 아키텍처 기준이다.

---

### 공통 데이터 모델 (Single Source of Truth)

이 섹션에 정의된 테이블은 플랫폼 전체의 단일 소스다.
모든 섹션은 이 정의를 따른다. 각 섹션에서 재정의하지 않는다.

---

#### payments 테이블 (최종 통합 정의)

```sql
payments
- id
- buyer_tenant_id        -- 결제 주체 (식당)
- seller_tenant_id       -- 수취 주체 (공급자)
- direction              -- 'inbound' (공급자 입장) / 'outbound' (식당 입장)
- status                 -- 'pending' / 'confirmed' / 'reversed'
- amount
- type                   -- 'order' / 'settlement' / 'credit' / 'adjustment'
- payment_method         -- 무통장 / 현금 / 카드 / 플랫폼 / 기타
- due_date               -- 결제 예정일
- reference_id           -- 연관 문서 ID (order_id / rfq_id 등, nullable)
- memo
- created_at
```

**조회 기준**
```
식당OS   → direction = 'outbound' (나가는 돈)
공급자OS → direction = 'inbound'  (들어오는 돈)
관리자OS → 전체 조회 가능 (tenant_id = nullable)
```

**상태 정의**
```
pending   → 결제 예정 / 대기
confirmed → 결제 완료
reversed  → 취소 / 롤백
```

**type 정의**
```
order      → 발주/거래 기반 결제
settlement → 플랫폼 정산
credit     → 선지급 / 유예 결제
adjustment → 조정 / 차액
```

물리 삭제 금지. 취소는 반드시 reversed 처리.

---

#### relationships 테이블 (최종 통합 정의)

```sql
relationships
- id
- restaurant_tenant_id   -- 식당 (buyer)
- supplier_tenant_id     -- 공급자 (seller)
- trust_score            -- 플랫폼 전체 신뢰도 점수
- relationship_status    -- 'active' / 'inactive' / 'cooldown'
- rating                 -- 식당이 공급자를 평가한 점수
- memo                   -- 식당 전용 메모
- last_signal_at         -- 마지막 신호 발생 시각
- signal_suppressed_until -- 신호 차단 만료일
- cooldown_until         -- 쿨다운 만료일 (신뢰도 제한 해제 후)
- created_at
```

**사용 기준**
```
식당OS   → 거래처 선택 / 신호 체계 / 거래처 분류 기준
공급자OS → 거래처 연결 관계 확인
관리자OS → 전체 신뢰도 네트워크 관제
```

**relationship_status 정의**
```
active   → 정상 거래 관계
inactive → 비활성 (거래 없음)
cooldown → 신뢰도 회복 검증 중
```

같은 공급자 데이터를 중복 저장하지 않는다.
공급자 기본 정보는 tenants(role='supplier')에서 참조한다.

---

#### 전체 구조

```
[식당OS]          [공급자OS]         [관리자OS]
  buyer              seller            admin
    └──────────────────┴──────────────────┘
                       │
              단일 Supabase DB
              tenant_id 기반 격리
                       │
         ┌─────────────┴─────────────┐
         │                           │
   트랜잭션 데이터              관리자 제어 레이어
 (orders / payments 등)    (정책 / 관제 / 정산 / 학습)
```

관리자OS는 DB 위에서 "조회"가 아니라 "통제"를 수행한다.

---

#### 관리자OS 역할 (명시)

관리자OS는 모든 tenant 데이터를 기반으로:

```
정책 생성 및 변경
거래 흐름 자동 개입
신뢰도 기반 참여자 통제
정산 및 수익 확정
데이터 학습 및 인텔리전스 생성
```

관리자OS = DB 위의 "제어 레이어"

---

#### 핵심 테이블 구조

모든 트랜잭션은 이 4개 축으로 흐른다.

```
rfq_requests (발주요청)
rfq_bids     (입찰)
orders       (buyer ↔ seller)
payments     (payer ↔ payee)
```

---

#### 데이터 경계

```
식당 전용:         menus / ingredients / fixed_costs
공급자 전용:       원가 / 마진 / 타 거래처 정보
발주요청 기반 공유: rfq_requests / rfq_bids
공통:             orders / payments (direction으로 역할 분기)
```

공유는 "거래를 통해서만" 발생한다.

---

#### tenant_id 격리 원칙

이 시스템의 가장 중요한 보안 기준이다.

**기본 원칙**
```
모든 데이터는 tenant_id로 분리된다
모든 쿼리는 tenant_id를 반드시 포함해야 한다
tenant 간 직접 접근은 금지한다
```

**관리자 예외**
```
관리자OS만 tenant_id = nullable 접근 가능
단, 모든 조회/개입은 admin_logs 기록 필수
```

**관계 기반 접근**
```
거래 관계가 있는 경우에만 제한적 공유 허용
예: rfq / orders 기반 연결
```

---

#### 이벤트 기반 연결 구조

식식이OS는 호출 기반이 아니다. 상태 변화 기반 이벤트 시스템이다.

**핵심 원칙**
```
이벤트는 "트랜잭션 결과"로 발생한다
직접 API 호출 금지
상태 변경 → 이벤트 발생
```

**이벤트 예시**

거래 흐름:
```
발주 확정 (selected → ordered) → 공급자OS에 수주 이벤트
지급 처리 (planned → paid)     → 공급자OS에 수금 이벤트
```

관리자OS 개입:
```
신뢰도 기준 미달 → 식당OS / 공급자OS에 제한 정책 이벤트
직거래 감지      → 거래 중단 이벤트
정산 완료        → 공급자OS 수익 확정 이벤트
```

---

#### 이벤트 → 정책 → 실행 흐름

이 구조는 시스템 전체의 작동 원리다.

```
상태 변경 (DB)
→ 이벤트 발생
→ 관리자OS 정책 적용
→ 자동 실행
→ 결과 기록
→ 데이터 학습 센터 재유입
```

이벤트는 단순 알림이 아니다. 정책을 트리거하는 입력값이다. 실행은 자동으로 이루어진다.

이 흐름이 관리자OS 전체 구조(10-2 데이터 흐름)와 연결된다.

---

#### 구현 방식 위임

이벤트 전달 및 실행 구조의 구현 방식은 아래 중 하나로 구성할 수 있다:

```
Supabase Realtime
Webhook
DB Trigger
```

구현 방식은 이 문서에서 결정하지 않는다. **CONTEXT.md에서 최종 확정한다.**

```
PRODUCT.md  → "무엇을 할 것인가" 정의
CONTEXT.md  → "어떻게 구현할 것인가" 정의
```

역할 분리를 통해 개발 혼선을 방지한다.

---

#### 절대 금지 원칙

```
OS 간 직접 API 호출 금지 ❌
tenant_id 없는 쿼리 금지 ❌
관리자 개입 로그 없는 처리 금지 ❌
```

---

#### 핵심 원칙

1. 구조는 여기서 정의하고 구현은 분리한다
2. 흐름을 이해하면 구현은 선택 가능하다
3. 구현을 먼저 결정하면 구조가 깨진다

---

**최종 선언**

이 시스템은 "여러 앱이 연결된 구조"가 아니라
단일 DB 위에서 데이터, 정책, 실행이 하나로 작동하는 "통합 운영 시스템"이다.

## 10. 관리자OS 기능 상세

### 10-1. 정의

**한 줄 정의**: 관리자OS는 플랫폼 전체의 행동 데이터를 학습한 AI를 기반으로 스스로 판단하고 정책을 생성·실행하는 중앙 제어 시스템이다.

관리자OS는 보는 곳이 아니다. 데이터 → 판단 → 정책 → 자동화로 이어지는 구조를 만드는 시스템이다.

---

#### [철학]

- 관리자가 판단하는 것이 아니라 시스템이 판단한다
- 관리자는 예외만 처리한다
- 모든 돈은 플랫폼을 통과한다 — 직거래 절대 금지
- 코드 없이 정책을 바꿀 수 있어야 한다
- 모든 관리자 행동은 로그로 기록된다
- 관리자OS의 경쟁력은 UI가 아니라 데이터와 AI 학습에 있다

---

#### AI 학습 원칙

관리자OS는 식당OS와 공급자OS에서 발생하는 모든 데이터를 수집하고 학습한다.

```
공급자OS: 상품 / 가격 / 판매 데이터
식당OS:   구매 / 행동 / 수요 데이터
```

이 데이터를 기반으로:
- 시장 가격 인텔리전스
- 수요 예측
- 공급자/식당 행동 패턴 분석

을 생성한다. 이 인텔리전스는 정책 생성과 자동화의 핵심 입력값이 된다.

관리자OS는 단순 제어 시스템이 아니라 플랫폼 전체 데이터를 학습해 시장 인텔리전스를 생성하는 시스템이다.

단계별 진화 전략은 **10-6 데이터 학습 센터**에서 정의한다.

**플랫폼 ERP(디닷페이스) 보강**: 관리자OS는 위 학습·판단 축에 더해, **Storefront 플랫폼 주문**·**플랫폼 정산·수수료**·**공급 allocation**·**PG·무통장 등 결제 운영**을 한 축으로 묶는 **플랫폼 운영센터 + ERP** 역할을 지향한다. 공급자OS의 수동 입력형 주문 ERP와 혼동하지 않는다.

---

#### [실행 규칙]

**관리자 권한**
```
tenant_id = nullable (모든 tenant 데이터 접근 가능)
모든 거래 조회 / 개입 가능
모든 정책 변경 가능
모든 관리자 행동 → admin_logs 기록 필수
```

**직거래 차단**
```
식당 ↔ 공급자 직접 결제 절대 금지
모든 결제는 플랫폼 정산 시스템 통과
위반 시 자동 감지 + 관리자 알림
```

---

#### 운영 원칙 (CRUD 금지)

관리자OS에서 CRUD(목록/등록/수정/삭제) 중심 화면을 만드는 것을 금지한다.

모든 화면은 아래 흐름 중 하나로 작동해야 한다.

```
데이터 → 판단 → 정책 → 자동화

예:
데이터: "공급자 A 납기 준수율 55%"
판단:   "신뢰도 60 이하"
정책:   "입찰 참여 제한 자동 실행"
자동화: "경고 메시지 자동 발송"
```

관리자가 직접 제한을 거는 것이 아니라, 시스템이 먼저 실행하고 관리자는 예외를 처리한다.

---

### 10-2. 메뉴 구조

관리자OS의 메뉴는 화면 분류가 아니다. 각 메뉴는 플랫폼의 특정 역할을 담당하는 시스템이다.
메뉴는 독립 기능이 아니라 데이터 흐름으로 연결된 하나의 제어 시스템으로 작동한다.

```
관리자OS
ㄴ 중앙 대시보드        → 플랫폼 전체 상태 3초 파악 + 즉시 행동 결정
ㄴ 거래 흐름 관제       → 발주→낙찰→주문→정산 전 과정 추적 + 이상 자동 개입
ㄴ 참여자/관계 네트워크 → 신뢰도 기반 참여자 통제 + 관계 기반 정책 실행
ㄴ 데이터 학습 센터     → 플랫폼 전체 데이터를 학습해 인텔리전스를 생성하고
                          정책 엔진에 입력값을 제공하는 자율 진화 엔진
ㄴ 판단/분석 엔진       → 시스템이 먼저 위험과 기회를 판단하고 정책 트리거 생성
ㄴ 성장/영업 엔진       → 판단/분석 엔진 결과를 기반으로
                          이탈 위험 / 휴면 참여자 대상 자동 영업 실행
ㄴ 수익/정산 통제       → 모든 돈 흐름 통제 + 수수료 + 정산 + 직거래 차단
ㄴ 정책/실험 콘솔       → 코드 없이 정책 생성 / 수정 / 실험 (A/B 테스트 포함)
```

---

#### 메뉴 간 데이터 흐름 구조

관리자OS는 아래 흐름으로 작동한다:

```
데이터 학습 센터 (수집/학습)
       ↓
판단/분석 엔진 (판단)
       ↓
정책/실험 콘솔 (정책 생성)
       ↓
참여자/관계 네트워크 + 거래 흐름 관제 (자동 실행)
       ↓
수익/정산 통제 (결과 발생)
       ↓
중앙 대시보드 (현황 및 의사결정)
       ↓
결과 데이터 → 다시 데이터 학습 센터로 유입 (재학습)
```

---

#### 핵심 원칙

- 메뉴는 기능이 아니라 역할이다
- 메뉴는 독립이 아니라 흐름으로 연결된다
- 모든 메뉴는 정책 실행 시스템의 일부다
- UI는 결과일 뿐, 본질은 데이터 흐름이다
- 연결되지 않은 기능은 존재할 수 없다

---

**최종 선언**

관리자OS의 메뉴 구조는 "화면 구성"이 아니라
플랫폼을 통제하는 "역할 기반 제어 시스템 구조"다.

관리자OS의 모든 문서는 독립 기능 설명이 아니라
하나의 흐름 안에서 각 역할을 정의하는 시스템 문서다.

---

### 10-3. 중앙 대시보드

**흐름 위치**: 이 메뉴는 수익/정산 통제에서 확정된 결과와 판단/분석 엔진의 위험 신호를 받아 플랫폼 전체 상태를 3초 안에 파악하고 즉시 행동을 실행하며 결과 데이터를 다시 데이터 학습 센터로 유입시킨다.

**핵심 정의**: 중앙 대시보드는 "현황판"이 아니라 플랫폼을 실시간으로 통제하는 "실행 인터페이스"다.

---

#### 핵심 원칙

```
대시보드는 보는 곳이 아니라 실행하는 곳이다
모든 정보는 행동으로 연결되어야 한다
판단은 이미 끝났고, 대시보드는 실행만 담당한다
```

---

#### 블록 구조 (우선순위 기반)

**[1순위] 즉시 개입 블록 (Critical Action)**

목표: 지금 당장 개입해야 하는 문제

```
직거래 시도 감지 건수   → [즉시 차단]
신뢰도 급락 참여자      → [정책 즉시 적용]
이상 거래 감지          → [거래 중단 / 검토]
미정산 금액 상위 5개    → [즉시 정산 실행]
```

특징: 자동 감지된 문제만 표시 / 모든 항목에 즉시 실행 버튼 필수

**[2순위] 오늘 처리 블록 (Today Action)**

목표: 오늘 안에 처리해야 하는 작업

```
연체 30일 이상 거래처   → [수금 요청 / 제한 정책 적용]
미정산 잔액             → [일괄 정산 실행]
신뢰도 경고 대상        → [정책 적용 / 관찰 설정]
```

특징: 긴급은 아니지만 반드시 처리 필요 / 일괄 실행 버튼 포함

**[3순위] 운영 상태 블록 (Monitoring)**

목표: 전체 상태 파악

```
오늘 거래 건수 / 거래 총액
활성 식당 수 / 활성 공급자 수
오늘 발주요청 수 / 낙찰 수
플랫폼 수익
```

특징: 정보 제공 목적 / 행동 버튼 없음 / drill-down만 허용

**[4순위] AI 학습 상태 블록 (Learning Status)**

목표: 시스템 진화 상태 파악

```
현재 학습 단계: MVP / 중기 / 후기
다음 단계 전환 달성률 (예: orders 423 / 500 = 85%)
정책 자동화율 (자동 실행 비율)
관리자 개입률 (수동 개입 비율)
```

행동 버튼:
```
[학습 상태 상세 보기]
[정책 튜닝 이동]
```

특징: 단순 데이터 금지 / 반드시 "진화 상태" 중심

---

#### Action Queue (실행 관리 시스템)

Action Queue는 단순 리스트가 아니라 "실행 관리 시스템"이다.
플랫폼 운영을 움직이는 핵심 실행 큐다.

**역할**
```
판단/분석 엔진이 생성한 "지금 해야 할 행동 목록"

예)
1. 공급자 A 납기 위험 증가 → [대체 공급자 추천 실행]
2. 식당 B 결제 지연 반복  → [후불 제한 정책 적용]
3. 특정 품목 가격 이상    → [가격 정책 조정 실행]
```

클릭 시 즉시 실행 또는 정책/실험 콘솔로 이동

---

**생성 규칙 (Creation)**

```
판단/분석 엔진이 자동 생성
관리자 수동 생성 불가
모든 항목은 "판단 결과 → 실행 필요 상태"에서만 생성
```

---

**상태 구조 (State Machine)**

```
pending     → 대기 (생성 직후)
in_progress → 처리 중 ([정책 콘솔 이동] 클릭 시)
completed   → 완료 ([즉시 실행] 클릭 또는 조건 해소 시)
expired     → 만료 (72시간 이상 미처리)
```

---

**소멸 조건 (Resolution)**

```
[즉시 실행] 클릭      → completed → 큐에서 제거
[정책 콘솔 이동] 클릭 → in_progress (유지)
조건 해소 (신뢰도 회복 등) → 자동 completed → 제거
```

---

**만료 및 에스컬레이션 (Expiration)**

```
72시간 이상 미처리:
→ expired 상태 전환
→ 심각도 상승 (Critical로 승격)
→ 관리자 알림 발송

7일 이상 미처리:
→ 상위 관리자 알림
→ 시스템 개입 권고
```

---

**Action Queue 핵심 원칙**

```
Action Queue는 쌓이는 시스템이 아니라 소모되는 시스템이다
모든 항목은 생성부터 소멸까지 생명주기를 가진다
처리되지 않는 항목은 위험으로 간주된다
판단은 시스템이 하고, 실행은 관리자 또는 자동화가 한다
```

---

#### 최종 구조

```
대시보드 = 상태(What) + 행동(Action) + 우선순위(Priority) + 실행 큐(Queue)
```

---

### 10-4. 거래 흐름 관제

**흐름 위치**: 이 메뉴는 정책/실험 콘솔에서 생성된 정책을 받아 거래 흐름(발주→낙찰→주문→납품→정산)에 자동 적용하고 결과를 수익/정산 통제로 전달한다.

**핵심 정의**: 거래 흐름 관제는 "거래를 보는 시스템"이 아니라 거래를 실시간으로 통제하는 "자동 개입 시스템"이다.

관리자는 거래를 감시하지 않는다. 시스템이 먼저 개입하고, 관리자는 예외만 처리한다.

---

#### 핵심 구조

```
이상 감지 → 자동 개입 (Level 1~3) → Action Queue 생성 → 관리자 예외 처리
         → 결과 → 데이터 학습 센터 재유입
```

---

#### 거래 흐름 7단계

```
RFQ 생성 → 입찰 진행 → 낙찰 → 주문 확정 → 납품 완료 → 정산 대기 → 정산 완료
```

---

#### 단계별 정상 체류 시간 기준

모든 기준은 정책/실험 콘솔에서 수정 가능하다. 하드코딩 금지.

```
RFQ 생성 → 입찰 진행:  24시간 내 첫 입찰 없으면 플래그
입찰 진행 → 낙찰:      48시간 내 선택 없으면 플래그
낙찰 → 주문 확정:      6시간 내 확정 없으면 플래그
주문 확정 → 납품 완료: 납기일 + 24시간 초과 시 플래그
납품 완료 → 정산:      30일 초과 시 플래그
```

---

#### 자동 개입 레벨 (Level-based Intervention)

**Level 1 — 자동 알림**
```
사용자에게 알림 발송 + 행동 유도
예) 낙찰 후 주문 미확정 → 식당 알림 발송
```

**Level 2 — 제한/유도**
```
행동 제한 또는 자동 유도 실행
예) 신뢰도 낮은 공급자 → 입찰 제한
    정산 지연 → 자동 독촉 발송
```

**Level 3 — 강제 개입**
```
시스템이 거래 흐름 직접 제어
예) 직거래 시도 → 거래 중단
    장기 미정산 → 자동 정산 보류
```

---

#### Level 매핑 정책화 (핵심)

개입 레벨은 하드코딩되지 않는다. 모든 매핑은 정책/실험 콘솔에서 관리된다.

**기본 매핑 (변경 가능)**
```
직거래 시도    → Level 3 (기본값)
입찰 없는 RFQ → Level 1 (기본값)
장기 미정산    → Level 2 (기본값)
납기 지연      → Level 2 (기본값)
비정상 금액    → Level 2 (기본값)
```

**정책/실험 콘솔에서 가능한 변경**
```
이상 유형별 Level 변경
특정 조건에서 Level 강화/완화
A/B 테스트 기반 개입 강도 실험
```

**동적 개입 구조**

개입 레벨은 고정값이 아니다. 상황에 따라 동적으로 변경된다.

```
동일 공급자 반복 위반:
Level 1 → Level 2 → Level 3 자동 상승

플랫폼 초기 단계:
전체 Level 완화 (Level 1 중심 운영)

플랫폼 안정화 이후:
Level 2~3 확대 적용
```

핵심 원칙:
```
개입 강도는 코드가 아니라 정책이 결정한다
동일 이상도 상황에 따라 다르게 대응한다
시스템은 점점 더 강하게 개입하도록 진화한다
```

---

#### 이상 감지 → Action Queue 연결

모든 이상 감지는 Action Queue로 자동 연결된다.

**직거래 시도 감지**
```
자동 개입: 거래 일시 중단 (Level 3)
Action Queue 생성 (Critical)
→ [즉시 차단] / [거래 재개] / [조사 후 처리]
```

**입찰 없는 RFQ**
```
자동 개입: 없음 (Level 1 — 알림만)
Action Queue 생성 (Today)
→ [공급자 풀 확장] / [RFQ 연장] / [RFQ 종료]
```

**장기 미정산**
```
자동 개입: 정산 독촉 발송 (Level 2)
Action Queue 생성
→ [즉시 정산 실행] / [결제 제한 적용]
```

**비정상 금액 거래**
```
자동 개입: 관리자 확인 요청 (Level 2)
→ 해당 품목 평균 대비 ±50% 초과 시
Action Queue 생성 (Today)
→ [거래 승인] / [거래 중단]
```

---

#### 정상 거래 가속 시스템

문제 거래뿐 아니라 정상 거래도 더 빠르게 완결시킨다.

```
낙찰 후 3시간 미확정    → 식당 자동 알림 (Level 1)
납품 완료 후 7일 미정산 → 정산 독촉 자동 발송 (Level 2)
반복 거래 식당          → 자동 공급자 추천
```

---

#### 관리자 개입 원칙

관리자는 자동 개입 이후 예외 상황만 처리한다.

**수동 개입 기능 (예외 전용)**
```
거래 단계 강제 변경
거래 일시 중단 / 재개
정산 수동 처리
```

모든 개입은 admin_logs 기록 필수. 사유 입력 필수.

---

#### 최종 구조

```
거래 흐름 관제 =
자동 감지 → 자동 개입 (Level 1~3) → Action Queue 생성
→ 관리자 예외 처리 → 결과 → 학습 센터 재유입
```

거래 흐름 관제의 개입 시스템은 고정된 로직이 아니라
플랫폼 상태에 따라 진화하는 "동적 정책 시스템"이다.

---

### 10-5. 참여자/관계 네트워크

**흐름 위치**: 이 메뉴는 데이터 학습 센터의 신뢰도 계산 결과를 받아 신뢰도 기반 정책을 생성하고 거래 흐름 관제(Level-based Intervention)로 전달하며 Action Queue를 통해 실행된다.

**핵심 정의**: 참여자/관계 네트워크는 "신뢰도를 보는 시스템"이 아니라 플랫폼 참여자의 행동을 통제하고 진화시키는 시스템이다.

---

#### 핵심 구조 (통합 파이프라인)

```
신뢰도 계산 → 임계값 도달 → Level 결정 (1~3) → 정책 자동 실행
→ Action Queue 생성 → 관리자 예외 처리 → 회복 시스템 → 쿨다운 검증
```

---

#### 신뢰도 점수 구조

신뢰도는 행동 데이터 기반으로 자동 계산된다. 수동 수정 금지.

**공급자 신뢰도**
```
납기 준수율 (%)
클레임 발생 횟수
반복 거래율
입찰 후 미납품 횟수
```

**식당 신뢰도**
```
결제 준수율
발주요청 완결율 (들러리 여부)
플랫폼 활성도
```

**데이터 소스**
```
orders / payments / claims / delivery_logs / bid_participation
```

---

#### 관계 기반 신뢰도 (이중 구조)

신뢰도는 단일 점수가 아니다.

```
플랫폼 전체 신뢰도: B 공급자 = 75점
A 식당 ↔ B 공급자 신뢰도: 90점
C 식당 ↔ B 공급자 신뢰도: 40점
```

같은 공급자라도 식당마다 신뢰도가 다르다.
이 구조가 발주요청 추천 정확도를 결정한다.

---

#### 신뢰도 → Level 매핑 (핵심 통합)

신뢰도는 단순 점수가 아니라 개입 레벨을 결정하는 기준이다.
모든 임계값은 정책/실험 콘솔에서 관리. 하드코딩 금지.

```
settings:
supplier_trust_warning_threshold  = 70
supplier_trust_restrict_threshold = 60
supplier_trust_block_threshold    = 50
restaurant_trust_warning_threshold  = 60
restaurant_trust_restrict_threshold = 50
restaurant_trust_block_threshold    = 40
```

**공급자**
```
70 이하 → Level 1 (자동 경고 발송)
60 이하 → Level 2 (입찰 제한 / 노출 감소)
50 이하 → Level 3 (입찰 완전 차단 + Action Queue 생성 Critical)
```

**식당**
```
60 이하 → Level 1 (자동 경고 발송)
50 이하 → Level 2 (후불 결제 제한 → 선결제 전환)
40 이하 → Level 3 (RFQ 생성 제한 + Action Queue 생성 Critical)
```

---

#### Action Queue 연결

Level 3 진입 시 반드시 Action Queue 생성.

```
공급자 신뢰도 48 → 입찰 차단 자동 실행 → Action Queue 생성 (Critical)
→ [제한 유지] / [조건부 해제] / [정책 수정]

식당 신뢰도 38 → RFQ 제한 자동 실행 → Action Queue 생성 (Critical)
→ [제한 유지] / [조건부 해제] / [정책 수정]
```

---

#### 신뢰도 회복 시스템

신뢰도는 하락만 하는 시스템이 아니다. 회복 경로가 반드시 존재한다.

**공급자 회복**
```
납기 준수 3회 연속   → +5점
클레임 없는 거래 5회 → +3점
```

**식당 회복**
```
결제 정상 처리 3회 연속   → +5점
발주요청 완결 3회 연속    → +3점
```

**자동 해제 조건**
```
제한 임계값 +5점 초과 시 → 정책 자동 해제
해제 후 쿨다운 시스템 자동 진입
```

---

#### 쿨다운 시스템 (Cooldown)

신뢰도 회복은 즉시 해제되는 구조가 아니다. 회복 이후 안정성을 검증한다.

**기본 설정 (정책/실험 콘솔에서 관리)**
```
settings:
trust_cooldown_days              = 14  (쿨다운 기간)
trust_escalation_threshold       = 2   (가중 제재 발동 위반 횟수)
```

**쿨다운 기간 동작**
```
쿨다운 기간 동안:
정상 행동 지속        → 상태 유지 → 14일 후 정상 해제
신뢰도 재하락 발생 시 → 즉시 재제한 + 가중 제재 적용
```

**가중 제재 (Escalation)**
```
쿨다운 기간 내 재하락:
기존 Level 2 → 재하락 시 Level 3 즉시 적용

반복 위반 횟수 누적:
위반 2회 이상 → 제재 강도 자동 증가
위반 3회 이상 → 관리자 수동 승인 없이 해제 불가
```

---

#### 통보 원칙

모든 정책 실행은 사전 통보 + 사유 + 회복 조건 명시 필수.

```
정책 실행 통보:
"납기 준수율 하락으로 입찰 참여가 제한됩니다"

회복 조건 명시 필수:
"납기 준수 3회 시 제한이 해제됩니다"
"해제 후 14일 쿨다운 기간이 적용됩니다"
```

통보 없이 제한만 걸리면 참여자 이탈 원인이 된다.

---

#### 참여자 상태 구조 (CRUD 제거)

참여자는 목록이 아니라 상태 그룹으로 관리된다.

**자동 분류**
```
위험 그룹  (Level 3)     → 즉시 조치 필요
주의 그룹  (Level 2)     → 오늘 처리 필요
쿨다운 그룹 (회복 검증 중) → 모니터링
정상 그룹  (Level 1 이하)  → 우수 참여자 분석 대상
```

**그룹별 즉시 행동**
```
위험 그룹:
→ [즉시 조치 실행] / [정책 강화] / [관리자 검토]

주의 그룹:
→ [관찰 설정] / [경고 재발송]

쿨다운 그룹:
→ [쿨다운 현황 확인] / [조기 해제 검토 (관리자 승인)]

정상 그룹:
→ [우수 참여자 분석] / [추천 대상 활용]
```

---

#### 핵심 원칙

1. 신뢰도는 점수가 아니라 통제 수단이다
2. 신뢰도는 Level 시스템과 반드시 연결된다
3. 신뢰도는 Action Queue를 통해 실행된다
4. 신뢰도는 회복 가능해야 한다
5. 신뢰도는 쉽게 회복되지 않는다 — 안정성이 검증되어야 한다
6. 반복 위반은 더 강하게 제재한다

---

### 10-6. 데이터 학습 센터

**흐름 위치**: 이 메뉴는 플랫폼 전체 데이터를 수집하여 학습하고 판단/분석 엔진에 인텔리전스를 제공한다. 중앙 대시보드에서 발생한 결과 데이터도 재유입되어 지속적으로 재학습한다.

**한 줄 정의**: 데이터 학습 센터는 분석 도구가 아니라 플랫폼을 스스로 진화시키는 엔진이다.

모든 학습 결과는 반드시 정책으로 연결된다.
```
데이터 → 학습 → 판단 → 정책 → 자동화 → 결과 → 재학습
                                              ↓
                                    정책 성능 평가
                                              ↓
                          자동 조정(약화/확대) + 수동 승인(중단)
```

이 연결이 없는 분석은 금지한다.

---

#### 역할

```
식당OS / 공급자OS 데이터 통합 수집
AI 학습 기반 인텔리전스 생성
판단/분석 엔진 + 정책/실험 콘솔에 입력값 제공
```

수집 데이터:
```
공급자OS: 상품 / 가격 / 판매 / 납기 / 입찰 데이터
식당OS:   구매 / 행동 / 수요 / 발주 / 결제 데이터
```

---

#### 피드백 루프 (Self-Learning Loop)

정책 실행 결과는 반드시 수집되어 학습에 반영된다.

수집 대상:
```
정책 실행 후 거래 성공률 변화
정책으로 인한 거래 감소/증가
관리자 오버라이드 발생 여부
사용자 이탈/불만 발생 여부
```

예:
```
입찰 제한 정책 실행
→ 거래량 감소 / 공급자 이탈 감지
→ 정책 강도 자동 약화
→ 재학습 반영
```

이 구조가 있어야 "진화"가 된다.

---

#### 피드백 루프 시간 기준 (Feedback Timing Control)

정책 실행 결과는 즉시 반영하지 않는다. 노이즈로 인한 정책 흔들림을 방지하기 위함이다.

**기본 원칙**
```
정책 평가 최소 기간: 7일
단기 변동 (3일 이내): 평가에서 제외
충분한 데이터 축적 후 재학습 수행
```

**예외 (즉시 반영)**
```
사용자 이탈 급증
클레임 / 불만 급증
결제 실패율 급증
```
안정성보다 리스크가 더 큰 경우 즉시 개입한다.

---

#### 정책 성능 평가 (Policy Evaluation)

모든 정책은 성능 지표를 가진다. 정책도 학습 대상이다.

**정책 KPI**
```
거래 성공률 변화
플랫폼 수익 영향
사용자 이탈률
관리자 개입률 (오버라이드 비율)
```

**자동 평가**
```
성능 기준 미달 → 정책 자동 약화 (자동 허용)
성능 우수      → 정책 자동 확대 적용 (자동 허용)
성능 심각 저하 → 관리자 알림 즉시 발생
정책 완전 중단 → 관리자 승인 필수
```

---

#### 정책 자동 중단 안전장치 (Policy Safety Guard)

정책은 자동으로 조정되지만 "완전 중단"은 자동으로 실행되지 않는다.

```
약화 / 확대:  자동 허용
완전 중단:   관리자 승인 필수 (자동 불가)
```

자동 시스템의 오판으로 인한 치명적 오류를 방지한다.

---

#### 데이터 네트워크 효과 (Network Intelligence)

데이터 학습 센터는 단순 분석이 아니라 플랫폼 전체 데이터를 연결하여 네트워크 인텔리전스를 생성한다.

```
A 식당의 구매 패턴 → 유사 식당 그룹 생성
B 공급자의 납기 패턴 → 리스크 그룹 분류
지역/업종별 수요 패턴 클러스터링
```

활용:
```
유사 식당 기반 추천 고도화
위험 공급자 사전 차단
지역별 가격 정책 차별화
```

플랫폼을 떠나면 이 연결 데이터가 사라진다.
데이터 학습 센터가 식식이OS의 진짜 해자다.

#### 단계적 진화 구조

---

**[MVP 단계] 규칙 기반 자동 판단**

목표: 데이터 수집 + 즉시 자동 판단 실행

AI 모델 없음. 규칙 기반. 하지만 자동 판단 시스템은 이미 작동한다.

수집 데이터:
```
orders / payments / claims / delivery_logs / bid_participation
```

자동 판단 (임계값 기준):
```
납기 준수율 60% 이하     → 공급자 신뢰도 하락 → 입찰 제한 정책 실행
결제 지연 발생           → 식당 신뢰도 하락   → 후불 결제 제한 정책 실행
발주요청 완결율 40% 이하 → 들러리 의심        → RFQ 생성 제한 검토
```

정책 연결:
```
신뢰도 점수 → 참여자/관계 네트워크 정책 트리거
임계값 기준 → 정책/실험 콘솔에서 수정 가능
```

**MVP → 중기 전환 조건**
```
orders 데이터 누적 500건 이상
신뢰도 점수 계산 참여자 50명 이상
신뢰도 정책 자동 실행 정확도 70% 이상
(관리자 오버라이드 비율 30% 이하)
```

---

**[중기 단계] 통계/패턴 기반 인텔리전스**

목표: 시장 인텔리전스 생성 + 이상 자동 감지

수집 데이터 확장:
```
품목별 시장 가격 분포
공급자 입찰 가격 패턴
식당별 발주 주기 / 품목 변화
```

생성 인텔리전스:
```
시장 가격 인텔리전스
→ 품목별 평균 / 표준편차 계산
→ 평균 대비 ±30% 초과 → 이상 자동 플래그

공급자 입찰 패턴 분석
→ 과도한 저가 입찰 탐지 (덤핑 감지)
→ 특정 공급자 낙찰 독점 감지

식당 수요 패턴 분석
→ 계절별 / 요일별 발주 패턴
→ 비정상 수요 급등 감지
```

정책 연결:
```
가격 이상     → 거래 흐름 관제 자동 플래그
덤핑 감지     → 해당 공급자 입찰 제한 정책 검토 트리거
수요 급등     → 공급자 풀 확장 제안 자동 생성
```

**중기 → 후기 전환 조건**
```
시장 가격 데이터 100개 품목 이상 축적
이상 감지 정확도 80% 이상 (오탐율 20% 이하)
공급자/식당 패턴 식별률 60% 이상
menu_cost_cache source = 'internal' 비율 30% 이상
```

---

**[후기 단계] 예측 기반 AI**

목표: 정책 선제 실행 + 완전 자동화

생성 인텔리전스:
```
수요 예측 모델
→ 특정 식당 다음 발주 시점 / 품목 예측
→ 발주 전 최적 공급자 자동 추천

공급자 품질 예측
→ 납기 지연 발생 확률 사전 계산
→ 위험 공급자 사전 경고

가격 최적화
→ 품목별 적정 시장가 자동 산출
→ 공급자 입찰가 이상 여부 실시간 판단
```

정책 연결:
```
수요 예측      → 공급자 사전 알림 (재고 준비 유도)
납기 위험 예측 → 대체 공급자 자동 추천
가격 이상 예측 → 식당에 발주 시점 조정 제안
```

**후기 완성 기준**
```
수요 예측 정확도 75% 이상
납기 위험 예측 정확도 70% 이상
관리자 수동 개입 비율 10% 이하 (90% 자동 실행)
```

#### 현재 학습 현황 (운영 화면)

```
현재 단계 표시 (MVP / 중기 / 후기)
다음 단계 전환 조건 달성률

메뉴 원가 캐시 (menu_cost_cache):
- 총 건수 / source 비율 (gpt vs internal)
- 신뢰도 낮은 항목 목록
- 수동 보정 기능
- 캐시 초기화

신뢰도 점수 분포:
- 공급자 / 식당 신뢰도 현황
- 정책 트리거 발생 건수
- 관리자 오버라이드 건수 (정확도 지표)

정책 성능 현황:
- 활성 정책 목록 / KPI
- 자동 조정 이력
- 관리자 승인 대기 정책
```

---

#### 금지 사항

```
단순 통계 리포트 생성 ❌
관리자용 분석 대시보드 중심 구조 ❌
정책과 연결되지 않는 데이터 처리 ❌
```

---

#### 핵심 원칙

1. 데이터는 수집이 아니라 학습을 위해 존재한다
2. 학습 결과는 반드시 정책으로 연결된다
3. 모든 인텔리전스는 자동화의 입력값이다
4. MVP부터 이미 자동 판단 시스템이 작동한다
5. 시스템은 빠르게 반응하지만 쉽게 흔들리지 않는다
6. 자동화는 강하지만 통제 가능해야 한다
7. 모든 정책은 성능과 안정성을 동시에 고려한다
8. 관리자는 예외만 처리한다 — 판단은 시스템이 한다

### 10-7. 판단/분석 엔진

**흐름 위치**: 이 메뉴는 데이터 학습 센터의 인텔리전스를 입력받아 위험과 기회를 판단하고 정책/실험 콘솔, 거래 흐름 관제, 성장/영업 엔진으로 트리거를 전달한다.

**핵심 정의**: 판단/분석 엔진은 "데이터를 해석하는 시스템"이 아니라 플랫폼의 모든 행동을 결정하는 "중앙 의사결정 엔진"이다.

틀림을 학습하여 스스로 진화하는 시스템이다.

---

#### 핵심 구조

```
입력 (Data Intelligence)
→ 판단 (Decision)
→ 우선순위 분류 (Priority)
→ 출력 (Trigger Routing)
→ 오탐 피드백 (Self-Learning)
```

---

#### 입력 → 판단 변환 구조

데이터 학습 센터 출력이 판단으로 변환되는 방식:

```
신뢰도 점수 변화율  → 이탈 위험 판단
가격 분포 이상      → 시장 가격 이상 판단
수요 패턴 변화      → 기회 / 공급 부족 판단
거래 흐름 지연      → 프로세스 이상 판단
```

---

#### 판단 우선순위 체계

모든 판단은 우선순위를 가진다:

```
Critical → 즉시 개입 필요 → Action Queue (Critical) 자동 생성
High     → 오늘 처리 필요 → Action Queue (Today) 자동 생성
Medium   → 이번 주 대응  → 정책 트리거 전달
Low      → 모니터링      → 데이터 축적
```

---

#### 판단 → 출력 구조 (Trigger Routing)

모든 판단은 반드시 출력 대상을 가진다. 출력 없는 분석은 존재하지 않는다.

**[이상 감지 → 거래 흐름 관제]**

```
직거래 시도:
Priority: Critical
Output: Level 3 트리거 → 거래 흐름 관제 → Action Queue (Critical)
        [즉시 차단] / [조사 후 처리]

장기 미정산:
Priority: High
Output: Level 2 트리거 → 거래 흐름 관제 → Action Queue (Today)
        [즉시 정산 실행] / [결제 제한 적용]

비정상 금액 거래:
Priority: High
Output: Level 2 트리거 → 거래 흐름 관제 → Action Queue (Today)
        [거래 승인] / [거래 중단]
```

**[이탈 위험 → 성장/영업 엔진]**

```
식당 30일 미활동:
Priority: High
Output: 영업 타깃 자동 전달 → 재활성 캠페인 실행

공급자 14일 미입찰:
Priority: High
Output: 영업 타깃 전달 → 입찰 유도 메시지 실행

신뢰도 하락 추세:
Priority: High
Output: 이탈 예측 타깃 → 선제 영업 실행
```

**[수익성 판단 → 정책/실험 콘솔]**

```
공급자 부족 품목:
Priority: Medium
Output: 공급자 모집 정책 트리거 → 노출 정책 조정

낙찰률 하락 품목:
Priority: Medium
Output: 입찰 인센티브 정책 검토 트리거
```

**[기회 판단 → 성장/영업 엔진]**

```
수요 급증 품목:
Priority: Medium
Output: 공급자 확장 타깃 생성 → 사전 입찰 유도

반복 거래 증가 식당:
Priority: Medium
Output: 우수 고객 전환 캠페인 → 맞춤 공급자 추천

신규 지역 활성화:
Priority: Medium
Output: 지역 공급자 모집 → 시장 확장 정책 트리거
```

---

#### 오탐 처리 시스템 (False Positive Handling)

판단/분석 엔진은 항상 정확하지 않다. 오탐을 처리하고 학습하는 구조가 반드시 필요하다.

**오탐 처리 흐름**

관리자가 Action Queue에서 [오탐으로 처리] 클릭 시:

```
1. 해당 판단 결과 즉시 취소
   → 적용된 정책 롤백 (거래 재개 등)
2. Action Queue 항목 completed 처리
3. 오탐 데이터 기록
   → admin_logs + error_logs 저장
4. 데이터 학습 센터로 피드백 자동 전달
   → 재학습 입력값으로 사용
   → 동일 패턴 재발 방지
   → 판단 기준 자동 보정
```

---

#### 오탐 관리 지표

판단/분석 엔진은 자신의 정확도를 측정한다.

```
오탐률 (False Positive Rate)
미탐률 (False Negative Rate)
관리자 오버라이드 비율
판단별 정확도 이력
```

**오탐률 기반 자동 정책 조정**

```
오탐률 20% 초과 시:
→ 해당 판단 로직 자동 약화
→ 또는 관리자 검토 요청

예:
직거래 탐지 오탐률 20% 초과
→ Level 3 → Level 2 자동 완화 검토
→ 정책/실험 콘솔에 조정 트리거 전달
```

---

#### 핵심 원칙

1. 모든 판단은 출력으로 이어진다
2. 판단은 우선순위를 가진다
3. 위험과 기회를 동시에 본다
4. 판단은 실행을 위한 것이다
5. 모든 판단은 틀릴 수 있다
6. 틀린 판단은 반드시 학습으로 연결된다
7. 시스템은 시간이 지날수록 더 정확해진다

---

### 10-8. 성장/영업 엔진

**흐름 위치**: 이 메뉴는 판단/분석 엔진의 결과를 입력받아 영업 타깃을 자동 생성하고 적절한 캠페인을 적용하여 성장 활동을 실행하며 결과 데이터를 데이터 학습 센터로 재유입시킨다.

**핵심 정의**: 성장/영업 엔진은 "연락을 하는 시스템"이 아니라 제한된 리소스 안에서 가장 높은 성장을 만들어내는 "최적화 엔진"이다.

관리자가 대상을 고르지 않는다. 시스템이 타깃을 생성하고, 관리자는 실행만 한다.

---

#### 핵심 구조

```
판단 결과 → 타깃 생성 → 우선순위 분류 → 캠페인 매핑
→ 실행 (수동 / 조건부 자동) → 결과 수집 → 재학습
```

---

#### 타깃 자동 생성

타깃은 사람이 선택하지 않는다. 판단/분석 엔진이 자동 생성한다.

```
식당 30일 미활동    → 재활성 타깃 자동 생성 (High)
공급자 14일 미입찰  → 입찰 유도 타깃 생성 (High)
수요 급증 품목      → 공급자 모집 타깃 생성 (Medium)
반복 거래 식당      → 우수 고객 전환 타깃 생성 (Medium)
이탈 직전 참여자    → 즉시 개입 타깃 생성 (Critical)
```

---

#### 실행 우선순위 + 용량 제한 (Execution Capacity Control)

타깃이 많아지면 무엇부터 실행할지 기준이 필요하다. 무한 실행 금지.

**우선순위**
```
Critical → 즉시 실행 (이탈 직전)
High     → 오늘 실행
Medium   → 이번 주 실행
```

**실행 용량 제한**
```
settings:
daily_execution_limit = 50 (하루 최대 실행 건수 / 수정 가능)

초과 시: 자동 대기열 이동
예) 오늘 120건 생성 → 50건 실행 + 70건 대기 (우선순위 순)
```

---

#### 캠페인 피로도 제어 (Fatigue Control)

같은 대상에게 반복 연락하면 역효과가 발생한다.

```
settings:
fatigue_contact_limit     = 3  (최근 7일 내 최대 연락 횟수)
fatigue_no_response_limit = 2  (응답 없음 최대 횟수)
fatigue_cooldown_days     = 14 (쿨다운 기간)
```

**동작**
```
7일 내 3회 연락     → 자동 제외
응답 없음 2회       → 14일 쿨다운
쿨다운 대상 → 다음 캠페인 대상에서 자동 제외
```

---

#### 캠페인 유형

각 타깃은 캠페인 유형으로 자동 분류된다.

**재활성 캠페인**
```
대상: 휴면 참여자
목적: 재사용 유도
채널: 카카오 / 문자
스크립트: "재참여 유도" 계열
성공 기준: 연락 후 14일 내 발주요청 1건 이상
```

**신규 모집 캠페인**
```
대상: 잠재 고객 (리드)
목적: 첫 거래 유도
채널: 문자 / 전화
스크립트: "첫 거래 혜택" 계열
성공 기준: 연락 후 30일 내 첫 거래 발생
```

**공급자 확장 캠페인**
```
대상: 특정 품목 공급자 부족 시
목적: 공급 확보
채널: 전화 우선
스크립트: "입찰 참여 유도" 계열
성공 기준: 연락 후 7일 내 첫 입찰 참여
```

**우수 고객 전환 캠페인**
```
대상: 반복 거래 식당
목적: VIP화 / 거래 확대
채널: 전화
스크립트: "전용 혜택 제안" 계열
성공 기준: 연락 후 30일 내 거래 증가율 +20%
```

성공 기준은 settings에서 관리. 플랫폼 성장 단계에 따라 조정 가능.

---

#### 자동 실행 트리거 (Semi-Automation Layer)

일부 캠페인은 조건부 자동 실행을 허용한다.

**자동 실행 허용 조건**
```
Low Risk 대상
검증된 스크립트 (성공률 80% 이상)
비침습적 채널 (카카오 / 문자)
```

**자동 실행 허용 예시**
```
휴면 식당 카카오 알림
납품 완료 후 감사 메시지
반복 거래 유도 메시지
```

**자동 실행 금지**
```
전화 영업 ❌ (항상 수동)
고위험 대상 ❌
미검증 스크립트 ❌
```

---

#### 스크립트 추천 (데이터 기반)

스크립트는 고정이 아니다. 데이터 학습 센터 기반으로 추천된다.

```
추천 기준:
채널별 성공률
타깃 유형별 전환율
과거 유사 캠페인 성과
```

---

#### 성과 → 재학습 연결

모든 영업 결과는 반드시 학습으로 연결된다.

```
수집 데이터:
연락 성공 여부
전환 여부 (활성화)
채널별 성공률
스크립트별 성과
캠페인 성공/실패 판정
```

```
활용:
→ 데이터 학습 센터로 전달
→ 다음 타깃 선정 정확도 향상
→ 스크립트 추천 정교화
→ 캠페인 성공 기준 자동 보정
```

---

#### 핵심 원칙

1. 타깃은 사람이 고르지 않는다
2. 모든 타깃은 우선순위를 가진다
3. 모든 영업은 피로도를 고려한다
4. 자동화는 허용되지만 통제된다
5. 캠페인은 데이터 기반으로 선택된다
6. 모든 영업은 학습으로 연결된다
7. 성장 엔진은 자동으로 진화한다

---

### 10-9. 수익/정산 통제

**흐름 위치**: 이 메뉴는 거래 흐름 관제 및 참여자 네트워크의 결과를 받아 돈 흐름을 자동 통제하고 수익을 확정하며 결과 데이터를 데이터 학습 센터로 전달한다.

**핵심 정의**: 수익/정산 통제는 "정산 기능"이 아니라 플랫폼의 돈과 리스크를 동시에 관리하는 "금융 제어 시스템"이다.

---

#### 핵심 구조

```
거래 완료 → 정산 조건 판단 → 자동 정산 / 보류 결정
→ Action Queue 생성 → 관리자 예외 처리
→ 수익 확정 → 데이터 학습 센터 재유입
```

---

#### 돈 흐름 원칙

```
모든 결제는 플랫폼을 통과한다
모든 정산은 기록되고 검증된다
모든 거래는 결제 / 정산 / 증빙 상태를 가진다
직거래 차단: 식당 ↔ 공급자 직접 결제 절대 금지
위반 시 자동 감지 → 관리자 알림 → 거래 중단
```

---

#### 결제 / 정산 / 증빙 통합 상태 관리

각 거래는 아래 4가지 상태를 반드시 가진다.

```
결제 상태:  미결제 / 완료
정산 상태:  대기 / 처리중 / 완료 / 보류
증빙 상태:  계산서 미발행 / 발행 완료
선지급 상태: 해당 없음 / 선지급 완료 / 상환 대기 / 미납
```

4가지 불일치 시 → 리스크 거래 자동 플래그 → Action Queue 생성

관리자는 한 화면에서 확인:
```
식당이 결제했는가?
플랫폼이 수취했는가?
공급자에게 정산했는가?
계산서가 발행되었는가?
```

---

#### 자동 정산 시스템

정산은 수동이 아니라 조건 기반 자동 실행이다.

**자동 정산 조건 (모두 충족 시)**
```
거래 완료
클레임 없음
납기 정상
신뢰도 기준 이상
→ 자동 정산 실행
```

**정산 대기 트리거**
```
거래 완료 후 7일 경과  → 자동 대기 등록
정산 대기 14일 초과   → Action Queue 생성 (High)
결제/정산 불일치 감지 → Action Queue 생성 (Critical)
```

---

#### 분쟁 / 보류 처리

**보류 조건**
```
클레임 발생 거래
납기 지연 미해결 거래
직거래 의심 거래
```

**보류 해제**
```
관리자 검토 후 승인
또는 당사자 합의 후 처리
```

**보류 에스컬레이션**
```
보류 30일 초과 → Action Queue 생성 (Critical) → 강제 개입 필요
```

---

#### 신뢰 기반 정산 유예 (Credit Line)

플랫폼은 신뢰도 기반으로 금융 유연성을 제공한다.
신뢰도 = 금융 권한. 선지급은 편의 기능이 아니라 신용이다.

**신용 한도 조건**
```
신뢰도 80 이상 → 최대 500만원 유예 허용
신뢰도 70 이상 → 최대 200만원 유예 허용
신뢰도 70 미만 → 선지급 불가 / 즉시 결제만
기존 미납 있음 → 선지급 불가
한도 초과 금액 → 선지급 불가
```

모든 한도 기준은 settings에서 관리. 거래 이력 기반 동적 조정 가능.

**유예 기간**
```
7일 / 14일 / 30일 (신뢰도 + 정책 기반 결정)
```

**선지급 실행**
```
조건 충족 → 플랫폼 선지급 → 공급자 즉시 정산
→ 식당에게 후청구 발행
```

---

#### 선지급 미납 리스크 처리

**즉시 조치**
```
신뢰도 급락 (강제 하락)
결제 유예 권한 즉시 박탈
신규 거래 제한 (Level 2 이상 자동 적용)
```

**재무 처리**
```
미납 금액 → "리스크 채권"으로 분류
수금 프로세스 자동 실행
```

**Action Queue 생성 (Critical)**
```
→ [수금 실행] / [거래 제한 유지] / [법적 조치 검토]
```

**반복 미납 에스컬레이션**
```
2회 이상 미납:
→ 신용 한도 축소
→ 선지급 완전 차단
→ 참여자 상태 위험 그룹 강제 이동
```

**최종 미회수 손실 처리**
```
일정 기간 이후 플랫폼 손실 처리
→ 데이터 학습 센터로 전달 (신용 정책 강화 입력값)
```

---

#### 수수료 구조 (정책 기반)

#### 회계 이벤트 정책 (ACCOUNTING-EVENT-POLICY-001 · DECISIONS **[D-021]**)

> **플랫폼 storefront·allocation·`supplier_payables`·`payments` 축**에 적용. 본 절(10-9)의 일반 서술(예: 조건 기반 자동 정산)과 충돌할 경우 **storefront 회계 이벤트는 [D-021] 및 아래 원칙이 우선**한다.

**[회계 이벤트 원칙]**

- **cancelled** = 운영(또는 품질) 상태로서의 종료 표시. **단독으로 회계 확정·KPI 역전을 의미하지 않는다.**
- **reversal** = 회계 이벤트 — **append-only 방향**(상쇄·추가 기록 우선, 확정 금액 overwrite 금지).
- **refund** = 실제 돈 반환 이벤트 — **cancellation 과 동일시하지 않는다.**
- **KPI** = **reversal/refund 완료**를 반영하는 것을 목표로 한다(구현은 `tasks.md` **`[ACCOUNTING-EVENT-POLICY-001]`**·`[PLATFORM-ERP-001]` 범위).
- **`commerce_order_allocations` `confirmed` 이후** 자동 rollback·자동 reversal **금지** — **관리자 수동 검토** 필수.

**[취소·환불 원칙]**

- **pending allocation**: 자동 `cancelled` 허용(현행).
- **confirmed allocation 이후**: 관리자 수동 처리 필수.
- **현재 지원 단위**: **주문 전체** 취소·환불·reversal 만(부분 환불·품목 단위 취소는 장기 과제, **P0/P1 부분 환불 로직 금지**).

**[immutable 원칙]**

- 주문 시점 **스냅샷 삭제 금지** · **확정 금액 필드 overwrite 금지**.
- reversal 은 **새 회계 이벤트**로 남기고, **audit trail(`admin_logs`) 유지**를 전제로 한다.

**[append-only 방향]**

- 기존 이벤트 **삭제보다 reversal 이벤트 추가**를 우선하여, ERP·**forensic 재현**이 가능하도록 한다.

#### `payments.type` taxonomy 정책 (**PAYMENTS-TAXONOMY-POLICY-001** · `DECISIONS.md` **[D-022]**)

> 본 절은 위 **[회계 이벤트 정책]** 과 모순되지 않게 **`payments` 행의 분류(`type`)** 만 다룬다. 상세 설계는 **`docs/PAYMENTS-TAXONOMY-DESIGN-001.md`** — **정책 확정 문구는 [D-022]** 가 우선한다.

**[`payments.type` 원칙]**

- **신규 accounting 이벤트**(플랫폼·RFQ·정산 축에서 회계 의미를 갖는 INSERT): **`type` 명시 필수** 방향(앱·RPC 가드는 별도 과제).
- **기존 `type` NULL**: **legacy debt** — 운영 부채로 추적; **임의 backfill 금지**.
- **최종 목표**: 컬럼 **`NOT NULL`** — 시점은 **[D-022]** 에 따라 **P1 이후** 검토.
- **enforcement**(DB CHECK·NOT NULL 등): **P1 이후**; 그 전에는 **taxonomy semantics alignment** 및 **settlement/payout lifecycle** 안정화가 선행.
- **순서**: 정책 → lifecycle → enforcement(**enforcement 선행 금지**).

**[현재 허용 type 상태]**

- **`settlement`**: **transition taxonomy** — lifecycle·payout chain 완성 전 **세분화·리네임 금지**([D-022] Q2).
- **storefront / RFQ**: 일부 경로 **`type` 미설정(NULL) 다수** — legacy.
- **reversal**: append-only reversal row 방향(구현은 **`ACCOUNTING-REVERSAL-P0-001`** 등 별도).
- **payout taxonomy**: **미완성**.

**[현재 허용·표준 방향 type 목록(요약)]**

- `storefront_collection` — **신규 표준 방향**(storefront 인바운드 수금 등).
- `rfq_collection` — **신규 표준 방향**(RFQ 인바운드 등).
- `settlement` — **현행 유지**(수수료·정산 인바운드 등 기존 코드 축).
- `reversal` — **append-only 방향**.
- `adjustment` — **조건부**(정책·감사 절차 하에서만).
- **`NULL`** — **legacy only**; 신규 accounting row에 **의도적 NULL 금지** 방향.

**[금지]**

- enforcement 없이 **임의 taxonomy 변경**.
- **`NULL` 임의 backfill**.
- **`settlement` 명칭·의미 임의 세분화**(fee/payout/accrual 분리 등).
- **semantics alignment 이전** migration·CHECK·NOT NULL **선행 enforcement**.
- **drift 발견 후 근거 없는 임의 수정** — 기록·재검증 절차는 `CONTEXT.md` **[SCHEMA-DRIFT-001]** · semantics drift 원칙 따름.

### 10-10. 정책/실험 콘솔

**흐름 위치**: 이 메뉴는 판단/분석 엔진의 트리거를 입력받아 정책을 자동 제안하고 관리자 승인 후 적용하며 거래 흐름 관제 / 참여자 네트워크 / 수익 통제로 전달하고 결과를 데이터 학습 센터로 재유입시킨다.

**핵심 정의**: 정책/실험 콘솔은 "설정 페이지"가 아니라 충돌하는 정책들을 통제하고 최적의 행동을 선택하는 "정책 오케스트레이션 시스템"이다.

---

#### 핵심 구조

```
판단 트리거 → 정책 제안 자동 생성 → 충돌 감지 → 우선순위 해결
→ 관리자 승인 → 정책 적용 → 결과 측정 → 자동 평가
→ 유지 / 롤백 / 확대 → 재학습
```

---

#### 정책 제안 자동 생성

정책은 사람이 처음부터 만드는 것이 아니다. 판단/분석 엔진 트리거 기반으로 자동 생성된다.

```
직거래 탐지 오탐률 20% 초과
→ "Level 3 → Level 2 완화" 정책 제안 자동 생성

공급자 부족 품목 감지
→ "입찰 인센티브 정책" 제안 자동 생성

특정 식당 이탈 증가
→ "재활성 캠페인 강화" 정책 제안 자동 생성
```

---

#### 정책 충돌 감지 시스템

정책/실험 콘솔은 여러 정책이 동시에 작동하는 시스템이다. 충돌을 감지하고 해결하는 구조가 반드시 필요하다.

**정책 충돌 정의**
```
동일 대상에 대해 상반된 행동 요구:
하나는 제한 ↔ 하나는 확대
하나는 차단 ↔ 하나는 유도

예:
공급자 신뢰도 하락 → 입찰 제한 (리스크 정책)
공급자 부족 감지   → 입찰 인센티브 확대 (성장 정책)
→ 동일 공급자에 대해 충돌 발생
```

**충돌 감지 기준**
```
정책 적용 전 반드시 충돌 여부 검사:
대상 기준 (식당 / 공급자 / 그룹)
정책 유형 기준 (제한 / 확대 / 차단 / 유도)
충돌 감지 시 → 자동 플래그 생성
```

---

#### 우선순위 기반 충돌 해결

```
1순위: 리스크 / 안전 정책
2순위: 수익 / 정산 정책
3순위: 성장 / 영업 정책
4순위: UX / 편의 정책
```

**자동 해결**
```
상위 우선순위 정책 자동 적용
하위 정책 → 일시 보류 또는 제한 적용

예:
입찰 제한 (리스크 1순위) > 입찰 인센티브 (성장 3순위)
→ 제한 우선 적용 / 인센티브 정책 보류
```

**해결 불가 시 (수동 개입)**
```
동일 우선순위 충돌
복합 조건 충돌 (다중 대상)
→ Action Queue 생성 (High)
→ [정책 선택] / [병합 정책 생성] / [조건 분기 설정]
```

**정책 병합 (고급)**
```
충돌 반복 시 시스템이 병합 정책 자동 제안:
예) "신뢰도 낮은 공급자 → 제한 유지
    + 해당 공급자의 특정 품목만 인센티브 적용"
```

---

#### 정책 적용 범위 (Scope Control)

```
전체 적용
특정 그룹 적용 (식당 / 공급자 / 지역 / 신뢰도 구간)
A/B 테스트 적용
```

```
애매      → 추가 실험

```

#### 핵심 원칙

1. 정책은 사람이 만드는 것이 아니라 시스템이 제안한다
2. 정책은 반드시 실험된다
3. 정책은 성과로 평가된다
4. 정책은 자동으로 진화한다
5. 정책은 항상 충돌할 수 있다
6. 충돌은 시스템이 먼저 해결한다
7. 리스크는 항상 성장보다 우선한다
8. 해결되지 않는 충돌만 사람이 판단한다

---

### 핵심 원칙

1. 관리자OS는 보는 곳이 아니라 플랫폼이 스스로 판단하게 만드는 곳이다
2. CRUD 화면 금지 — 데이터→판단→정책→자동화 구조만 허용
3. 신뢰도는 사람이 판단하지 않는다 — 행동 데이터가 계산하고 정책을 실행한다
4. 모든 돈은 플랫폼을 통과한다 — 직거래 절대 금지
5. 모든 관리자 행동은 admin_logs에 기록된다
6. 코드 없이 정책을 바꿀 수 있어야 한다

---

**최종 선언**

```
식당OS   → 거래를 생성한다
공급자OS → 거래를 처리한다
관리자OS → 플랫폼이 스스로 작동하게 만든다

세 시스템이 연결될 때 식식이OS는 완성된다.
```

## 11. 사업자 구조

### 법인 분리

| 사업자 | 역할 | 운영 앱 |
|--------|------|---------|
| 디닷페이스 | 플랫폼 운영사 | 관리자OS |
| 해내음코리아 | 공급자 (초기 유일한 공급자) | 공급자OS |

### 돈의 흐름

```
식당 → 디닷페이스 입금 (계산서 발행)
        ↓
디닷페이스 → 공급자 정산 (공급자가 계산서 발행)
```

---

### 11-1. 초기 운영 전략

```
1단계: 식당 확보 우선
       → 관리자OS에서 발주요청 확인 후 공급자OS로 배정

2단계: 공급자 회원 확장
       → 공급자OS로 직접 배정

3단계: 플랫폼 완전 자동화
       → 관리자OS는 관제만 / 시스템이 판단하고 실행
```

## 12. 커머스 전략 — 구매 경험으로 운영까지

### 핵심 철학
식식이OS는 ERP를 팔지 않는다.
구매 경험을 장악한다.

기존 커머스 플랫폼은 식당 운영 데이터와 연결되지 않는다.
식식이OS는 메뉴/원가/구매/재주문/발주요청 데이터를 통합해서
운영 기반 추천과 구매 최적화를 제공한다.

따라서 커머스는 별도 시스템이 아니라
운영 OS 내부에 존재해야 한다.

---

### 우리는 오픈마켓이 아니다

식식이OS는 불특정 다수가 상품을 올리는
오픈마켓 구조를 지향하지 않는다.

상품 수 확대보다
식당별 구매 효율과 운영 최적화가 우선이다.

쿠팡/네이버 최저가 구조로 가면 죽는다.
우리가 파는 것은 상품 가격이 아니라 운영 효율이다.

무엇을 안 만들 것인지가
무엇을 만들 것인지만큼 중요하다.

---

### 왜 식식이OS 안에서 구매해야 하는가

식당 사장님이 체감하는 즉각적 가치:

- 발주 시간 절감: 재주문이 클릭 한 번으로
- 원가 절감: 대체 상품 추천으로 식자재 비용 감소
- 구매 스트레스 감소: 내가 쓰는 메뉴 기준으로 추천
- 장바구니 최적화: 같이 사면 더 저렴
- 운영 데이터 연동: 구매 이력이 원장/미수에 자동 반영

목표:
"이번 달 식자재 비용 48만원 절감"
이런 실제 숫자를 데이터 기반으로 보여준다.

---

### 전환 흐름 (Lock-in 전략)

발주요청을 억지로 가르치지 않는다.
구매 경험을 통해 자연스럽게 연결된다.
쇼핑이 발주요청 학습 장치가 된다.

1단계: 쇼핑 경험 (익숙함)
→ 식당OS에서 식자재를 쇼핑몰처럼 구매

2단계: 개인화 추천 경험 (신기함)
→ 메뉴판/식자재 데이터 기반 맞춤 추천
→ "이 시스템이 우리 가게를 이해한다"는 경험

3단계: 재주문 경험 (편리함)
→ 한 번 산 것을 클릭 한 번으로 재주문

4단계: 발주요청 경험 (자연스러움)
→ 없는 상품을 자연스럽게 요청
→ 억지로 배우지 않아도 된다

---

### 추천은 플랫폼 핵심 엔진이다

추천은 단순 기능이 아니다.
구매/재주문/원가절감/발주요청/장바구니 최적화/공급 연결
전체를 연결하는 핵심 엔진이다.

식식이OS는 단순 쇼핑몰이 아니다.
식당마다 붙어있는 디지털 식자재 영업사원을 지향한다.

식당이 등록할수록 추천이 정확해진다:

메뉴판 등록:
→ 메뉴에 필요한 식자재 자동 추천
→ 원가 기반 대체 상품 추천
→ 업종/메뉴 맞춤 묶음 추천

현재 사용 식자재 등록:
→ 더 싼 대체 상품 추천
→ 재주문 주기 기반 자동 알림

구매 데이터 축적:
→ 함께 구매하는 상품 추천
→ 재주문 주기 자동 감지
→ 장바구니 최적화

등록 진입장벽 제거:
- 사진만 올려도 됨 (OCR 자동 인식)
- 한 번 등록하면 반복 사용
- 자동 추천으로 빈칸 채워줌

---

### 추천 시스템의 성장 구조

초기 추천은 반자동/기초 추천 수준일 수 있다.
왜냐하면 초기에는 데이터가 적기 때문이다.

식당 데이터와 구매 데이터가 축적될수록:
- 추천 정확도
- 재주문 예측
- 대체 상품 추천
- 장바구니 최적화

가 점진적으로 고도화된다.

식식이OS의 추천 품질은
운영 데이터 축적과 함께 성장한다.

---

### 데이터 입력의 이유

식식이OS는 식당이 데이터를 입력할수록 더 강력해진다.

메뉴판 등록 / 현재 사용 식자재 등록 / 구매 이력 축적
이 쌓일수록 추천 정확도/재주문 편의/원가 절감/장바구니 최적화가 개선된다.

데이터 입력은 관리 업무가 아니라
운영 절감으로 되돌아오는 투자다.

초기 온보딩 설득 논리:
"메뉴판 한 번 올리면 필요한 식자재를 알아서 추천해 드립니다"

---

### 식당 전용 비공개 가격 구조

식식이OS 가격은
검색 엔진이나 오픈마켓에 노출되지 않는다.

식당별 업종/구매 패턴/장바구니/거래 규모/재주문 주기
기반으로 운영 최적화 가격이 다르게 적용될 수 있다.

이를 통해:
제조사/유통사의 온라인 가격 노출 리스크 없이
실질 할인과 운영 최적화를 동시에 제공한다.

이것이 제조사/유통사를 설득하는 논리이기도 하다.

---

### 장바구니 할인 전략

할인은 개별 상품 최저가 경쟁이 아니다.
장바구니/묶음 구매 기반으로 설계한다.

운영 데이터 기반 할인:
모든 식당이 같은 가격 구조가 아닐 수 있다.
- 재주문 주기 기반
- 업종 기반
- 구매 패턴 기반
- 객단가 기반

구독료를 받는 구조이므로
일반 쇼핑몰보다 공격적인 할인 전략이 가능하다.

---

### 운영 절감 경험

식식이OS는 단순 주문 시스템이 아니다.
식당의 구매 비용/발주 시간/원가/재주문 효율을
지속적으로 최적화한다.

실제 데이터 기반으로 보여주는 것:
- "이번 달 식자재 비용 48만원 절감"
- "장바구니 최적화로 구매 효율 증가"
- "대체 상품 추천으로 원가 절감"

식당 사장님의 감정을 건드리는 숫자를 보여준다.

---

### 공급망 학습 시스템

식식이OS는 주문/발주요청/재주문/장바구니/업종 데이터를
지속적으로 학습한다.

이를 통해:
- 어떤 상품이 반복 수요가 있는지
- 어떤 업종이 무엇을 함께 구매하는지
- 어떤 지역에서 어떤 수요가 발생하는지

를 축적한다.

이 학습 데이터는:
추천 정확도와 공급 협상력을 함께 강화한다.

### 발주요청 UX — Loose Input → Structured RFQ

핵심 원칙:
발주요청 엔진과 발주요청 입력 UX는 다르다.

기존 RFQ 엔진은 유지한다.
입력 진입장벽만 낮춘다.

식당이 입력하는 것 (느슨하게):
- 사진 한 장
- URL 붙여넣기
- "이거 구해주세요" 한 줄 텍스트

내부에서 일어나는 것 (구조화):
1. AI/OCR 파싱
2. 상품/카테고리/수량 추정
3. 공급 가능 여부 탐색
4. RFQ 구조화 → 기존 RFQ 엔진으로 전달

입력은 단순하게. 처리는 구조화하여.
기존 RFQ 엔진 건드리지 않는다.
간편 입력 레이어를 위에 추가한다.

### 비정형 주문 흡수 — 카카오톡 채널 전략

카카오톡을 없애는 것이 목표가 아니다.
식식이OS 안으로 흡수하는 것이 목표다.

카카오톡은 식식이OS로 진입시키기 위한 보조 채널이다.
핵심 데이터와 운영 흐름은 반드시 식식이OS 내부에 축적되어야 한다.
장기적으로 카카오 주문 흐름 역시 식식이OS 내부 주문 구조로 흡수한다.

카카오톡이 핵심 시스템이 되면 안 된다.

#### 초기 구조 (현실적)

결제 화면에서 선택:
- 카드결제 (즉시 처리)
- 무통장입금 선택 시:
  → "카카오톡으로 주문 보내기" 버튼
  → 주문 요약 자동 생성
    (상품명/수량/요청사항/총액/식당명)
  → 운영자 카카오톡으로 전달
  → 운영자가 계좌이체 안내 후 수동 처리

초기엔 사람이 중간에 있어도 된다.
중요한 건 식당이 "편하게 요청했다"는 경험이다.
이 수동 처리 과정이 실제 주문 흐름 학습 데이터가 된다.

#### 장기 방향

카카오 채널 개설:
→ 식당이 카카오 채널로 자유롭게 주문 요청
→ 운영자가 확인 후 식식이OS에 수동 등록

카카오 챗봇 연동:
→ 카카오로 주문 → 자동으로 식식이OS 주문 생성

카카오 주문 자동 구조화:
→ 카카오로 들어온 사진/텍스트/주문내역을
  AI가 상품 추정/수량 추정/거래처 연결
→ 식식이OS 주문/RFQ로 자동 변환
→ Loose Input → Structured Order 흐름과 동일

식식이OS는 단순 판매 플랫폼이 아니다.

를 축적한다.

### 초기 공급 구조

### 초기 운영 원칙 (기능 과다 금지)

실제 식당 주문 흐름과 공급 수요를 학습하는 것이다.

자동화는 실제 운영 데이터가 쌓인 이후
단계적으로 진행한다.

초기에는 이것만 만든다:
1. 상품 노출
2. 장바구니
3. 결제 (PortOne/토스페이먼츠 + 무통장입금)
4. 재주문
5. 간편 발주요청

추천/AI/OCR/최적화는 초기엔 반자동이어도 된다.

쇼핑몰 UX 위에 운영 데이터 엔진이 결합된 구조를 지향한다.

### buy의 역할 정의

buy는 단순 쇼핑몰이 아니다.
"이미 확보된 상품을 가장 빠르게 다시 구매하는 공간"으로 정의한다.

buy의 핵심 목적:
- 재주문
- 빠른 구매
- 운영 기반 추천
- 자동발주 진입
- RFQ 자연 연결

초기 buy 핵심 UX:
1. 최근 구매 상품
2. 재주문 추천
3. 자주 구매하는 상품
4. 장바구니 최적화
5. 발주 시기 추천
6. 없는 상품 → RFQ 자연 연결

buy는 "상품 탐색 중심 오픈마켓"이 아니다.
식당 운영 흐름 중심:
- 다시 사기
- 빨리 사기
- 생각 줄이기
- 운영 절감

이 핵심이다.

buy는 RFQ를 대체하지 않는다.
buy는 RFQ의 진입 장벽을 낮추는 역할을 한다.

식당OS에 등록된 데이터는 반드시 buy 추천에 반영되어야 한다:
- 메뉴판 등록 → 핵심 메뉴 우선 추천
- 현재 사용 식자재 등록 → 이미 사용 중인 상품은 중복 추천 금지
- 구매 이력 존재 → 재주문 주기 반영

buy는 일반 쇼핑몰이 아니라
"식당 운영 기반 구매 인터페이스"다.

### commerce_orders 분리 원칙

commerce_orders를 기존 orders와 분리한다.

이유:
RFQ 흐름과 커머스 흐름은 구조적으로 다르다.

RFQ:
- 견적 요청 / 공급자 비교 / 협상 / 입찰 / 공급 탐색

Commerce:
- 즉시 구매 / 장바구니 / 결제 / 재주문 / 자동발주

DB 구조:
RFQ 관련: rfq_requests / rfq_items / rfq_quotes
Commerce 관련: commerce_orders / commerce_order_items / cart_items

RFQ → commerce_order 전환은 가능해야 한다:
RFQ로 요청 → 운영자 sourcing 성공 → 상품 등록
→ 이후부터 buy에서 commerce_order로 반복 구매

RFQ는 공급 발견 엔진.
Commerce는 반복 구매 엔진.
둘은 연결되지만 동일하지 않다.

기존 RFQ 엔진은 유지한다.
커머스 추가 때문에 RFQ 구조를 흔들지 않는다.
커머스는 기존 운영 구조 위에 얹는 방식으로 진행한다.

**플랫폼 주문 (Platform Order)**: `commerce_orders` 계열 주문은 **공급자OS에 수동으로 재입력하는 ERP 대상이 아니다.** 주문 발생 자체가 **플랫폼 이벤트**이며, **관리자OS(디닷페이스 ERP)** 측으로 **자동 반영·동기화**되는 것을 목표 구조로 한다. 이후 **공급 fulfillment**(예: 해내음코리아 등 할당된 공급자)와 **공급자 정산**은 플랫폼 주도 하에 allocation·정산 파이프라인으로 연결된다(상세 과제: `tasks.md` **`[PLATFORM-ERP-001]`**).

---

### 카페24 전략

카페24는 건드리지 않는다.
연동에 시간 낭비하지 않는다.

기존 매출/고객 유지용 레거시로 운영한다.
카페24 고객을 식식이OS로 직접 영업해서 이동시킨다.
식식이OS 자체 커머스를 만든다.

### 결제 전략

PG 직접 만들지 않는다.
PortOne 또는 토스페이먼츠 연동.

흐름:
식식이OS 장바구니/주문
→ 카드결제: 외부 PG → 성공 callback → 주문 완료
→ 무통장입금: 카카오톡 주문 전달 → 수동 처리

### 식식이OS의 최종 방향

식식이OS는 단순 쇼핑몰도, 단순 ERP도 아니다.

- 발주
- 원가
- 재주문
- 거래 흐름
- 공급 연결

전체를 운영 데이터 기반으로 최적화하는
외식 공급망 운영 시스템을 지향한다.

## 13. Storefront / 반복주문 시스템

### 1. Storefront 정의

- Storefront는 식당의 반복주문을 위한 Direct Order 시스템이다.
- Storefront는 RFQ를 대체하지 않는다.
- Storefront operator = **플랫폼 운영사(디닷페이스)** — 식식이OS 상에서 **결제·주문 고객의 owner** 이다.
- Storefront는 단순 오픈마켓이 아니다.
- Storefront는 반복 거래와 재주문을 위한 운영 인터페이스이다.
- 플랫폼은 storefront 운영 및 거래 orchestration을 담당한다.
- **Storefront에서의 식당 고객 = 디닷페이스의 플랫폼 고객**; **Storefront 주문 = 플랫폼 주문(platform order)** 이다.
- 공급자(예: **해내음코리아** 등)는 **fulfillment provider**(출고·배송·공급 실행)로 묶이며, **고객·주문·결제의 owner가 아니다.**
- 세금·계약서 상 세부 표현은 법무·회계 확정에 따르되, **시스템·운영 책임의 1차 축은 디닷페이스(플랫폼)** 로 둔다.

### 1-1. 플랫폼 주문 → ERP → Fulfillment → 정산 (목표 흐름)

```
Platform Commerce Event   (storefront 주문 생성·결제 이벤트)
        ↓
Platform ERP Auto Sync    (관리자OS / 디닷페이스 ERP — 수동 재입력이 아닌 자동 반영 방향)
        ↓
Supplier Fulfillment      (할당된 공급자 — 출고·배송·공급 실행)
        ↓
Supplier Settlement       (공급자 ↔ 디닷페이스 정산)
```

- **식당 ↔ 디닷페이스**: Storefront 결제·환불·클레임·플랫폼 미수 등.
- **공급자 ↔ 디닷페이스**: fulfillment 대가·수수료·정산 주기 등(공급자↔식당 직접 결제는 PRODUCT 기존 원칙과 동일하게 **금지**).

### 1-2. B2B 가격정책 엔진 — 금액 모델 (정책 확정, DISCOUNT-ENGINE-POLICY-001)

가격정책 엔진은 단순 할인 UI가 아니라 **플랫폼 마진**과 **공급자 payable**을 동시에 정하는 **ERP 가격 엔진**이다. 아래 금액·원칙은 **정무님 확정(2026-05-14)** 이며, 상세 결정 문구는 **`DECISIONS.md` [D-020]** 과 **`docs/DISCOUNT-ENGINE-DESIGN-001.md`** 를 참조한다.

#### [가격 금액 모델] (품목·주문 스냅샷 단위)

- **customer_charge**: 식당 **실결제** 금액(청구·`payments` 대사 축).
- **supplier_basis**: 공급자에게 인정하는 **납품 기준가**. **`commerce_price`와 동일시하지 않는다** (판매가 ≠ 납품가).
- **platform_fee**: **초기 정책** `platform_fee = customer_charge × fee_rate` (fee_rate는 관리자 설정 축; 코드 하드코딩 금지 원칙은 기존과 동일).
- **supplier_payable**: `supplier_basis − supplier_discount − platform_fee` (공급자 부담 할인·수수료 반영 후 지급 예정액).
- **platform_margin**: `customer_charge − supplier_payable` (economics·리포트 축; **fee**와 개념 분리 유지).

#### [원칙]

- **판매가 ≠ 납품가** — 단일 “할인 후 결제금액”만으로 allocation·fee·payable·receivable을 **동시에** 정하지 않는다.
- **storefront 가격 결정**은 향후 **`pricing_policies`** 가 SSOT(현재 테이블·엔진 **미구현**).
- **`customer_product_prices`** 는 **참고 데이터**(공급자 CRM 마지막 거래가 등)일 뿐, **storefront 가격정책에 직접 연결하지 않는다.**
- **fee**와 **margin** 은 설계·운영에서 분리해 추적한다.
- **주문 생성 시** 가격·금액 **스냅샷 확정**; **allocation·supplier_payables** 는 해당 스냅샷 기반 **불변(immutable ERP snapshot)**. 이후 가격·정책 변경이 기존 주문에 영향을 주지 않는다.

### 2. RFQ와 역할 분리

RFQ와 Storefront는 경쟁 관계가 아니다.

- RFQ = 신규 거래처 탐색 / 가격 발견 / 저빈도 전략 행동
- Storefront = 반복주문 / 습관 형성 / 고빈도 운영 행동

역할 차이:

**RFQ**

- 새로운 공급자 탐색
- 가격 비교
- 신규 거래 시작
- 공급자 검증

**Storefront**

- 반복 주문
- 빠른 재주문
- 거래 유지
- 운영 효율화

### 3. 거래 Lifecycle

#### 1단계: Storefront 진입

- 기존 카페24 회원 → 식식이OS 가입 → storefront 사용
- 신규 가입 식당 → storefront 탐색 → 플랫폼 경험 축적

#### 2단계: RFQ 기반 신규 거래

- 식당은 RFQ를 통해 신규 공급자를 탐색한다
- 공급자는 식당 정보를 모른 상태로 견적 경쟁한다

#### 3단계: 거래 관계 형성

- RFQ 성공 시 식당 ↔ 공급자 거래 관계가 생성된다
- 반복 거래는 storefront 기반으로 운영된다

#### 4단계: 반복주문

- 식당은 storefront 또는 재주문 인터페이스에서 반복 주문한다
- **플랫폼 주문**은 관리자OS(디닷페이스 ERP)에 **자동 연동**되는 것을 목표로 한다(수동 이중 입력 금지 방향).
- **Fulfillment** 담당 공급자(예: 해내음코리아)는 allocation에 따라 출고·배송·납기 응답을 수행한다(고객 owner 아님).

#### 5단계: 관계 종료 및 재탐색

- 거래 문제 발생 시 식당은 다시 RFQ를 통해 신규 공급자를 탐색할 수 있다

### 3-1. 거래 관계 (Relationship)

식식이OS의 핵심 단위는 단순 주문이 아니라
식당과 공급자 간의 거래 관계이다.

- RFQ는 새로운 거래 관계를 생성한다
- Storefront는 생성된 거래 관계를 반복 운영한다
- 재주문은 거래 관계 기반으로 동작한다
- 거래 관계 종료 시 식당은 다시 RFQ를 사용할 수 있다

핵심 자산:

- 반복 주문 데이터
- 공급자 신뢰 데이터
- 납기/응답 패턴
- 거래 이력
- 재구매 패턴

### 3-2. 학습 파이프라인

식식이OS는 식당별 거래 데이터를 학습하여
재주문 추천과 자동발주 제안의 기반으로 사용한다.

#### 학습 데이터 소스

- rfq_requests / rfq_bids → 가격 발견 이력
- orders (RFQ 기반) → 거래 이력
- ingredients → 식자재 현재가 / 목표가
- price_history → 품목별 가격 추이
- commerce_orders → storefront 반복주문 패턴
- ai_decision_logs → AI 판단 이력 (식당별)
- savings_stats → 절약 통계

#### 학습 → 추천 → 자동발주 확장 순서

1단계: storefront 주문 데이터 축적

2단계: 식당별 패턴 학습
(어떤 식자재를 얼마나 자주 주문하는가)

3단계: 재주문 추천
(storefront 내부 노출)

재주문 추천은:

- 최근 주문 주기
- 거래 안정성
- 가격 변동
- 공급자 만족도
- 품목 반복성

등을 기반으로 계산한다.

4단계: 자동발주 제안

5단계: 식당 확인 후 발주 실행

#### 비가역 원칙

- 자동발주는 제안만 한다
- 식당 확인 없는 자동 실행 절대 금지
- (DECISIONS.md D-013 원칙 동일 적용)

#### 현재 구조 미결 사항 (임의 수정 금지)

- commerce_orders는 현재 학습 파이프라인과
  미연결 상태
- 연결 방식은 orders 이중화 구조 확정 후 결정
- 커서가 임의로 연결 코드 또는 migration 생성 금지

거래 관계는 relationships 테이블에 저장한다.
(CONTEXT.md [ARCH-04] 참조)

### 4. 비가역 원칙 (절대 변경 금지)

아래는 기능이 아니라 플랫폼 생존 원칙이다.

#### RFQ 보호 원칙

- RFQ 계약 완료 전 식당 정보 공급자에게 비공개
- 공급자는 RFQ 단계에서 식당 직접 접근 불가
- RFQ 단계에서 공급자는 식당명/연락처/주소를 알 수 없다

#### 플랫폼 보호 원칙

- 재주문은 반드시 플랫폼 안에서만 가능
- 플랫폼 밖 거래 유도 금지
- 거래 관계 데이터는 플랫폼 핵심 자산이다
- 공급자에게 식당 거래 데이터 직접 공개 금지
- 공급자가 식당을 직접 인지하는 순간 직거래/우회 리스크 발생

#### 운영 원칙

- Storefront와 RFQ는 역할을 분리한다
- RFQ는 신규 탐색
- Storefront는 반복 운영
- 공급자 간 직접 가격 경쟁 구조를 storefront에 노출하지 않는다

### 5. 현재 운영 구조 (1단계)

현재 storefront 운영은 플랫폼 중심 수동 운영 구조다.

현재 흐름:

- 식당 → storefront 주문
- 플랫폼 관리자 → 주문 확인
- 주문 export / 취합
- 공급자 발주
- 공급자 배송

현재 단계에서는:

- 주문 자동 routing 없음
- 공급자 자동 할당 없음
- 자동 정산 없음

초기에는 운영 데이터 축적과 거래 패턴 확보를 우선한다.

### 6. 향후 확장 영역 (구조만 확장 가능하게 설계)

현재 확정하지 않는 영역:

- seller 법적 구조
- 정산 구조
- 공급자 알림 flow 세부
- 공급자별 routing
- 자동 정산
- 주문 자동 분배
- 납기 자동화
- 공급자 fulfillment 구조

현재 구조 미결 사항 (임의 수정 금지):

- commerce_orders와 orders 이중화 구조 존재
- 통합 방식은 향후 확정
- relationship 구조 확정 전 임의 통합 금지
- 커서가 임의로 migration 생성 또는 통합 구현 금지

주의:
위 영역은 실제 운영 데이터 기반으로 확정한다.
추측 기반 구조 고정 금지.

### 7. 금지 사항

아래는 플랫폼 정책 위반으로 간주한다.

- storefront에서 공급자 정보 직접 노출
- RFQ 단계에서 식당명 공급자 노출
- 플랫폼 외부 결제 유도
- 플랫폼 외부 직거래 유도
- 공급자 간 경쟁 공급자 정보 노출
- 거래 관계 데이터 외부 공개

## 14. 자동발주 전략 — 발주 판단 자동화

### 핵심 정의
식식이OS 자동발주는 완전 자동 구매가 아니다.
핵심은 발주 판단 자동화다.

식당 운영에서 가장 반복적이고
스트레스가 큰 행동:
- 뭘 시켜야 하지?
- 뭐 떨어졌지?
- 얼마나 시켜야 하지?

식식이OS는 이 판단 과정을
데이터 기반으로 줄인다.

---

### 자동발주의 목표

초기 자동발주의 목표는
완벽한 수량 예측이 아니다.

핵심은:
식당 사장님의 발주 판단 피로를 줄이는 것이다.

"뭘 시켜야 하지?"라는 생각을 줄여주는 것.
그것만으로도 충분히 강력하다.

---

### 자동 주문 금지 원칙

초기 자동발주 시스템은
사장님의 최종 승인 없이 주문을 생성하지 않는다.

자동발주의 핵심은:
주문 자동 생성이 아니라
발주 판단 보조다.

판단은 시스템이 먼저.
승인은 사람이 최종.

---

### 사람 우선 원칙

시스템 추천보다
식당 사장님의 판단이 항상 우선이다.

식당 운영은 예외 상황이 많다:
- 오늘 단체 예약 있음
- 이번 주 휴무
- 갑자기 메뉴 교체
- 행사 예정
- 재고 남아있음

이런 상황은 시스템이 모른다.
자동발주는 보조 시스템으로 동작한다.
사람의 판단을 대체하지 않는다.

---

### 정기배송과 다른 점

정기배송:
- 매주 화요일
- 동일 수량
- 동일 품목

식당 현실:
- 비 오면 다르고
- 주말 매출 다르고
- 메뉴 바뀌고
- 갑자기 단체 예약 들어오고
- 재고 남고

따라서:
패턴 기반 반자동 발주가 핵심이다.
subscription commerce처럼 동작하면 안 된다.

---

### 재고 데이터 환상 주의

초기 자동발주는 재고 기반이 아니다.

현실:
대부분 영세 식당은 재고를 입력하지 않는다.

따라서 초기 자동발주는:
재고 기반 → 불가능
주문 패턴 기반 → 현실적

학습 데이터 우선순위:
1. 구매 이력 (가장 중요)
2. 재주문 주기
3. 요일 패턴
4. 업종 패턴
5. 메뉴 데이터
6. 계절성
7. 장바구니 패턴
8. 자주 함께 구매하는 품목

재고 데이터는 나중에 선택적으로 받는다.
강제하지 않는다.

---

### 자동발주 UX 흐름

시스템 알림:
"사장님, 발주할 시기입니다. 재고를 확인해보세요."

추천 리스트:
☐ OOO 고춧가루 1kg × 5봉 — 50,000원
☐ 참맛기름 1.8L × 10개 — 90,000원
☐ 냉동삼겹살 × 2박스 — 172,000원

예상 금액: 312,000원
예상 사용 기간: 약 6일
최근 평균 구매 패턴 기준입니다.

[선택 후 주문하기]
→ 배송지 확인
→ 결제
→ 주문 완료

---

### 핵심 UX 원칙

초기 구조:
1. 시스템 추천
2. 사장님 검토 (체크/수량 수정)
3. 배송지 확인
4. 결제
5. 주문 완료

반자동 발주가 핵심이다.
자동으로 바로 주문하면 안 된다.

---

### 추천 최소화 원칙

식식이OS는 과도한 추천/알림을 지양한다.

추천은 아래 경우에만 제한적으로 노출한다:
- 실제 절감 가능성이 높거나
- 반복 수요 가능성이 높거나
- 운영 효율 개선 가능성이 높은 경우

추천 수보다 추천 정확도가 중요하다.

추천 과잉은 식당 사장님을 피곤하게 만든다.
핵심 메뉴 1~3개부터 시작한다.
30개 메뉴를 동시에 공략하지 않는다.

### 진짜 락인

이 시스템의 진짜 락인은 상품이 아니다.
발주 습관이다.

한 번 "생각 없이 체크만 하면 발주되는 경험"에
익숙해지면 다른 플랫폼으로 돌아가기 어려워진다.

### Buy ↔ RFQ 연결 구조

/buy: 이미 확보된 상품을 구매하는 곳
→ 빠른 구매 / 추천 / 재주문 / 장바구니 할인 / 결제

/rfq: 없는 상품을 요청하는 곳
→ "이거 구해주세요" / 대체 상품 요청 / 가격 비교

흐름:
식당이 /buy에서 상품 탐색
→ 없는 상품 발견
→ "원하시는 상품 요청하기" (RFQ 자연 연결)
→ 사진/URL/텍스트 입력 (느슨하게)
→ 내부에서 RFQ 구조화
→ 기존 RFQ 엔진으로 전달

식당은 RFQ라는 개념을 모른다.
그냥 "상품 요청"이라고 느낀다.

### 장기 방향

데이터가 충분히 쌓이면:
- 자동 수량 조정
- 계절성 반영
- 매출 기반 예측
- 폐기율 반영
- 재고 소진 예측

하지만 초기에는:
추천 + 체크 기반 반자동 발주가 현실적이다.

---

### 초기 시작점 (기능 과다 금지)

절대 "AI 자동발주"같이 거창하게 가면 안 된다.

처음엔 그냥:
"사장님 발주할 시기예요"
이 수준부터 시작한다.

수동 운영이 포함되어도 괜찮다.
중요한 것은 완벽한 자동화가 아니라
실제 식당 발주 패턴을 학습하는 것이다.

자동화는 패턴이 쌓인 이후
단계적으로 진행한다.
