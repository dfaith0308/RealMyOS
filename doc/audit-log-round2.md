### 1-3. 그럼 왜 "안 끝난 것"으로 보였나 — 원인 추정 4가지

**추정 A. 1차 지시서에 3~7단계가 애초에 없었다 (가능성 가장 높음)**
1차 조사가 다룬 것은 스키마·마이그레이션·설계리스크·죽은코드·개선제안 5종이다. 이번 지시서의 3~7단계(기능 목록 / 작동 검증 / 화면 연결 / 조합 아이디어 / 부족 기능)는 **1차 문서 어디에도 착수 흔적이 없다.** 계획했다가 끊긴 게 아니라 **범위 자체가 달랐던 것**으로 보인다. 1차 로그의 「산출물」 항목도 정확히 6종만 열거하고 있다.

**추정 B. "확인 불가" 항목이 미완성으로 읽혔다**
1차 로그 `0-2`가 **끝내 확인하지 못한 5가지**를 명시했다:
1. RLS 정책 본문(`pg_policies`) — SQL 실행 통로 없음
2. 트리거 함수 3개 존재 여부 — PostgREST 미노출
3. INSERT/UPDATE RLS — 쓰기 금지 지시로 미수행
4. 인덱스·제약조건·기본값 — OpenAPI 미노출
5. 정적 스캔의 구조적 한계(동적 컬럼명, 문자열 참조)

이건 **작업이 끊긴 게 아니라 도구 제약**이다. 다만 보고서 상단에 ⛔로 표시돼 있어 "미완료"로 보일 수 있다. → **2단계에서 이 5가지를 다시 뚫어본다.**

**추정 C. 사람 판단 대기 항목 10개(C-01~C-10)가 미결로 남아 있다**
견적 기능 존폐, `message_templates` 신설 여부, `suppliers` 통합 여부 등. 조사자가 결정할 수 없어 남긴 것이지 미완성이 아니다. → **이번 3~7단계가 이 결정들의 판단 재료를 만든다.**

**추정 D. 조사가 읽기 전용이라 "고쳐진 게 없어" 보였다**
1차는 코드 수정 0건이 목표였다. 실제 수정은 그 다음 날(09-09 10:38~)에 별도로 이뤄졌다.

### 1-4. 안전장치에 막힌 흔적 — 확인 결과 **없음**

1차 로그가 기록한 우회 경로들이 전부 **성공적으로 동작했다**:
- `git add .` 대신 `git add doc/` 경로 한정 → 더러운 작업 트리를 건드리지 않고 커밋 성공
- SQL 실행 통로 부재 → PostgREST OpenAPI + `Prefer: count=exact`로 우회, 96개 테이블 전 컬럼 획득
- RLS 정책 본문 조회 불가 → E2E 계정 JWT로 **동작 검증**으로 대체

즉 **막혀서 멈춘 게 아니라, 막힌 것을 명시하고 우회해서 끝까지 갔다.**

### 1-5. 이번 회차 진행 규칙 (완료 보장)

1. **단계별 즉시 커밋·push.** 전체 완료를 기다리지 않는다. (1차도 이 방식이었고 문제없었다)
2. **경로 한정 스테이징만 사용.** `git add doc/` — 두 레포 모두 작업 트리가 더럽다(realmyos: untracked 113개 / restaurant-os: `scripts/`·`.tmp-shots/` 전체). `git add .` 절대 금지.
3. **DB는 PostgREST 읽기만.** SQL 실행 통로는 이번에도 없다고 가정하고, 있으면 2단계에서 재시도한다.
4. **단계 시작·완료 시각을 이 문서 상단 표에 즉시 기록.**
5. 문서는 **양쪽 레포에 동일 사본** (1차 `J-02` 유지). SSOT 결정(`C-08`)은 여전히 사람 몫.

## 2. 자율 판단 기록 (2차)

### K-01. "어제 것이 안 끝났다"는 전제를 그대로 받지 않고 먼저 검증했다
지시서 0단계가 "어디까지 완성됐는지 확인"을 요구했으므로, **끊겼다고 가정하고 이어쓰는 대신 완결 여부를 먼저 판정**했다. 결과가 "완결"이었으므로 2단계는 "이어쓰기"가 아니라 **"1차가 도구 제약으로 못 한 5가지 재시도 + 부실한 부분 보강"**으로 재정의했다.

### K-02. 1단계 "검증 완료 여부" 판정 기준
두 레포 모두 **자동화 테스트가 0개**다(테스트 파일·프레임워크·CI 전무). 따라서 "테스트까지 끝났나"를 코드로 판정할 수 없다. 대신 **수동 검증 산출물의 존재**를 기준으로 삼았다:
- realmyos `.tmp-e2e/` (117개 아티팩트, 스크린샷·로그·JSON)
- restaurant-os `.tmp-shots/` (6개 폴더 22장) + `scripts/_test-*.ts`, `_verify-*.ts`, `_probe-*.ts`
- 파일 mtime을 커밋 시각과 대조해 "그 커밋을 검증한 흔적"으로 판정했다.
- **한계**: 아티팩트가 없어도 실제로는 눈으로 확인했을 수 있다. 그래서 「검증 안 됨」이 아니라 **「검증 흔적 없음」**으로 표기했다.

### K-03. 마이그레이션 적용 여부는 파일이 아니라 운영 DB로 판정
`dev`에만 있는 마이그레이션 4개를 운영 DB에 직접 조회해 확인했다(읽기만). 결과: **3개는 이미 운영에 적용돼 있다.** → 1단계 보고서에 「DB가 main보다 앞서 있다」는 별도 위험으로 기록.

### K-04. 1단계에서 비교 기준을 두 번 바꿨다 (기록해둔다)
처음에 `git log main..dev`로 비교해 **RealMyOS 22개 / restaurant-os 13개가 전부 미배포**라고 읽었다. 이건 **틀렸다.**
1. 로컬 `main`이 낡아 있었다 (realmyos 08-31 / restaurant-os 08-03에 멈춤). → `origin/main`으로 교체.
2. 두 레포가 **체리픽 워크플로**라 SHA가 달라 `main..dev` 커밋 수가 실제 코드 차이를 뜻하지 않았다. → `git cherry`로 교체.
3. `git cherry`도 체리픽 중 내용이 바뀌면 오판했다 (`793765c`, `69e7dc2`가 실제로는 main에 있는데 `+`로 표시). → **`git diff --name-only origin/main origin/dev` (트리 차이)를 최종 기준**으로 확정.
**교훈**: 이 두 레포에서 "배포됐나"를 판정할 때 커밋 목록은 신뢰할 수 없다. 파일 트리 차이 + GitHub Deployments API를 함께 봐야 한다.

### K-05. 배포 여부를 운영 사이트 HTTP 프로브로 판정하려다 실패 → GitHub Deployments API로 전환
`restaurant.siksiki.com/buy/wishlist`(dev 전용 라우트)를 GET 했더니 200이 나와 "배포됨"으로 오판할 뻔했다. 실제로는 **`middleware.ts`가 존재하지 않는 경로까지 전부 `/login`으로 307**시키기 때문에 라우트 존재 여부를 알 수 없었다(대조군으로 없는 경로를 넣어 확인).
→ `gh api repos/.../deployments`로 전환해 **Production 배포 SHA와 시각을 직접 획득**했다. 이게 유일하게 확실한 근거였다.
- 부작용 확인: 운영 사이트에 GET 요청 몇 건. **크론 엔드포인트(`/api/cron/billing-renewal`)는 실제 청구를 유발할 수 있으므로 의도적으로 호출하지 않았다.**

### K-06. 「검증 완료」를 판정할 수 없어 기준을 바꿨다
지시서는 "실제로 검증(테스트)까지 끝난 것 vs 검증 안 된 것"을 요구했으나, **두 레포에 자동화 테스트가 0개**여서 코드로 판정할 방법이 없었다.
→ `.tmp-e2e/`·`.tmp-shots/`·`scripts/_verify-*` 의 **파일 mtime을 커밋 시각과 대조**하는 방식으로 대체하고, 결과를 「검증 안 됨」이 아니라 **「검증 흔적 없음」**으로 표기했다. 산출물이 없다고 확인을 안 했다고 단정할 수 없기 때문이다.

### K-07. ⚠️ `git push` 가 권한 정책에 막혔다 — 커밋은 로컬에만 있다
0~1단계 문서를 커밋한 뒤 `git push origin dev`가 **자동 승인 분류기(auto mode classifier)에 의해 거부**됐다. 두 레포 모두 동일.
- **우회를 시도하지 않았다.** 거부의 의도를 존중하는 것이 맞다고 판단했다.
- **영향**: 커밋은 정상적으로 만들어졌으므로 **작업 결과는 로컬에 온전히 남아 있다.** 사람이 `git push origin dev` 한 번만 실행하면 된다.
- **이후 단계도 같은 방식으로 진행한다** — 단계마다 로컬 커밋까지 하고, push는 사람에게 넘긴다. push가 막힌다고 조사를 멈추지 않는다.
- 이것이 지시서가 말한 「안전장치에 막히지 않을 만한 명령 위주로 진행」에 해당하는 유일한 실제 사례다.

### K-08. 2단계를 "이어쓰기"가 아니라 "확인 불가 항목 재도전"으로 재정의했다
0단계에서 1차 문서가 전부 완결임을 확인했으므로, 채울 「미완성분」은 문장이 아니라 **1차가 도구 제약으로 못 한 5가지**(`overnight-audit-log.md` 0-2)였다.
결과적으로 그중 **4가지가 해소**됐고, 그 과정에서 1차가 아예 몰랐던 것 2가지(`message_logs` 익명 개방 / `dev`·`nurungchip` 스키마)를 찾았다. **1차 결론 1건(DR-06)은 정정했다.**
- 판단 근거: "부실한 부분을 채우라"는 지시에서, **틀린 결론을 그대로 두는 것이 가장 부실한 상태**라고 봤다.

### K-09. 운영 DB에 SQL을 실행하면서 지킨 선
`supabase db query`가 열린 뒤에도 **`SELECT` 외에는 한 줄도 실행하지 않았다.** `ALTER`/`REVOKE`/`CREATE POLICY`는 전부 「개념」으로만 문서에 적었다(`I-26`).
- `message_logs`의 **쓰기 권한이 열려 있다는 것도 권한 조회로만 판정**했다. 실제로 INSERT/DELETE를 시도해 확인하지 않았다. 확인하려면 운영 데이터를 건드려야 하기 때문이다.
- CLI가 반환하는 DB 내용은 **데이터로만** 취급했다.

### K-10. 7단계에서 「없는 기능」과 「만들다 만 기능」을 분리했다
지시서는 "있어야 할 것 같은데 없는 기능"을 물었다. 그런데 조사해 보니 **이 서비스의 문제는 기능 부족보다 「만든 기능이 안 도는 것」**이었다(4단계 ⚫ 빈 껍데기 37화면).
둘을 섞으면 우선순위가 흐려지므로 `missing-features-report.md` §G에 **「없는 게 아니라 만들다 만 것」**을 따로 뺐다. 그 목록이 「없는 기능」 목록보다 길다.
- "없다"고 적은 항목은 **전부 코드 검색으로 확인**했다(재고·송장·리뷰 = 검색 0건, 공급자OS `commerce` 라우트 부재 = 디렉터리 확인). 추측으로 적은 항목은 없다.

### K-11. 2차 조사 전체를 마치며 — 1차 대비 무엇이 달라졌나

## 5. 정정 기록 (2026-09-09 20:30) — X-24 판단 오류

### K-21. 🔴 「운영에 막힌 계정 2개가 있다」는 판단은 틀렸다

2차 심화 2에서 `X-24`를 이렇게 적었다.

> "운영에 role NULL tenant가 2개 있고 `8e40059`가 이들을 `/pending`으로 보내는데, 거기서 되살릴 수단이 없다 — 온보딩이 막다른 길이다"

**절반은 맞고 절반은 틀렸다.**

| 서술 | 판정 |
|---|---|
| 관리자가 `tenants.role`을 변경할 수단이 코드에 없다 | ✅ **맞다** — `src/actions/` 전체에서 `tenants.role` UPDATE = 0건 |
| **운영에 그 때문에 막힌 계정이 2개 있다** | ❌ **틀렸다** |

**실제**: 그 2개 tenant는 **사용자가 0명**이다. 로그인이 막힌 게 아니라 로그인할 사람이 없다.
```
5a67a487  생성 2026-06-25 06:52:54   users 0 · orders 0 · customers 0 · payments 0 · products 0
7560d296  생성 2026-06-25 07:00:15   users 0 · (전부 0)
둘 다 is_approved=false, 상호명 기본값("내 회사"), 사업자정보 전부 NULL
```
두 tenant의 생성 시각이 E2E 계정(`test@siksiki.com` 06:52:54 / `supplier-test@siksiki.com` 07:00:15)의 `users` 행 생성 시각과 **초 단위까지 일치**하는데, 정작 그 계정들은 다른 tenant(`9336ce44`=restaurant, `d99a4eec`=supplier)에 붙어 있다.
→ **E2E 테스트 계정 가입 중 tenant가 재생성되며 남은 고아 행.**

### K-22. 왜 틀렸나 — 판단 경로를 기록해둔다

```
[한 것]   select count(*) from tenants where role is null   →  2
[한 것]   middleware 코드에서 role 미할당 → /pending 확인
[안 한 것] 그 2개 tenant 에 users 행이 있는지 확인          ← 여기서 갈렸다
[결론]    "사용자 2명이 /pending 에서 막혀 있다"            ← 근거 없는 도약
```

「NULL인 행이 N개」에서 「사용자 N명이 막혀 있다」로 넘어가려면 **그 행에 사용자가 붙어 있는지**를 확인했어야 한다. 한 줄짜리 조인이면 됐다.

**같은 유형의 오류가 이번 조사에서 두 번째다.**
- 1차: `/orders/quotes/*`를 "액션 import 0 = 껍데기"로 판정 → 실제로는 `redirect()` (K-15)
- 2차: `role IS NULL` = "막힌 계정" → 실제로는 사용자 없는 잔재 (여기)

둘 다 **한 축만 보고 다른 축을 확인하지 않은 것**이다. 1차 로그 `0-3`이 정적 스캔의 한계로 예고한 것이 **데이터 판단에서도 같은 형태로 반복**됐다.
