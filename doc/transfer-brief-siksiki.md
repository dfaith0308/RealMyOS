# 식식이OS 이식 기준서 — 상품 상세페이지 템플릿 / 배송 추적 / 자동 메시지

- 작성일: 2026-09-14
- 원문: `siksiki-transfer-brief.md` (선물답게 기준, 2026-09-14). 이 문서는 원문을 **식식이OS 용어로 재가공**한 것이다.
- 재가공 규칙: 브랜드·발신 명의 "선물답게" → "식식이" / "고객사" → 문맥에 따라 "공급자" 또는 "관리자" / "기업 구매 안내" → "발주 안내" / 선물 도메인 섹션 이름 → 원문 1-4절 표의 식자재 버전
- **설계 원칙은 원문 그대로다.** 바뀐 것은 용어뿐이다. 치환 판단이 애매했던 곳은 `doc/transfer-audit-log.md` 「0단계」에 전부 적었다.
- 읽는 사람: 식식이OS 담당 (RealMyOS = 공급자OS + 관리자OS / restaurant-os = 식당OS)
- 이 문서가 1~3단계 구현의 기준이다.

> 원문 대비 **의도적으로 바꾸지 않은 것 / 바꿀 수 없었던 것** 은 각 절 끝의 「이식 메모」에만 적었다.
> 본문 원칙 문장은 한 글자도 완화하지 않았다.

---

## 0. 세 줄 요약

1. **상세페이지**는 이미지가 아니라 **웹 템플릿**이다. 관리자가 사진과 글만 넣으면 가격·마감 같은 값은 시스템이 자동으로 채운다.
2. **배송 추적**은 특정 택배 조회 업체에 묶이지 않는다. 공통 창구 뒤에 업체를 갈아끼우고, 외부 상태값을 우리 자체 상태로 옮긴 뒤에만 쓴다.
3. **자동 메시지**는 배송 완료를 방아쇠로 삼아 **알림톡 우선 → 실패 시 문자 대체**로 나간다. 한 사람에게 두 번 나가지 않는다.

세 가지의 공통 설계 원칙은 하나다. **외부 서비스와 브랜드에 종속되지 않게 만든다.**

## 1. 상품 상세페이지 템플릿

### 1-1. 왜 이렇게 만들었나

기존 방식(제조사가 준 세로로 긴 상세 이미지 한 장)의 문제는 이랬다.

| 문제 | 내용 |
|---|---|
| 브랜드 종속 | 제조사 로고·연락처가 이미지에 박혀 있다. 식당이 제조사에 직접 연락할 수 있다 |
| 수정 불가 | 가격이 바뀌면 이미지를 다시 만들어야 한다 |
| 검색 안 됨 | 이미지 속 글자는 검색 엔진이 읽지 못한다 |
| 확장 불가 | 상품이 늘어날수록 디자인 비용이 비례해서 늘어난다 |
| 일관성 없음 | 상품마다 제조사가 달라 화면 톤이 제각각이다 |

그래서 **틀은 하나, 내용만 바꾸는 방식**으로 간다.

### 1-2. 구조 (식자재 버전)

```
상품 상세페이지
├─ 첫 화면                 ← 사진·규격(옵션)·가격·수량·총액·CTA
├─ 01 왜 이 식자재인가       ← 설득 근거 — 원가율, 조리 시간, 회전율 (복사 가능한 문장)
├─ 02 어떤 매장에 맞는가     ← 업종, 규모, 객단가
├─ 03 산지·가공·보관·HACCP  ← 어떻게 만들었는지, 왜 믿을 만한지
├─ 04 실제 메뉴 적용 예시    ← 활용 사진
├─ 05 규격×수량 단가표       ← 규격×수량 가격표
├─ 06 발주 안내             ← 발주 마감·배송 요일·최소 주문
├─ 07 원산지·알레르기·유통기한 표 ← 원재료·원산지·보관·유통기한 (표 복사 가능)
└─ 08 자주 묻는 질문
```

### 1-3. 핵심 설계 세 가지

**(1) 입력값과 시스템값을 나눈다**

| 구분 | 내용 | 누가 채우나 |
|---|---|---|
| 입력값 | 사진, 핵심 한 줄, 제품 이야기(산지·가공·보관·HACCP), 활용 사진(메뉴 적용 예시), 상품 정보, 질문 | 관리자가 한 번 |
| 시스템값 | 가격, 수량별 단가, 발주 마감, 배송 요일, 배송·정산 안내, 사업자 정보 | 자동 |

**같은 값을 두 번 입력하지 않는다.** 가격을 고치면 상세페이지의 모든 숫자가 같이 바뀐다. 이미지 방식에서는 불가능하다.

**(2) 상품 → 옵션 상속**

식식이는 한 상품 안에 여러 규격이 있다. (예: 같은 품목의 1kg / 5kg / 박스)

- 사진·설명·원재료·원산지를 **상품에 한 번 넣으면 모든 옵션이 쓴다**
- 옵션에 따로 넣으면 **그 옵션만 자기 것을 쓴다**
- 따로 넣은 것을 지우면 **다시 상품 것으로 돌아간다**
- **칸 단위로 따로 정해진다.** 예: 5kg에 활용 사진만 넣으면 5kg은 그것만 자기 것, 나머지는 상품 것

**(3) 안 채운 칸은 통째로 감춘다**

빈 제목만 남는 화면이 안 나온다. 상품마다 채우는 정도가 달라도 모두 완성된 화면으로 보인다.

### 1-4. 섹션 대응표 (원문 → 식식이OS)

| 원문 섹션 | 식식이OS 섹션 |
|---|---|
| 왜 이 선물인가 | 왜 이 식자재인가 — 원가율, 조리 시간, 회전율 |
| 보내는 대상 | 어떤 매장에 맞는가 — 업종, 규모, 객단가 |
| 제품 이야기 | 산지·가공·보관·HACCP 등 신뢰 근거 |
| 활용 사진 | 실제 메뉴 적용 예시 |
| 옵션×수량 가격표 | 규격×수량 단가표 (그대로 쓸 수 있다) |
| 기업 구매 안내 | 발주 안내 — 발주 마감·배송 요일·최소 주문 |
| 상품 정보 표 복사 | 원산지·알레르기·유통기한을 엑셀로 복사 |

**식당 사장이 발주를 넣기 전에 확인하는 것**이, 원문에서 기업 구매 담당자가 견적을 받기 전에 확인하던 것과 구조적으로 같다.

> 이식 메모 — 식식이OS에는 원문의 "상품 → 옵션" 묶음 개념이 없다. `commerce_product_listings` 한 행이 한 규격(`spec`)이다.
> 그래서 "상품"은 새 묶음(상세페이지 템플릿)으로, "옵션"은 거기에 연결된 listing 으로 대응시킨다.
> 오늘 아침 만든 상세이미지 생성기(`ProductDetailImageGenerator`)는 **그대로 둔다.** 템플릿은 "새로운 상세페이지 방식"으로 나란히 추가된다.

## 2. 배송 추적

### 2-1. 가장 중요한 설계 원칙

**외부 택배 조회 업체에 코드가 묶이지 않는다.**

```
서비스 로직
     ↓
조회 창구 (공통 인터페이스)
     ↓
업체별 연결 ── 택배 조회 업체 / 다른 업체 / 관리자·공급자 수동 입력
```

바깥 코드는 창구 하나만 부른다. **어느 업체를 쓰는지 모른다.** 업체를 바꾸면 연결 파일 하나만 교체하면 되고, 주문·배송·메시지 흐름은 건드리지 않는다.

### 2-2. 외부 상태값을 그대로 쓰지 않는다

택배사와 조회 업체가 주는 상태값은 제각각이다. 그것을 그대로 서비스 로직에 박으면 업체 교체가 사실상 불가능해진다.

그래서 **자체 배송 상태 7단계**를 정의하고, 외부 값을 여기로 옮긴 뒤에만 쓴다.

```
송장 등록 전 → 배송 준비 → 집화 → 배송 중 → 배달 중
→ 배송 완료 / 확인 필요(지연·주소 오류·반송) / 조회 오류
```

**규칙 세 가지**
- **모르는 값은 "조회 오류"로 둔다.** 추측해서 "배송 완료"를 만들지 않는다
- **낮은 단계로 되돌아가지 않는다.** 조회 순서가 뒤집혀도 상태가 후퇴하지 않는다
- **업체가 준 원본 값도 함께 보관한다.** 나중에 옮기는 규칙을 고칠 때 필요하다

### 2-3. 중복 처리 방지

같은 배송 사건이 여러 번 들어와도 **한 번만 반영된다.** 중복 방지 키를 쓴다. 배송 완료가 메시지 발송의 방아쇠이기 때문에, 여기가 뚫리면 같은 식당에 메시지가 여러 번 나간다.

### 2-4. 운영 방식

- **자동 조회:** 정해진 시각에 주기적으로
- **수동 조회:** 관리자가 "지금 한 번 돌려보기"
- **자동 멈춤:** 조회 실패가 연속되면 스스로 멈추고 관리자에게 알린다. 업체 장애 때 무한 재시도를 막는다
- **택배사 조회 링크 병행:** 자동 상태와 별개로, 식당이 직접 택배사 페이지에서 볼 수 있는 링크도 제공한다

> 이식 메모 — 식식이OS는 이식 시점에 **택배 조회 업체가 연결되어 있지 않다.** 자동 조회·자동 멈춤·조회 링크는 업체 연결 시점의 일이다.
> 1단계는 2-6절대로 **관리자·공급자 수동 입력**을 같은 상태 체계에 넣는 경로부터 만든다. 창구(인터페이스)는 업체 연결을 전제로 지금 설계한다.

### 2-5. 왜 링크만으로는 부족한가

"송장번호 링크만 걸면 되지 않나"는 흔한 질문이다. 안 된다.

링크 방식은 **우리가 배송 상태를 모른다.** 100건이면 링크를 100번 눌러야 안다. 그러면 이런 것들이 전부 불가능하다.
- "배송완료 83 / 배송중 12 / 확인필요 5" 같은 현황판
- 미배송 주문만 골라 보기
- **배송 완료 시 자동 메시지 발송**

**조회 서비스를 쓰는 진짜 이유는 "상태를 시스템이 안다"는 것**이다.

### 2-6. 식자재에서의 적용

식자재는 택배보다 **직배송·새벽배송**이 많아서 차이가 있다.

- 택배 조회 업체가 커버하지 못하는 자체 배송은 **기사 앱이나 관리자 입력**으로 같은 상태 체계에 넣는다
- 중요한 건 **"상태를 정의하고 한 곳에서 판정한다"**는 구조다. 조회원이 택배사든 자체 기사든 상관없다
- 식자재는 **정시 도착이 곧 신뢰**다. "확인 필요" 목록이 원문(선물)보다 더 중요할 수 있다

## 3. 자동 메시지

### 3-1. 발송 흐름

```
배송 완료 확인
→ 자체 사건 발생 (delivery_completed)
→ 발송 조건 확인 (사용 켬 + 제외 아님 + 미발송 + 발송 모드)
→ 카카오 알림톡 시도
→ 성공 → 완료
→ 실패 또는 카톡 수신 불가 → 문자(SMS/LMS) 대체 발송
→ 최종 결과 저장
```

**핵심:** 메시지 쪽은 **어느 택배 조회 업체를 쓰는지 전혀 모른다.** `delivery_completed`라는 자체 사건 하나만 본다. 배송 업체를 바꿔도 메시지 로직은 그대로다.

### 3-2. 발송 대상을 한 곳에서만 판정한다

"누구에게 보낼 것인가"를 DB 함수 하나가 판정한다.

```
배송 완료됨 + 사용함 + 제외 아님 + 아직 성공 기록 없음
```

계산하는 곳이 여러 곳이면 어긋난다. 한 곳이므로
- 한 식당에 **두 번 나가지 않는다**
- **실패한 주문만** 다시 대상이 된다
- 배송 조회가 "완료"를 여러 번 알려도 **한 번만** 나간다

### 3-3. 발신 명의와 내용

식식이는 **한 채널로 여러 공급자의 메시지를 보낸다.**

- **발신 명의는 "식식이"로 통일** — 공급자마다 채널을 만들지 않는다
- **실제 보낸 사람은 메시지 안에 표시** — "보내는 분: OO식자재 (공급자)"
- 관리자가 설정하는 것: 사용 여부 / 발송 모드 / 보내는 분 표기 / 감사 메시지
- 템플릿을 고르고 수정하거나 직접 작성. **미리보기 제공**

### 3-4. 광고 금지 원칙

**공급자 명의로 나가는 메시지에 우리 판매 문구를 넣지 않는다.**

- "같은 상품을 특별가로" 같은 문구 금지
- 저장 단계에서 링크·전화번호·광고 단어를 **거절**한다
- 이건 브랜드 원칙이자, **알림톡 템플릿 심사 통과 조건**이기도 하다

### 3-5. 발송 결과 상태

| 상태 | 뜻 |
|---|---|
| 발송 대기 | 조건 충족, 승인 대기 (확인 후 발송 모드) |
| 발송 안 함 | 사용 끔 또는 제외 대상 |
| 카카오 성공 | 알림톡 전달 |
| 카카오 실패 → 문자 성공 | 대체 발송으로 전달 |
| 카카오 실패 → 문자 실패 | 둘 다 실패 |
| 전체 실패 | 번호 오류 등 발송 자체 불가 |

시도마다 채널·시각·결과·실패 사유·외부 메시지 번호를 기록한다. 관리자 화면에는 "전체 100건 / 전달 98 / 실패 2"가 보이고, **실패한 주문만 골라 재발송**할 수 있다.

### 3-6. 안전장치 5겹

실수로 잘못된 메시지가 나가는 것을 막는다. 순서대로 걸린다.

1. 발송 열쇠가 없으면 → 테스트 모드 (기록만)
2. 실제 발송 스위치가 꺼져 있으면 → 테스트 모드
3. 시험 배포 환경에서는 → 발송하지 않음
4. 알림톡 템플릿이 없으면 → 건너뛰고 문자로
5. 번호 형식이 이상하면 → 발송하지 않음

**기본값은 "확인 후 발송"이다.** 저절로 나가지 않고 담당자가 확인하고 누른다.

### 3-7. 식자재에서의 방아쇠

배송 완료 외에도 방아쇠가 많다.

| 방아쇠 | 메시지 |
|---|---|
| 발주 접수 | "주문이 접수되었습니다" |
| 출고 | "오늘 출고됐습니다. 내일 새벽 도착 예정" |
| 배송 완료 | "도착했습니다" |
| 결품 | "OO이 결품입니다. 대체품 안내" |
| 정산 | "이번 달 정산서가 나왔습니다" |
| 발주 마감 임박 | "오늘 오후 3시까지 발주하셔야 내일 받습니다" |

**구조는 그대로 쓸 수 있다.** 자체 사건 → 대상 판정 한 곳 → 알림톡 우선 → 문자 대체 → 결과 기록 → 실패자 재발송.

식자재에서 특히 값진 것은 **결품 알림**과 **발주 마감 알림**이다. 식당 사장이 가장 화나는 순간이 "당연히 올 줄 알았는데 안 온 것"이다.

> 이식 메모 — 3단계 범위는 **배송 완료 방아쇠 하나**다. 나머지 방아쇠는 같은 구조(자체 사건 → 판정 한 곳)에 사건 종류만 추가하면 된다.
> 알림톡 템플릿은 식식이 채널로 **따로 심사**받아야 한다(5절 2번). 심사 전에는 안전장치 4번에 따라 문자로 대체된다.

## 4. 공통 설계 원칙 (가장 중요한 부분)

세 가지 기능보다 **그 아래 깔린 원칙**이 이식 가치가 크다.

### 원칙 1. 외부 서비스는 공통 창구 뒤에 둔다

택배 조회, 메시지, 결제, 주소 검색 모두 같다. 업체가 가격을 올리거나 장애가 잦아지면 **연결 파일 하나만 바꾼다.** 서비스 로직은 그대로다.

### 원칙 2. 외부 상태값을 그대로 쓰지 않는다

반드시 자체 상태로 옮긴 뒤에 쓴다. **모르는 값은 추측하지 않고 "확인 필요"로 둔다.**

### 원칙 3. 판정은 한 곳에서만 한다

"누구에게 보낼 것인가", "발송 가능한가", "마감이 지났는가" 같은 판정이 여러 곳에 흩어지면 반드시 어긋난다. 한 곳에서 판정하고 화면은 따르기만 한다.

### 원칙 4. 같은 값을 두 번 입력하지 않는다

상품에 한 번 넣으면 옵션이 상속받고, 가격을 고치면 상세페이지가 따라간다. **입력 중복은 곧 데이터 불일치다.**

### 원칙 5. 시간은 한국 기준으로 한 곳에서 판단한다

서버가 해외에 있으면 한국 새벽 시간대에 날짜가 하루 어긋난다. 원문(선물답게)에서 실제로 9곳이 발견됐고, **만료된 견적으로 주문이 가능한 상태**였다.

### 원칙 6. 기본값은 안전한 쪽으로

- 메시지는 **확인 후 발송**이 기본
- 상품 등록은 **비공개**로 먼저
- 열쇠가 없으면 **테스트 모드**
- 삭제가 아니라 **보관**

> 이식 메모 — 원칙 2의 "모르는 값은 확인 필요로 둔다"와 2-2절 규칙의 "모르는 값은 조회 오류로 둔다"는 원문에서도 표현이 다르다.
> 원문을 바꾸지 않았다. 구현(1단계)은 **배송 상태 매핑에서는 2-2절(조회 오류)** 을 따른다 — 사용자 지시서도 조회 오류로 명시했다.

## 5. 이식할 때 검토할 것

1. **택배 조회 업체가 자체 배송을 커버하는가.** 식자재 직배송·새벽배송은 택배사 조회로 안 잡힌다. 기사 앱이나 관리자 입력을 같은 상태 체계에 넣는 설계가 필요하다.
2. **알림톡 템플릿은 서비스마다 따로 심사받아야 한다.** 채널·템플릿이 별개다.
3. **발송 비용.** 식자재는 발주 주기가 짧아 메시지 건수가 원문(선물)보다 훨씬 많다. 알림톡 단가 × 예상 건수를 먼저 계산해야 한다.
4. **상세페이지 템플릿은 업종에 맞게 칸을 다시 짜야 한다.** 구조는 같지만 칸 이름과 순서는 다르다. (1-2절이 식자재 버전으로 다시 짠 결과)
5. **코드 직접 이식보다 설계 이식이 현실적이다.** 두 서비스의 DB 구조가 다르므로, 원칙과 구조를 옮기고 구현은 각자 하는 편이 빠를 수 있다.

## 6. 식식이OS 이식 상태

원문 6절은 선물답게의 구현 상태였다. 그 상태를 식식이 이름으로 옮기면 사실이 아니게 되므로, 이 절은 **식식이OS 쪽 이식 상태**로 바꿔 적는다.

| 기능 | 식식이OS 상태 (이 문서 작성 시점) |
|---|---|
| 배송 추적 (1단계) | 이식 예정 — 수동 입력 경로부터. 택배 조회 업체 미연결 |
| 상세페이지 템플릿 (2단계) | 이식 예정 — 기존 상세이미지 생성기와 병행 |
| 자동 메시지 (3단계) | 이식 예정 — 1단계 완료 후. 알림톡 템플릿 미심사 → 테스트 모드/문자 대체 |
| 상품 → 옵션 상속 | 이식 예정 (2단계에 포함) |
| 한국 시간 통일 | 기존 코드에 KST 헬퍼가 부분적으로 있음. 이번 범위에서 새로 쓰는 날짜 판단은 KST 기준으로 한다 |

진행 결과는 `doc/transfer-audit-log.md`, 검증 결과는 `doc/transfer-verification-report.md`에 있다.
