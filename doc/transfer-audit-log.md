### 1-02. 기존 `commerce_orders.status`와의 관계 → 갈아엎지 않고 `delivery_status`를 나란히 얹음
- `status`는 결제·회계 흐름에 묶여 있다: `paid`→allocation 생성 + 플랫폼 입금 기록, `cancelled`→reversal, `refunded`→환불 경고(`actions/admin/commerce.ts updateCommerceOrderStatus`). 배송 단계를 여기에 섞으면 이 분기들이 흔들린다.
- **판단**: `status`는 한 글자도 안 바꾼다. 새 컬럼 `delivery_status`(NULL 허용)를 추가. 기존 주문은 NULL = "추적 시작 전"으로 남는다(1순위).
- 둘을 자동으로 맞추지 않는다(예: 배송 완료 → status completed 자동 전환 없음). 자동 전환을 넣으면 배송 입력 한 번이 회계 분기를 건드리게 된다. 관리자 주문처리 화면의 기존 버튼(준비 시작/배송 시작/수령 확인)은 그대로 동작한다.
- 배송 입력은 `status ∈ (paid, preparing, shipped, completed)`일 때만 받는다. 결제 전·취소·환불 주문은 거부.

### 1-03. 규칙을 어디서 강제하나 → DB 함수 하나 (`apply_commerce_delivery_event`)
- 원칙 3 "판정은 한 곳에서만". 앱 두 개(공급자·관리자 화면)와 앞으로 붙을 조회 업체가 모두 같은 함수를 부른다.
- 함수 안에서: 주문 행 `FOR UPDATE` 잠금 → 중복 키 확인 → 후퇴/완료 판정 → 이벤트 INSERT → 반영이면 UPDATE → 관리자 입력이면 `admin_logs` INSERT. **한 트랜잭션**(RULE-19, inquiries `match_inquiry_to_tenant`와 같은 구조).
- 규칙 세부:
  - **모르는 값 → `lookup_error`**: 앱(provider)이 옮기고, DB 함수가 체계 밖 값을 한 번 더 `lookup_error`로 막는다(이중 방어).
  - **후퇴 금지**: "이미 도달한 최고 진행 순위"보다 낮은 단계는 `ignored_regress`. 최고 순위는 **이벤트 행에서 매번 계산**한다(저장 안 함).
  - **예외 상태**: 완료 전 어느 단계에서든 들어갈 수 있다. 빠져나올 때는 이미 도달한 단계 이상으로만 — 예외를 거쳐 후퇴하는 우회를 막는다.
  - **배송 완료는 끝**: 이후 모든 입력은 `ignored_terminal`. 확인 필요로도 못 돌린다.
  - **원본 보관**: 무시된 입력도 `raw_status`·`raw_payload`와 함께 이벤트 행으로 남긴다.
- 알려진 한계(⚠️ 사장님 판단 필요): 관리자가 **실수로 "배송 완료"를 누르면 되돌릴 방법이 없다.** 원문 규칙(후퇴 금지)과 3단계 메시지 방아쇠 보호를 우선했다. 정정 기능이 필요하면 "정정 사유 + 메시지 발송 전일 때만" 같은 별도 경로로 추가하는 것이 안전하다 — 이번 범위에서는 만들지 않았다.

### 1-04. 중복 처리 방지 → 키 2겹 + 인덱스 1겹
1. `(commerce_order_id, dedupe_key)` UNIQUE — 같은 사건은 행이 하나. 같은 키 재전송은 처음 결과를 돌려주고 끝.
2. 수동 입력 키 = `manual:<제출 UUID>`. 화면이 버튼을 누를 때 쓰는 UUID는 **서버 응답을 받기 전까지 바꾸지 않는다** → 더블클릭·네트워크 재시도가 한 번만 반영. (storefront 주문의 `checkout_submission_id`와 같은 발상 — 2순위)
3. 업체 조회 키 = `provider:<id>:<송장>:<원본상태>:<시각>` — 결정적이라 같은 조회 결과가 몇 번 와도 같다.
4. 마지막 벽: `mapped_status='delivered' AND outcome='applied'` partial unique index → 적용된 배송 완료는 주문당 1행만 존재 가능. 앱 버그가 있어도 메시지 방아쇠가 두 번 생기지 않는다.

### 1-05. 가드 트리거 추가 (지시서에 없던 것 — 추가 판단)
- 발견: `commerce_orders`의 기존 RLS `commerce_orders_tenant`는 구매자(식당)에게 **FOR ALL**이다. 판정 함수만 막아도 식당 세션이 PostgREST PATCH로 `delivery_status='delivered'`를 직접 쓸 수 있다. 3단계에서 그게 메시지 방아쇠가 된다.
- **판단**: `delivery_status`는 판정 함수 안에서만 바뀌게 BEFORE UPDATE/INSERT 트리거로 막는다(함수가 트랜잭션 한정 설정값을 켜고 쓴다). 기존 코드는 이 컬럼을 쓰지 않으므로 기존 흐름 영향 없음 — PGlite에서 `status` 변경이 가드에 안 걸리는 것까지 확인했다.
- 판정 함수 EXECUTE는 `service_role`에만. anon/authenticated는 REVOKE.
- 기존 RLS 자체(식당이 자기 주문 `status`를 바꿀 수 있는 것)는 **이번 범위 밖이라 손대지 않았다.** 기존 감사 문서 범위의 문제다.

### 1-06. 조회 창구(공통 인터페이스) 구조
```
화면(관리자 / 공급자)
   ↓ server action (권한·스코프 확인)
src/lib/delivery-tracking/gateway.ts  recordDeliveryObservation()   ← 창구: 이것만 부른다
   ↓ provider.mapRawStatus()  (provider.ts — manual_admin / manual_supplier, 업체는 여기에 추가)
   ↓ rpc apply_commerce_delivery_event()   ← 판정
```
- 택배 조회 업체가 생기면 `DeliveryTrackingProvider`를 구현한 파일 1개 + `PROVIDERS` 등록 1줄. 주문·화면·메시지 코드는 그대로.
- 자동 조회·자동 멈춤(원문 2-4)은 업체가 없어 **만들지 않았다**. 인터페이스에 `fetchEvents?` 자리만 뒀다.
- 택배사 조회 링크(원문 2-4 병행 링크)도 **만들지 않았다**: 택배사별 조회 URL 형식을 이 환경에서 확인할 방법이 없어, 추측으로 링크를 만드는 것은 원칙 2(추측 금지)에 어긋난다. 송장번호는 화면에 그대로 보여준다.

### 1-07. 공급자 입력 권한 — "단독 공급 주문만"
- 공급자는 `commerce_orders`를 RLS로 못 읽는다. 공급자 화면은 service role로 읽되 `commerce_order_allocations.supplier_tenant_id = 로그인 공급자`로 스코프를 건다.
- 배송 상태는 **주문 단위 하나**다. 공급자 A·B가 따로 보내는 주문에서 A가 "배송 완료"를 누르면 B 몫까지 완료로 보이고 메시지가 나간다.
- **판단**: 취소 안 된 allocation이 전부 자기 것인 주문만 입력 가능. 여러 공급자 주문은 공급자에게 읽기만 주고 관리자가 입력한다(보수적). 품목(allocation) 단위 배송으로 쪼개는 것은 테이블 구조가 커져 이번 범위에서 하지 않았다.
- 권한 판정은 `resolveSupplierOrderAccess()` 한 함수에서만 한다(목록 표시용 `sole_supplier`도 같은 기준).
- allocation이 없는 주문(공급자 식별 실패 — 기존에도 있는 경우)은 공급자 화면에 안 보이고 관리자 화면에서만 입력된다.

### 1-08. 계산값 저장 금지 적용
- 저장하지 않은 것: `delivered_at`, "마지막 갱신 시각", "도달한 최고 단계" — 전부 이벤트 행에서 같은 값으로 다시 구해진다(RULE-00).
- 저장한 것: `delivery_status`(현재 상태 — `status`와 같은 성격, 후퇴 금지를 쓰기 시점에 강제하려면 필요), 이벤트의 `outcome/status_before/status_after`(쓰는 순간의 판정 사실. 나중에 규칙이 바뀌어도 당시 판단이 남아야 한다 — append-only 기록).
- `commerce_orders.updated_at`은 배송 입력 때 **건드리지 않는다**. 결제·회계 쪽 "주문 변경" 신호와 섞지 않기 위해서다.

### 2-02. 입력값 / 시스템값 분리

### 2-03. 칸 단위 상속 규칙 — 판정은 한 함수(`resolveDetailFields`)
- 옵션 값 → 상품(템플릿) 값 → 비어 있음(숨김). 칸 하나 = 컬럼 하나라 칸마다 따로 결정된다.
- "지우면 복귀"를 확실히 하려고 **빈 값은 NULL 한 가지 모양만** 허용했다. 빈 문자열·빈 배열·빈 JSON 배열은 DB CHECK로 거부하고, 저장 액션도 `normalizeFieldValue`로 먼저 NULL로 바꾼다. 빈 문자열을 허용하면 "옵션에 빈칸을 넣어 상품 값을 가림"과 "옵션에 안 넣음(상속)"이 섞인다(inquiries의 boolean+note 분리와 같은 이유).
- 관리자 화면은 칸마다 「옵션 자기 값 / 공통 값 사용 / 비어 있음 — 식당 화면에서 숨김」 배지를 보여주고 「공통 값으로 되돌리기」 버튼을 둔다. 배지도 같은 `resolveDetailFields` 결과로 그린다.

### 2-04. 옵션 값이 이미 listing에 있는 칸 → 링크 테이블에 칸을 또 만들지 않음
- 발견: 원산지(`origin`)·알레르기(`allergen`)·보관(`storage_method`)·원재료(`ingredients`)·상세 이미지(`image_urls`)는 **listing에 이미 있다**. listing 한 행 = 옵션이므로 이게 곧 "옵션에 따로 넣은 값"이다.
- 링크 테이블에 같은 칸을 또 두면 옵션 원산지를 두 곳에 입력하게 된다(원칙 4 위반). 두 값이 다르면 기존 첫 화면(listing `origin` 표시)과 07 표가 서로 다른 원산지를 보여준다 — **법적 표기 항목이라 특히 위험**.
- **판단**: 이 5칸은 `optionSource='listing'` — listing 기존 칸이 채워져 있으면 그것, 비어 있으면 템플릿 값. 옵션 값을 바꾸거나 비우는 곳은 기존 상품 수정 화면이다. 유통기한은 listing에 칸이 없어 링크 테이블에서만 받는다.
- 결과적으로 기존 상품 수정 화면·기존 데이터는 한 줄도 바뀌지 않고, 템플릿이 "비어 있는 칸만" 채운다.

### 2-05. 06 발주 안내의 마감·배송 요일 — 시스템 출처가 없었다
- 발견: storefront에 발주 마감 시각·배송 요일 데이터가 **어디에도 없다**(두 레포 grep, `rfq.delivery_days`는 RFQ 입찰용이라 다름).

- "오늘 주문하면 언제 도착" 같은 날짜 계산은 **만들지 않았다**. 휴무일·공휴일 규칙이 없는 상태에서 도착일을 계산하면 추측이 된다(원칙 2). 마감 시각과 요일만 사실대로 보여준다.

- 완료: 2026-09-15 00:38 (커밋은 이 섹션과 같은 커밋)

### 3-01. `delivery_completed` 자체 사건 — DB 트리거가 만든다
- `commerce_orders.delivery_status`가 처음 `delivered`가 되는 순간 AFTER UPDATE 트리거가 `commerce_domain_events`에 1행을 넣는다. `(event_type, commerce_order_id)` UNIQUE → 주문당 1번.
- 왜 트리거인가: 1단계 판정 함수(배송 추적) 코드에 "사건을 만들어라"를 넣으면 배송 쪽이 메시지의 존재를 알게 된다. 원문 3-1 "메시지 쪽은 배송 업체를 모른다"의 반대 방향(배송 쪽도 메시지를 모름)까지 지키려고, 사건 생성은 **상태 변화 자체**에 걸었다. `delivery_status`는 1단계 가드 때문에 판정 함수로만 바뀌므로, 트리거가 곧 "판정 함수가 완료를 반영했다"와 같다.
- 사건 행에는 주문 id·식당 tenant·시각만 있다. 택배사·조회 업체·원본 상태값은 **넣지 않았다**(검증 M-5에서 메시지 모듈이 배송 조회 코드를 import하지 않는 것까지 확인).
- 사건 이름을 `commerce_domain_events.event_type` CHECK로 둔 이유: 원문 3-7의 결품·발주 마감 같은 다음 사건이 같은 테이블·같은 처리 입구(`lib/domain-events/drain.ts`)에 붙게 하기 위해서다. 이번 범위는 `delivery_completed` 하나.

### 3-02. 발송 대상 판정 — DB 함수 하나 `delivery_message_targets()`
- "배송 완료됨 + 사용함 + 제외 아님 + 아직 성공 기록 없음"을 이 함수만 계산한다. 배송 완료된 주문마다 `eligible`과 `ineligible_reason`(`not_active_order / disabled / excluded / already_sent / sending`)을 돌려준다.
- 사건 처리(`process_delivery_completed_events`)·발송 잡기(`claim_…`)·관리자 화면 목록·실패 재발송이 **전부 이 함수 결과를 그대로 쓴다.** 앱 코드에 대상 조건을 다시 쓴 곳이 없다.
- 추가한 조건 1개(⚠️ 원문에 없음): 배송 완료 뒤 **취소·환불된 주문은 제외**(`not_active_order`). 환불한 식당에 "도착했습니다, 감사합니다"가 나가는 것을 막기 위해서다.
- "한 번만"을 세 겹으로: ① 사건 UNIQUE ② 성공 기록이 있으면 `already_sent` ③ `claim_delivery_message_dispatch`가 주문 행을 잠그고 `sending`으로 바꾼 한 요청만 발송 — 동시에 두 번 눌러도 외부 호출 1번(검증 M-6).
- 테스트 모드 기록(`test_simulated`)은 **성공으로 치지 않는다.** 테스트로 한 번 돌렸다고 실제 발송 때 빠지면 안 되기 때문이다.

### 3-03. 설정 주체와 명의
- 설정 주체는 **관리자**(0-03 보수적 판단). 공급자 화면에는 이번에 아무것도 추가하지 않았다.
- 설정 행: `scope_tenant_id = 플랫폼 sentinel`(기본값) 또는 공급자 tenant(그 공급자가 **단독**으로 보내는 주문에만). 공급자 행이 있으면 기본값을 **행 단위로 대체**한다(칸별 상속 아님 — 사용 여부·모드·문구가 섞여 예측하기 어려워지는 것을 피했다).
- 명의: 첫 줄 `[식식이]` + 발신번호는 기존 플랫폼 번호(SOLAPI_SENDER)로 통일. 본문 「보내는 분」 = 설정의 표기 → 단독 공급자 상호 → 「식식이」 순.
- 공급자가 둘 이상인 주문은 보내는 분을 특정 공급자로 쓰지 않는다(1단계 1-07과 같은 이유).
- 기본값: 설정 행이 없으면 발송 안 함 / 행을 만들어도 `enabled=false`, `send_mode='manual_confirm'`(원칙 6).
- 제외 대상은 식당 단위. 해제는 행을 지우지 않고 `released_at`을 남긴다(보관).

### 3-04. 알림톡 우선 → 문자 대체 — `message.ts`는 건드리지 않음
- 문자: 오늘 리드 문자에서 만든 `lib/solapi-admin.ts sendSolapiText`를 **그대로 재사용**(같은 열쇠·같은 발신번호·같은 SMS/LMS 판정). `actions/message.ts`는 tenant·customer에 묶여 있어 쓰지 않았고 **수정도 0줄**(검증 M-5에서 git diff로 확인).
- 알림톡: `lib/delivery-message/channels.ts` 신규. 같은 솔라피 SDK에 `kakaoOptions`만 더한다. 솔라피 자체 대체발송은 `disableSms: true`로 끄고, 대체 발송은 우리가 결과를 기록하며 직접 한다(시도마다 채널·시각·결과·실패 사유·외부 번호를 남기려면 필요).
- 채널은 인터페이스(`DeliveryMessageChannels`)로 받는다 → 원칙 1(외부 서비스는 창구 뒤). 검증은 가짜 채널로 모든 분기를 돌렸다.
- 결과 상태는 원문 3-5절 표 그대로 + 두 개: `sending`(발송 중 — 잡고 있는 상태), `test_simulated`(테스트 모드 기록).
- 알림톡 템플릿 원문은 `ALIMTALK_TEMPLATE_TEXT` 한 곳에 두고 관리자 화면에서 볼 수 있게 했다. 문자 대체도 같은 틀에 값을 채우므로 두 채널 내용이 같다. **템플릿 심사는 사장님이 직접 받아야 한다**(원문 5-2).

### 3-05. 안전장치 5겹 (`lib/delivery-message/safety.ts`)
| 순서 | 조건 | 결과 |
|---|---|---|
| 1 | SOLAPI 열쇠 없음 | 테스트 모드(기록만) |
| 2 | `DELIVERY_MESSAGE_LIVE_SEND`가 정확히 `true`가 아님 | 테스트 모드 |
| 3 | `VERCEL_ENV=preview` | 테스트 모드 |
| 4 | `SOLAPI_KAKAO_PF_ID`·`SOLAPI_KAKAO_TEMPLATE_DELIVERY_COMPLETED` 중 하나라도 없음 | 알림톡 건너뛰고 문자 |
| 5 | 휴대전화(01X) 형식 아님 | 발송 안 함(`failed`) |
- **현재 운영 환경에는 `DELIVERY_MESSAGE_LIVE_SEND`가 없으므로, 이 코드가 배포·마이그레이션되어도 실제 문자는 한 통도 나가지 않는다.** 켜는 것은 사장님 결정이다.
- 5번을 휴대전화만으로 좁힌 이유: 알림톡·문자 모두 유선번호로는 전달되지 않는다. `shipping_phone`에 유선번호가 들어 있으면 "전체 실패"로 남아 관리자가 볼 수 있다.

### 3-06. 광고 금지 — 저장 단계에서 거절 (`findContentViolation`)
- 설정 저장 액션이 「보내는 분 표기」·「감사 메시지」를 검사하고, 걸리면 **저장하지 않고 이유를 돌려준다**. 미리보기도 같은 함수로 막힌 이유를 보여준다.
- 거절 대상: 링크(http/www/도메인/단축 URL) · 전화번호(휴대·지역·1588류) · 광고성 단어(특가·할인·쿠폰·이벤트·1+1·무료·최저가 등 목록).
- 시스템이 채우는 부분(주문번호 등)은 검사하지 않는다 — 주문번호 `ORD-20260915-12345`가 전화번호 패턴에 걸리기 때문이다. 관리자가 입력하는 칸만 검사한다.
- ⚠️ 한계: 단어 목록 방식이라 우회 표현(예: "특 가")은 못 막는다. 알림톡은 템플릿 심사가 한 번 더 막는다. 목록은 `AD_WORDS` 한 곳에서 늘린다.

### 3-07. 처리 시점 — 누가 사건을 깨우나
- ① 배송 상태 입력 액션(관리자·공급자): 배송 완료가 **처음** 반영된 직후 `drainDomainEvents`를 부른다. 실패·예외는 로그만 남기고 배송 입력은 성공으로 돌려준다(사건 행이 남아 있으므로).
- ② 관리자 「지금 한 번 돌려보기」 버튼.
- ③ `/api/cron/domain-events` 라우트 — **작성만 하고 `vercel.json`에 등록하지 않았다.** 배포 설정 변경은 사장님 승인 사항이다(billing-renewal과 같은 CRON_SECRET 방식).
- 배송 액션이 메시지 규칙을 아는 것은 아니다: 액션은 "사건 처리기를 깨워라"만 부르고, 무엇을 보낼지는 DB 판정 함수가 정한다.

### 3-08. 알려진 한계 (사장님 확인 필요)
1. **발송 중 멈춤**: 외부 발송 직후 결과 기록(`finish`)이 실패하면 그 건은 `sending`에 남고 자동 재발송 대상에서 빠진다. 실제로 나갔는지 모르는 상태에서 다시 보내면 두 번 나갈 수 있어 **중복 방지를 우선**했다. 관리자 화면 현황에 「발송 중(확인 필요)」 건수로 보인다. 풀어주는 버튼은 만들지 않았다.
2. 관리자 현황판은 배송 완료된 주문 전체를 한 번에 읽는다. 건수가 수천을 넘으면 페이지 나누기가 필요하다.
3. 발송은 건마다 claim·외부 호출·finish를 한다(발송 루프라 조회 N+1과 성격이 다름). 한 번에 최대 50건.
4. 발송 비용(원문 5-3): 식자재는 주문 주기가 짧다. 알림톡 단가 × 월 배송 완료 건수 계산은 하지 않았다 — 운영 건수 조회가 필요한데 운영 DB를 읽지 않기로 했기 때문이다.
