# combination-ideas.md — 기존 기능 조합 아이디어 (6단계)

- 작성일: 2026-09-09
- 성격: **강제 사항 아님.** 3~5단계에서 확인한 **이미 있는 자산**만 조합했다. 새로 만들어야 하는 것은 7단계(`missing-features-report.md`)로 넘겼다.

## A. 지금 끊긴 연결을 잇기만 해도 새 기능이 되는 것

> 5단계에서 찾은 단절 지점을 잇는 조합이다. **새로 만드는 게 아니라 이미 있는 두 쪽을 연결**하는 것이라 효과 대비 비용이 가장 좋다.

### K-01 · 🔥 공급자 정산 대시보드 — "이번 달 내가 받을 돈"
**조합**: 커머스 주문(`commerce_orders` 9) + 배분(`commerce_order_allocations`) + 지급원장(`supplier_payables`) → **공급자OS에 새 화면 1개**

| | |
|---|---|
| **왜** | 지금 공급자는 **자기 상품이 얼마나 팔렸는지 볼 방법이 없다.** 관리자OS `/admin/commerce/payables`에만 있고 공급자는 접근 못 한다 |
| **난이도** | **중간** — 선행조건이 진짜 일 |
| **선행조건** | 🔴 `commerce_product_listings.supplier_tenant_id` **36/38 미지정을 채워야 한다**(5단계 C-18). 이걸 채우면 배분·지급원장이 자동으로 생긴다 |
| **효과** | 🔥 **공급자가 플랫폼에 남을 이유**가 생긴다. 지금은 상품만 올려두고 아무 피드백이 없다 |
| **재료** | `admin/supplier-payables.ts`(이미 있음) 의 조회를 공급자 tenant 기준으로 감싸면 됨 |

### K-02 · 🔥 식당 ↔ 공급자 계정 연결 → 재구매 자동 제안
**조합**: `customers.linked_tenant_id` 채우기 + 공급자OS 영업스케쥴(`sales_schedules`) + 식당OS 구매 이력

| | |
|---|---|
| **왜** | 지금 `customers.linked_tenant_id`가 **0/142**다. 공급자는 거래처가 식당OS에서 무엇을 사는지 모르고, 식당은 공급자OS의 자기 원장을 못 본다 |
| **난이도** | **중간** (연결 UI + 매칭 규칙) |
| **효과** | 🔥 이게 이어지면 **"이 식당이 지난달 산 것 중 이번 달에 안 산 것"** 을 자동으로 뽑을 수 있다. `sales_schedules`(현재 1행)가 비로소 의미를 갖는다 |
| **재료** | 사업자번호(`tenants.biz_number`) 매칭 → 승인 흐름. 공급자OS `/customers/[id]/edit`에 "식당OS 계정 연결" 버튼 |
| **주의** | 두 tenant를 잇는 것이므로 **RLS 설계가 선행**돼야 한다 (4단계 G-01의 `order_lines` 비대칭이 여기서 터진다) |

### K-03 · ⚡ 식당OS "내 거래처" 화면을 `suppliers` 없이 되살리기
**조합**: 기존 `orders`·`commerce_orders` 이력 → 거래처 목록을 **집계로 생성**

| | |
|---|---|
| **왜** | `/suppliers` 3화면이 **테이블이 없어 작동 안 함**(4단계 F-03). 그런데 「내가 누구한테 샀는지」는 이미 `orders.seller_tenant_id`·`commerce_orders`에 있다 |
| **난이도** | **간단** — 테이블 신설 없이 조회만 바꾸면 됨 |
| **효과** | ⚡ 죽은 화면 3개가 살아난다. 1차 조사 `C-03`(테이블 만들 것인가 통합할 것인가)에 **제3의 답**을 준다 |
| **주의** | 수기 등록(`/suppliers/new`)은 포기해야 한다. 거래 이력이 없는 거래처는 못 만든다 |

### K-04 · ⚡ 명세서 OCR → 공급자OS 상품 원가 자동 갱신
**조합**: 식당OS 명세서 OCR(`order-capture.ts`, `import.ts`) + `price_history` + 공급자OS `product_costs`

| | |
|---|---|
| **왜** | 식당이 올린 명세서 사진에는 **실제 거래 단가**가 들어 있다. 지금은 식당OS 안에서만 쓰이고(그나마 0행) 공급자OS 원가 관리와 무관하다 |
| **난이도** | **중간** |
| **효과** | ⚡ 1차 조사가 지적한 **「원가 미확정 라인 64/522(12.3%)」** 문제의 실제 해결책이 될 수 있다. 사람이 원가를 입력하는 대신 명세서에서 뽑는다 |
| **선행조건** | 식당OS 식자재 기능의 3중 장벽 해소(5단계 §4) — 컬럼·RLS·데이터 |

## B. 이미 있는 엔진에 데이터만 넣으면 도는 것

### K-05 · 🔥 가격 정책을 실제로 쓰기 — 거래처별 단가 245건을 정책으로 승격
**조합**: 공급자OS `customer_product_prices`(**245건, 실사용 중**) → 관리자OS `pricing_policies`(0행) → 결제 경로 DB함수

| | |
|---|---|
| **왜** | 결제 경로가 이미 `fetch_active_pricing_policies_for_checkout`를 호출하는데 **테이블이 0행**이다(5단계 §6). 반면 공급자OS에는 거래처별 단가가 **245건이나 쌓여 있다** |

| **효과** | 🔥 커머스에서 **단골 식당에게 다른 가격**을 줄 수 있다. 지금 관리자OS 가격정책 화면은 만들어도 효과가 안 보인다 |
| **주의** | 🔴 1차 조사 `I-06`(할인 역산으로 원가 유출)과 직결. `69e7dc2`가 그 경로를 막았으므로 **그 위에서** 설계해야 한다 |

### K-06 · ⚡ 신뢰도 엔진에 첫 입력 주기 — 감사로그 455건 + 주문 284 + 수금 260
**조합**: `admin_logs`(455) + `orders`(284) + `payments`(260) + `contact_logs` → `trust_scores`(현재 0)

| | |
|---|---|
| **왜** | `trust-engine.ts`가 **11개 테이블을 다루는 완성된 코드**인데 `trust_scores`·`trust_score_logs`·`relationships`가 **전부 0행**이다. 한 번도 안 돌았다 |
| **난이도** | **간단** — 배치 1회 실행이면 초기 점수가 생긴다 (단, **쓰기 작업**이라 이번 조사 범위 밖) |
| **효과** | ⚡ `/admin/trades`(이상거래) `/admin/participants`(참여자) `/admin/settlements`(정산) **3화면이 동시에 살아난다** |
| **주의** | 점수 산식이 타당한지 먼저 확인해야 한다. 잘못된 점수로 정산을 막으면 사고다 |

### K-07 · ⚡ 자금 배분 규칙 1개만 넣어도 `/funds` 2화면이 산다
**조합**: `accounts`(1) + `account_purposes`(7) + `generate_fund_transfers` DB함수 → `fund_rules`(현재 0)

| | |
|---|---|
| **왜** | 계좌와 목적은 이미 등록돼 있는데 **규칙이 0행**이라 배분이 한 번도 안 일어났다 |
| **난이도** | **간단** |
| **효과** | ⚡ 죽어 있는 화면 2개가 산다. 다만 소규모라 실효는 제한적 |

### K-08 · 💡 현장 관찰기록 → 리드 전환 → 프로모션 자동 발급
**조합**: `field_observations`(3건, 🚧 화면 미배포) + `sales_leads` + `admin/sales-promo.ts` + `coupons`

| | |

## G. 이 문서를 쓰면서 든 판단 (기록)

- **조합 아이디어의 절반 이상이 "이미 있는 두 기능을 잇는 것"이다.** 새 기능을 만드는 것보다, 3~5단계에서 확인한 **단절 지점을 잇는 쪽이 비용 대비 효과가 크다.**
- **가장 큰 제약은 기술이 아니라 데이터다.** ⚫ 빈 껍데기 37화면(4단계)이 말해주듯, 코드는 대부분 완성돼 있고 **입력이 없다.** K-01·K-05·K-06이 전부 "데이터를 넣으면 도는" 유형인 이유다.
- **커머스 규모(리스팅 38)가 병목이다.** 리스팅이 수백 개가 되면 K-01·K-05·K-10·K-13이 전부 의미를 갖는다. 그전까지는 어떤 조합도 효과 측정이 어렵다.
- 이 문서는 **어느 것도 구현하지 않았다.** 전부 제안이다.

## J. §G 판단 기록에 추가

- **조합안을 쓸 때 선행조건을 "그럴 것이다"로 적었다.** 이번에 전부 실측했고, **판단이 뒤집힌 것은 없었다.** 다만 K-04는 원인이 특정돼 난이도가 내려갔고, K-18이라는 빠진 조각이 드러났다.
- **가장 유용했던 확인은 참조 무결성이었다.** "끊겼다"가 「데이터 손상」이 아니라 「미입력」임을 확정하니, 조합안 대부분의 선행 비용이 크게 낮아졌다.
- K-18은 **조합 아이디어라기보다 빠진 부품에 가깝다.** 그럼에도 여기 적은 이유는, `K-08`(관찰기록 퍼널)이 이것 없이는 성립하지 않기 때문이다.
