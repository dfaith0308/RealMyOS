## A. 개발·운영 안전장치 — 지금 가장 시급하다

### X-01 · 🔴 **자동화 테스트가 한 개도 없다**

| 확인 항목 | RealMyOS | restaurant-os |
|---|---|---|
| 테스트 파일 (`*.test.*`, `*.spec.*`) | **0** | **0** |
| 테스트 프레임워크 (vitest/jest/playwright) | **없음** | **없음** |
| `package.json` scripts | `dev / build / start / lint` | 동일 |
| CI (`.github/workflows/`) | **없음** | **없음** |

**왜 문제인가 — 이번 조사에서 실제로 관측된 결과**
- 1단계 §5-3: **검증 흔적이 없는 높은 위험 코드(결제 상한·원가 분리·접근 차단)가 이미 운영에 나갔고, 잘 검증된 낮은 위험 코드는 배포 대기 중이다.**
- `8e40059`: role 게이트를 넣고 **45분 만에** 핫픽스. 테스트가 있었으면 `role NULL` 케이스가 배포 전에 걸렸다.
- `f247b21`: "상한 없이 int4 범위 초과값이 **DB까지 내려갔다**". 경계값 테스트 1개면 막혔다.
- 검증은 지금 **`.tmp-e2e/`·`.tmp-shots/`의 수동 스크린샷**으로 대체되고 있고, 그마저 09-07(RealMyOS)·08-26(restaurant-os) 이후 끊겼다.

**최소 제안**: 전면 도입이 아니라 **돈을 만지는 경로만** 먼저. `lib/analytics-calc.ts`, `lib/buy-discount.ts`, `lib/commerce-constants.ts`(상한 판정), `lib/subscription-renewal.ts` — 전부 순수 함수라 테스트가 쉽다.

### X-02 · 🔴 **스키마 계약 검증이 없다**
1차 조사 `I-01`과 같은 내용이며 **여전히 없다.** 이번 4단계에서 운영(main)에 **10건**의 코드↔스키마 불일치가 그대로 살아 있음을 라이브 쿼리로 확인했다.
`supabase db query` 통로가 열려 있으므로(2단계 §5) **CI 없이 `npm run check:schema` 스크립트 하나로도 가능하다.**

### X-03 · 🟠 **배포 전 체크리스트·환경변수 검증이 없다**
1단계 「묶음 I」(토스 단건결제 키 분리)는 **코드만 머지하면 운영 결제가 전부 실패**할 수 있다. 그런데 Vercel 환경변수가 준비됐는지 확인하는 절차가 없다.
`.env.example`은 있지만 **운영에 실제로 그 키가 있는지 검증하는 것은 없다.**

### X-04 · 🟠 **브랜치·배포 상태를 볼 방법이 없다**
1단계에서 확인했듯 `main`/`dev`가 **체리픽으로 갈라져 있고**, 로컬 `main`은 낡아 있었으며, **트리 차이를 직접 계산해야만** 무엇이 미배포인지 알 수 있었다.
→ "지금 운영에 없는 게 뭐냐"를 한 명령으로 답하는 스크립트가 없다.

## B. 커머스가 커머스로 성립하기 위해 없는 것

### X-05 · 🔴 **재고(수량) 개념이 없다**
`commerce_product_listings`에 재고·수량 컬럼이 없다(코드 검색 `stock|inventory|quantity_available` → **0건**).

| 결과 | |
|---|---|
| 품절 표시 불가 | 없는 물건을 계속 팔 수 있다 |
| 주문 후 취소 발생 | 공급자가 "없어요"라고 하면 수동 처리 |
| 대량 주문 통제 불가 | 재고 100개인데 1000개 주문이 들어와도 막을 수 없다 |

리스팅 38건 규모에서는 수동으로 감당되지만, K-16(AI 상품 자동 등록)으로 수백 건이 되면 **가장 먼저 터진다.**

### X-06 · 🔴 **배송 상태·송장 추적이 없다**
- `commerce_orders.status` 실측값 = **`completed`, `pending_payment` 2가지뿐**
- 송장번호·택배사 컬럼 없음 (`tracking_number|송장|courier` 검색 → **0건**)
- 🚧 `BuyOrderTimeline`(미배포)의 "3단계"는 결제·주문 상태를 표시할 뿐 **실제 배송 추적이 아니다**

식자재는 **당일·익일 배송이 핵심**인 품목이다. "언제 오는지 모른다"는 식당 입장에서 치명적이다.

### X-07 · 🟠 **식당이 받는 반품·취소 경로가 없다**
- 관리자OS에는 `admin/commerce-reversal.ts`(주문 취소·환불)가 있다
- 🚧 식당OS `BuyOrderCancelSection`은 **미결제 주문만** 취소 가능(미배포)
- **결제 완료 후 반품·부분취소·환불 요청 경로가 식당 쪽에 없다.** 카카오 문의(🚧 미배포)로 사람에게 말하는 수밖에

### X-08 · 🟠 **리뷰·평점이 없다**
어떤 테이블에도 리뷰·평점이 없다. 커머스에서 **구매 판단 근거가 가격뿐**이다.
공급자 입장에서도 좋은 평판을 쌓을 방법이 없다 — `trust_scores`가 있지만 **관리자 전용이고 0행**이다.

### X-09 · 🟠 **재주문(같은 걸 또 사기)이 한 번에 안 된다**
`/buy/orders/[id]`에 "다시 담기"가 없다. 식자재는 **같은 것을 반복 구매**하는 품목인데, 매번 검색 → 상세 → 담기를 다시 해야 한다.
> 재료는 다 있다: `commerce_order_items`에 이전 주문 항목이 있고 `cart_items`에 담기만 하면 된다. **난이도 간단.**

### X-10 · 💡 **정기배송·구독 주문이 없다**
"매주 화요일 배추 10kg" 같은 반복 주문이 없다. 식자재 B2B에서 흔한 형태다.
`subscription-renewal.ts`(🚧)는 **플랫폼 이용료 구독**이지 상품 정기배송이 아니다.

## C. 공급자가 이 플랫폼에 남을 이유가 없다

> 3단계 기능 맵에서 확인한 것: **공급자OS(`(app)`)에 `commerce` 라우트가 아예 없다.**
> 커머스 리스팅 등록·수정·가격 설정은 **전부 관리자OS에만** 있다.

### X-11 · 🔴 **공급자가 자기 상품을 커머스에 직접 올릴 수 없다**
```
공급자OS (app) 라우트: analytics customers dashboard disbursements funds
                        ledger orders payments products purchases quotes rfq sales settings subscribe
                        → commerce 없음
```
공급자는 `/products`에 상품 199건을 갖고 있지만, 그걸 커머스 리스팅(38건)으로 만드는 건 **관리자가 대신 해줘야 한다.**
→ 이것이 **리스팅이 38건에서 안 늘어나는 구조적 이유**로 보인다(6단계 §G의 "커머스 규모가 병목").

### X-12 · 🔴 **공급자가 자기 정산을 볼 수 없다**
5단계에서 확인: `supplier_payables` **0행**, 그리고 조회 화면은 관리자OS `/admin/commerce/payables`에만 있다.
공급자는 **"내 상품이 얼마 팔렸고 언제 얼마를 받는지"를 볼 방법이 전혀 없다.** → 6단계 K-01

### X-13 · 🟠 **공급자용 알림이 없다**
- 주문이 들어와도 공급자에게 가는 알림이 없다 (`notifications` **0행**, RFQ 알림 모듈은 있으나 미사용)
- 푸시는 식당OS 쪽에만 구독 흐름이 있다(`push_subscriptions` 3건)

### X-14 · 🟠 **공급자OS가 모바일을 고려하지 않았다**
- 식당OS: 하단 탭 5개 + Android TWA + 푸시 → **모바일 전제**
- 공급자OS: 좌측 사이드바 14그룹 → **PC 전제**
공급자(배송기사·사장)가 현장에서 주문을 확인해야 하는데 그 화면이 PC용이다.
> 09-07에 `_probe-admin-mobile.ts`·`admin-mobile-products.png` 같은 모바일 확인 흔적이 있으나 **관리자OS 일부에 국한**된다.

## D. 식당 사용자의 일상 불편

### X-15 · 🟠 **내가 뭘 얼마에 샀는지 한눈에 볼 곳이 없다**
- `/money/*` 4화면은 `payments`만 본다 → 식당 세션 실측 **0행**
- 커머스 구매(`commerce_orders`)는 `/buy/orders`에, 발주 주문은 `/orders`에 **따로** 있다
- **"이번 달 식자재비 총액"** 을 알려면 두 화면을 더해야 한다

### X-16 · 🟠 **가격이 오르내려도 알 수 없다**
`price_history` 테이블이 있지만 **0행**이고, 상품 상세에 가격 추이가 없다.
식자재는 시세 변동이 큰 품목인데 **"지금이 싼가"를 판단할 근거가 화면에 없다.** → 6단계 K-13

### X-17 · 🟠 **주문 마감·배송 가능 시간 안내가 없다**
"오늘 몇 시까지 주문하면 내일 오나"가 어디에도 없다. `shipping_groups` 테이블은 있으나 **0행**이다.

### X-18 · 💡 **장바구니가 공급자별로 안 나뉜다**
여러 공급자의 상품을 한 장바구니에 담으면 배송비·배송일이 각각 다를 텐데, 그 구분이 화면에 없다.
`shipping_groups`(0행)가 이걸 하려던 것으로 보이나 쓰이지 않는다.

### X-19 · 💡 **검색은 있으나 필터가 약하다**
`/buy`에 `search` 파라미터는 있다(확인함). 다만 가격대·공급자·배송일 필터는 보이지 않는다. 리스팅 38건에서는 문제없으나 늘어나면 필요해진다.

## E. 돈·정산의 마감이 없다

### X-20 · 🟠 **세금계산서 발행 흐름이 없다**
`ledger.ts`·`SettleOrderButton.tsx`·거래처 원장 화면에 "계산서" 문자열이 나오지만, **발행 API 연동이나 발행 이력 테이블이 없다.**
B2B 식자재 거래에서 세금계산서는 선택이 아니다.

1차 조사 `design-risk-report.md` R-05(거래명세서가 스냅샷이 아님)와 같은 뿌리다.

### X-22 · 💡 **회계 프로그램 연동이 없다**

## F. 계정·권한

### X-23 · 🟠 **한 사업장에 여러 사용자를 둘 수 없어 보인다**
운영 실측: `tenants` **8개**에 `users` **6명**. 즉 tenant당 1명 이하다.
사장·직원·배송기사가 각자 계정을 갖고 권한을 나누는 구조가 화면에 없다.
게다가 `users.auth_uid`가 **6/6 전부 NULL**이라(1차 조사) 인증 사용자와 앱 사용자의 연결 축도 비어 있다.

### X-24 · 🟠 **role이 없는 계정을 위한 자리가 이제서야 생겼다**
`tenants` 8개 중 **role NULL이 2개**다. 09-09 `8e40059`가 이들을 `/pending`으로 보내도록 고쳤지만, **그 상태를 관리자가 해소해주는 화면이 없다.**
`/admin/tenants`에서 role을 부여할 수 있는지는 이번 조사에서 확인하지 못했다(관리자 세션 로그인 실패).

## G. 「없는 게 아니라 만들다 만 것」 — 별도 분류

부족한 기능과 구분해야 한다. **코드는 있는데 데이터가 0행이거나 미배포**인 것들이다. 4단계 ⚫ 37화면이 여기 해당한다.

| 항목 | 상태 | 어디 |
|---|---|---|
| 지급 상세 화면 | 사이드바가 **`soon: true`로 명시** | 공급자OS |
| 발주(RFQ) 전 구간 | 화면 6개 완성 · **데이터 0행** | 양쪽 |
| 신뢰도·이상거래 | 코드 11테이블 · **0행** | 관리자OS |
| 가격 정책 | 결제 경로가 이미 읽음 · **0행** | 관리자OS |
| 자금 배분 | DB함수 있음 · **규칙 0행** | 공급자OS |
| 쿠폰·프로모션 | 화면 2개 · **0행** | 관리자OS → 식당OS |
| 현장 관찰기록 | **데이터 3행 있는데 화면 미배포** | 관리자OS |
| 찜·주문취소·타임라인·문의 | 검증 완료 · **14일째 미배포** | 식당OS |
| 구독 자동 재청구 | 498줄 완성 · **미배포** | 공급자OS |

> **이 목록이 "부족한 기능"보다 길다.** 새로 만들 것보다 **이미 만든 것을 살리는 쪽**이 먼저다. 6단계 조합 아이디어가 여기에 대응한다.

## J. 계정·권한 — 확인 결과

### X-23 갱신 · 🟠 **스키마는 다중 사용자를 지원한다. 코드 경로가 없다**

기존 서술은 "한 사업장에 여러 사용자를 둘 수 없어 보인다"였다. 절반만 맞았다.

**스키마는 이미 준비돼 있다**
```
users 컬럼: id, tenant_id, email, role, user_type, auth_uid, created_at
                              ^^^^  ^^^^^^^^^
```
`users.role`과 `users.user_type`이 존재한다. 즉 **한 tenant 아래 역할이 다른 여러 사용자**를 담을 수 있게 설계돼 있다.

**그런데 넣을 방법이 없다**
```
src/actions/ 전체에서 users INSERT 가 일어나는 곳 = createTenantWithUser() 한 곳뿐
  → tenant 를 새로 만들 때 사용자 1명을 같이 만든다
  → 기존 tenant 에 사용자를 추가하는 경로(초대·직원 등록)는 없다
```

**운영 실측이 그대로 보여준다**
| role | tenants | users |
|---|---|---|
| supplier | 2 | 2 |
| restaurant | 3 | 3 |
| admin | 1 | 1 |
| **NULL** | **2** | **0** |

tenant당 사용자가 **정확히 1명**이고, tenant별 사용자 수를 세면 **전부 1**이다. 우연이 아니라 **구조가 그렇게밖에 안 되기 때문**이다.

**정확한 표현**: 「기능이 없다」가 아니라 **「테이블은 있는데 그 테이블을 채우는 화면이 없다」.** 사장·직원·배송기사 구분은 스키마 변경 없이 화면만 만들면 된다. **난이도가 생각보다 낮다.**

### X-24 갱신 · 🔴 **role NULL 계정을 관리자가 되살릴 방법이 없다 — 확인됨**

## L. §I 판단 기록에 추가

- **X-23·X-24를 "없어 보인다"에서 "없다"로 확정하는 데 필요한 것은 코드 확인 한 번이었다.** 이번에 `src/actions/` 전체에서 `role` UPDATE와 `users` INSERT 지점을 세어 확인했다.
- **X-23은 확인해 보니 원래 판단보다 가벼운 문제였다.** 스키마(`users.role`, `users.user_type`)가 이미 다중 사용자를 전제하고 있어, 없는 것은 **기능이 아니라 화면**이다.
- ~~**X-24는 반대로 무거워졌다.**~~ → **이 판단은 틀렸다.** "되살릴 수단이 없다"(코드 갭)는 맞았지만, **"운영에 막힌 계정이 2개 있다"는 사실이 아니었다.** `tenants.role IS NULL`만 세고 **사용자 유무를 확인하지 않은** 것이 원인이다. 그 2개는 사용자 0명의 E2E 가입 잔재였다(§X-24 정정).
- **교훈**: 「NULL인 행이 N개 있다」에서 「사용자 N명이 막혀 있다」로 넘어갈 때, **그 행에 사용자가 붙어 있는지**를 한 번 더 확인해야 했다. 1차 로그 `0-3`이 예고한 정적 판단의 한계가 데이터 판단에서도 같은 형태로 반복됐다.
